# 수직형 초기 실행 실패 분석

2026-09-19 작성. 대상은 `run-f2533ee`의 초기 구현 검증이다. **검증 실패를 보존하며, 수평·수직 성능 비교나 정책 효과의 증거로 사용하지 않는다.** 이후 수정 실행과 별개로 이 기록을 유지한다.

## 진행사항

기준정책(`NO_REALLOC`: 블록·시간을 바꾸지 않음)의 2일 입력을 시뮬레이션 시작 후 50시간까지 처리했다. 외부 트럭은 모두 끝났지만 본선 작업은 남았다.

| 확인 항목 | 초기 실행 결과 | 뜻 |
|---|---:|---|
| 외부 트럭 | 120 / 120대 완료 | 트럭 완료만으로 전체 작업 완료를 판단할 수 없다. |
| 본선 작업 | 4,469 / 5,738건 완료 | 1,269건이 종료 시점에 남았다. |
| 실행 검사 | 19개 중 18개 참 | `all_vessel_work_completed`만 거짓이며 전체 판정은 실패다. |
| 시간 조정 정책(`RL_TIME`) | 실행하지 않음 | 기준정책 검증 실패 후 다음 정책으로 넘어가지 않았다. |
| 새 학습·이 분석에서 시작한 시뮬레이션 | 각각 0회 | 저장된 초기 실행 자료만 계산했다. |

[검증 결과](run-f2533ee/NO_REALLOC/qualification.json)와 [실패 기록](run-f2533ee/failure.json)을 그대로 유지했다. 결과 파일, 압축 입력, 원본 관측 기록과 입력 일치 등을 17개 항목으로 재확인했으며 모두 일치했다. 이는 **자료 정합 검사 통과**이며, 실패한 실행 판정을 통과로 바꾸는 것이 아니다.

## 해석: 트럭 120대가 전체 저부하를 뜻하지 않는 이유

하루 외부 트럭은 60대씩이지만, 별도로 16개 본선 작업 묶음에 5,738건이 들어 있다. 선박에서 내리거나 선박으로 보내는 이 물량도 야드 크레인과 내부 이송차량을 사용한다. 따라서 트럭 수만 줄였다고 전체 장비 작업량이 작은 것은 아니다.

YT(선박과 야드 사이에서 컨테이너를 옮기는 내부 차량)는 블록마다 3대를 사용하며, 같은 블록의 적하와 양하가 이 3대를 공유한다. 원래 환경의 이송 주기는 180초였고, 초기 수직형 구현에서는 합성 도로 거리로 계산한 왕복 주기가 블록별 410.4~762.4초가 되었다. 이는 현장 측정값이 아니라 이번 구현의 명시적 가정이다.

대기나 크레인 작업시간을 모두 무시해도 필요한 시간을 계산했다. 블록별 전체 이송 완료의 낙관적인 하한은 다음과 같다.

`첫 본선 작업 시작시각 + 올림((적하 건수 + 양하 건수) / 3대) × 이송 주기`

3대가 처음부터 모두 비어 있고, 모든 물량을 즉시 처리할 수 있다고 가정한다. 실제 작업 투입 간격, 크레인 처리시간, 대기와 충돌을 넣으면 더 늦어질 수 있다. 아래 시간은 실행 시작 후의 시각이며, 실제 완료시각 예측은 아니다.

| 블록 | 적하+양하 건수 | 왕복 주기(초) | 전체 이송 완료 하한(시간) | 실제 남은 야드 작업 |
|---|---:|---:|---:|---:|
| Y02 | 804 | 744.8 | **63.03** | 348 |
| Y03 | 324 | 727.2 | 29.97 | 0 |
| Y04 | 359 | 709.6 | **50.35** | 67 |
| Y05 | 448 | 692.0 | 36.42 | 36 |
| Y06 | 364 | 674.4 | **53.58** | 118 |
| Y09 | 687 | 621.6 | 49.15 | 65 |
| Y10 | 680 | 604.0 | 46.24 | 80 |
| Y13 | 331 | 551.2 | 26.61 | 0 |
| Y14 | 690 | 533.6 | 43.70 | 325 |
| Y18 | 364 | 463.2 | 46.43 | 155 |
| Y19 | 687 | 445.6 | 37.96 | 75 |

본선 물량이 없는 나머지 10개 블록까지 포함한 수치는 [분석 JSON](initial-diagnostic-analysis.json)에 있다. Y02는 첫 작업이 7.587시간에 시작하므로, `7.587 + 올림(804/3) × 744.8/3600 = 63.033시간`이다. 모든 이송을 50시간 안에 끝내는 것은 이 낙관적인 계산으로도 불가능하다.

**전체 이송 완료와 야드 작업 완료는 서로 다른 사건이다.** 적하는 야드 작업이 끝난 뒤 선박 쪽 이송이 이어질 수 있다. 따라서 위 표만으로 야드 작업 미완료 1,269건을 모두 설명하지 않는다.

양하(선박에서 내려 야드로 들여오는 작업)는 도착 이후에 야드 처리가 가능하므로, 양하 묶음별로도 별도 계산했다. 다른 묶음과 경쟁하지 않고 차량 3대를 독점한다고 해도 `양하 시작시각 + 올림(양하 건수/3) × 주기`가 다음과 같다.

| 블록 | 양하 건수 | 마지막 양하 도착 하한(시간) |
|---|---:|---:|
| Y02 | 356 | **55.24** |
| Y04 | 359 | **50.35** |
| Y06 | 364 | **53.58** |
| Y10 | 356 | **50.58** |

위 4개 묶음은 양하 도착만으로도 50시간을 넘는다. 이 계산은 왕복 이동을 하나의 완료 사건으로 처리하는 **현재 시뮬레이터**에 대한 하한이다. 실제 차량의 편도 도착과 빈차 복귀를 나눈 현장 모델의 하한으로 일반화하지 않는다.

반대로 하한이 50시간보다 짧다고 완료 가능성이 입증되지는 않는다. **Y05와 Y14에서 작업 대기 중 크레인이 쉬는 현상은 별도로 진단 중이다.** 차량 용량만으로 모든 잔여 작업을 설명하거나, 장비가 서로 기다려 멈추는 문제가 없다고 결론 내리지 않는다.

## 기존 환경 진단과 비교 범위

[기존 환경의 같은 2일 입력 진단](legacy-two-day-diagnostic.json)은 트럭 120대와 본선 5,738건을 모두 완료했다. 시드, 외부 요청, 초기 재고, 본선 물량의 식별값이 같고 기존 합성 도착곡선도 유지되었다.

다만 새 구현에서는 도로 거리와 이송시간뿐 아니라 양 끝 인계, 크레인 역할, 동시에 처리할 수 있는 양하 물량 제한도 함께 달라졌다. 이 차이는 구현 원인 점검에 쓰며, **수직 배치가 수평 배치보다 나쁘다는 증거가 아니다.** 기존 환경을 검증된 수평형으로 부르지도 않는다.

## 남은 판정과 증거 보존

현재 판정은 **초기 구현의 본선 전량 완료 검사 실패**다. 원인 확인과 수정 검증 전에는 시간 조정 정책의 성능이나 수평·수직 우열을 주장할 수 없다. 이 문서는 새로운 실행을 승인하거나 기존 연구 판정 기준을 변경하지 않는다.

원본 결과·실패 기록·압축 입력·환경 설정·기존 환경 진단·원본 관측 파일의 SHA-256(파일 내용이 바뀌었는지 확인하는 값)을 [분석 JSON](initial-diagnostic-analysis.json)에 저장했다. 계산에 사용한 모든 블록과 양하 묶음의 원시 수치, 계산식, 미해결 원인도 함께 남겼다.

후속 확인: Y05/Y14 정체는 가능한 후보를 모두 탈락시키는 후보 축소 문제였다. [수정 재생 검증](deadlock-probe-f2533ee/candidate-fix-replay.json)에서 같은 상태의 1시간 처리량이 두 블록 모두 0건에서 10건으로 늘었다. 이 국소 수정이 위의 초기 실행 수치나 운반 용량 하한을 바꾸지는 않는다.
