# K 비교 후속 확인 — 기존 자료 점검

2026-11-10. **예약 정보 설명의 오류와 비용 증가 위치를 확인했다. 판단 반전의 원인은 아직 확정하지 않았다.**
기존 파일을 읽고 집계한 탐색적 점검이다. 새 시뮬레이션·학습·정책 변경은 없다.
현재 합성 환경의 결과이며 실제 터미널의 성능이나 최적 K를 증명하지 않는다.

## 1. 이번에 확인한 범위

- K=1·2·3·6의 학습 기록 72개: 같은 결정 295개 × K 네 가지 = 비교 쌍 1,180개.
- 반복 실행을 제외한 기존 평가 144개: 입력은 9개이고 모델 초기값은 3개다.
- 입력 9개의 기존 트럭 장부 78,000건: 예정된 게이트 진입과 실제 진입을 대조했다.
- 비추적 DGT 방문 원자료 100건: 필드 채움과 통지 시각만 집계했다. 개인·화물 식별자는 내보내지 않았다.
- 원래 실험의 코드·설정 파일 해시, 학습 기록 해시, 같은 질문·입력·첫 공동 배정을 대조했다.

재실행: `python scripts/v7/audit_horizon_evidence.py` (저장소 루트, 표준 라이브러리만 사용).

## 2. 예약 정보: 기존 설명을 정정한다

**최근 K 실험의 하루 무대도 예약 시각과 실제 게이트 진입 시각이 같다.**
기존 작업 문서의 “하루는 약 10분 오차, 30일은 오차 0” 설명은 실제 하루 실행 경로와 달랐다.

1. `stage/vessels.py:build_diurnal_v3`가 도착 명단에 `arrival_s`를 기록한다.
2. `stage/orders.py:orders_from_schedule`이 같은 값을 `in_out_reserve_s`에 넣는다.
3. `V3Announcer.review`가 같은 `arrival_s`를 작업 생성과 실제 투입에 전달한다.
4. `_job_from_entry`는 별도 실현 시각이 없으면 전달받은 진입 시각을 실제 진입에도 쓴다.
5. 기존 장부 78,000건에서도 명단의 진입 시각과 실제 진입 시각 차이는 전부 0초였다.

장부에는 공개 예약 필드가 별도로 저장되어 있지 않다. 예약 매핑은 코드 확인이고,
78,000건은 명단→실제 진입 대조다. 둘을 구분해 근거로 남긴다.
600초 준수 오차 설정은 다른 생성 경로에 있으며 최근 하루 평가에서는 적용하지 않는다.
블록까지의 실제 주행에는 오차가 있을 수 있으므로 “모든 미래 시각이 정확하다”는 뜻은 아니다.
정책은 공개 예상값을 읽지만 그 예상의 게이트 진입 부분이 완벽하게 맞도록 만든 환경이다.
이 사실만으로 K별 성능 차이의 원인을 확정할 수는 없다. 모든 K가 같은 조건에서 비교됐다.

## 4. K1과 K6의 판단 반전은 끝에서 잘린 탓인가

| 구분 | 비교 결정 | 우열이 뒤집힌 결정 |
|---|---:|---:|
| 전체 | 295 | 87 (29.5%) |
| 6시간을 온전히 비교 | 242 | 78 (32.2%) |
| 환경 종료로 6시간보다 짧게 비교 | 53 | 9 (17.0%) |

끝에서 잘린 경우를 제외해도 반전이 남는다. **관찰시간 부족만으로 반전을 설명할 수 없다.**
다만 각 K의 종료 경계가 전혀 영향을 주지 않는다는 판정은 아니다.
반전 87건 모두 K1·K6의 비용 격차 절댓값이 각각 1원보다 크다. 반올림 수준 차이만은 아니다.
정규화 전후 부호가 모두 일치했다. 같은 종료시각이 된 K 간 비교 64건의 비용도 일치했다.
동률 여부가 바뀐 결정은 별도 6건이며 87건에 섞지 않았다.

반전 중 48건(55.2%)은 반출끼리·반입끼리·적하끼리 등 **같은 업무 종류 사이의 선택**이다.
따라서 트럭과 본선의 가중치 충돌만을 유일한 설명으로 삼을 수 없다.
같은 업무끼리의 선택도 이후 본선에 영향을 줄 수 있으므로 본선 비용 영향을 배제한 것은 아니다.
295개 선택은 18개 학습 입력에서 나온 종속된 관찰이며 독립 실험 295회가 아니다.

## 5. 실제 하루 평가에서 어디가 나빠졌나

아래는 개별 학습 선택의 비용이 아니라 **학습된 정책을 하루 운영한 기존 평가**다.

| 하루 트럭 주문 | K1 평균 체류(분) | K3 | K6 | 해석 |
|---|---:|---:|---:|---|
| 3,500 | 22.290 | 21.632 | 23.479 | K3이 K1보다 짧다. |
| 7,500 | 55.213 | 53.224 | 58.579 | 여기서도 K3이 K1보다 짧다. |
| 15,000 | 173.696 | 200.252 | 203.848 | K1의 전체 평균 이득은 특히 이 혼잡 조건에서 크다. |

평균은 24시간까지 관측한 게이트 진입→출차 시간이며 미출차 트럭도 그때까지의 시간을 센다.
부하별로 모델 3개×입력 3개를 평균했다. 모든 부하에서 K 증가가 단조 악화를 만든 것은 아니다.

K6−K1의 평균 총비용 증가는 208,826,663.19원, 그중 트럭 체류 항은 201,931,695.23원이다.
즉 **추가 비용의 96.70%가 트럭 체류 항**이다. 부하별 비중은 40.91%·71.98%·99.30%다.
현재 모형의 공식 비용 분해이며 실제 청구 비용이나 손실 금액이 아니다.
K6는 K1보다 평균 본선 비용도 더 높아, 단순히 본선 이득을 위해 트럭을 희생했다고 설명할 근거는 없다.
이 집계는 손실이 나타난 위치를 알려주며, 개별 학습 신호의 반전 원인을 증명하지는 않는다.

## 6. 입력과 학습량에서 확인한 범위

- 공통 학습 후보 590개 중 본선 후보는 153개이고, 142개(92.81%)의 마감 여유 입력이 ±2시간 상한에 있다.
  마감 여유가 크게 달라도 같은 값으로 표시될 수 있다. 전체 운영 후보 비율이나 실항만 비율은 아니다.
- 15,000건 조건의 트럭 후보 195개 중 62개는 대기 입력의 2시간 상한에 있다.
  긴 대기의 차이가 사라지는 경로다. 이것이 K6 손실 원인이라는 판정은 아직 없다.
- K마다 갱신 18회·총 최적화 900단계로 같았다. 학습에서 떼어둔 동률 아닌 비교 49개의
  우열 정답률은 K1 55.1%, K2 55.1%, K3 63.3%, K6 55.1%다.
  작은 내부 검증 집계이며 독립 운영 검증이 아니다. 더 오래 학습하면 해결된다는 근거는 없다.
- 원화 비용 격차의 중앙값은 K1 약 15,489원→K6 약 199,524원으로 오히려 커졌다.
  정규화가 부호를 바꾸지 않았으므로 “보상 숫자가 작아져서 희석됐다”는 단순 설명은 지지하지 않는다.

## 7. 아직 답할 수 없는 부분과 다음 순서

기존 1,180개 분기 비교는 **합계 비용만** 저장했다. 트럭·본선·이동·재취급별 값과
후속 작업 결정 기록이 없어, 0~1·1~2·2~3·3~6시간 중 어느 업무가 반전을 만들었는지 복원할 수 없다.
K별 종료 비용을 빼서 만든 값은 종료점 간 차이일 뿐이다. 공통 구간의 진행이 같다는 검증 없이
그 값을 실제 시간 구간별 기여라고 부르지 않는다. 이 차이는 결정별 파일에 그 이름으로 보존했다.

1. [예약 보정](../../../.claude/docs/dashboard-task-specs/YR-332-f-v7-truck-info-realism.md)과
   [운반 보정](../../../.claude/docs/dashboard-task-specs/YR-332-i-discharge-calibration.md): 원자료와 사건 정의부터 맞춘다.
2. [분기 비용 기록](../../../.claude/docs/dashboard-task-specs/YR-323-f-branch-cost-trace.md):
   보정·착수 조건을 충족한 뒤 동일 비교에 비용 항목과 후속 결정을 남겨 원인을 분리한다.
3. [본선 긴급도 입력](../../../.claude/docs/dashboard-task-specs/YR-332-x-vessel-slack-input-scale.md)과
   [기존 개선 목록](../../../.claude/docs/dashboard-task-specs/YR-323-a-horizon-cause-audit.md): 재현된 원인에 맞는 한 축만 검증한다.

현재는 원인 분해 전체 완료나 K1 채택 단계가 아니다. 기존 성능·현실성 미통과 판정을 유지한다.
