# 운반 흐름·대기 수·고물량 근거 재확인

2026-11-20 · YR-332-i(내부 운반), f(대기 수 정의), ap(고물량 도착 몰림).

**기존 자료의 정확한 전달은 다시 확인했다. 그러나 운반 단계·대기 집계 정의와 고물량 실측 근거가 추가되지는 않았다.**
현재 학습·평가 결과는 합성 환경 결과로 유지하며, 이 확인으로 실제 항만 성능을 승인하지 않는다.

## ① 진행사항

사용자의 후속 확인 요청에 따라 기존 세 작업의 현실성 보정 허가를 받고 읽기 전용으로 조사했다.
[허가 기록](authorization.json) · [집계 원값](summary.json) · [검증](verification.json).

- 원자료 600파일, 452,795,529바이트: 추가·누락·내용 변경 모두 0.
- 대기 값 48,620건은 원본 로그와 일치. 본선 목록 263개 CSV/JSON 쌍, 291,499행의 비교 시각 필드도 일치.
- 과거 감사의 원자료 목록·대조·대기·본선·보정 겹침 보고서 5개가 이번 재실행과 바이트까지 같다.
- 시각 근거가 확인된 현재 보정 표본은 13일, 컨테이너 오더 33,703건, 실제 트럭 방문 27,395번이다.
  분별 방문 수를 다시 합해 확인했으며, 관측 최대는 여전히 시간당 245번이다.
- 최근 정책 비교(bc)의 기존 최종 평가 입력 9개를 재생성했다. 오더 명단·물리 입력·본선 입력의 저장 검사가 모두 일치했다.
  정책 실행 없이 **트럭 방문 단위**로 시간당 도착 수만 셌다. 새 학습·정책 평가·보정값 변경은 없다.

### 최근 평가 입력과 관측 범위

| 하루 컨테이너 오더 수 | 세 입력의 최대 시간당 트럭 방문 수 | 관측 최대 245번을 넘는 시간대 |
|---:|---:|---:|
| 3,500건 | 216~237번 | 0 / 72시간 |
| 7,500건 | 461~503번 | 35 / 72시간 |
| 15,000건 | 917~997번 | 60 / 72시간 |

각 물량에서 서로 다른 하루 입력 3개 × 24시간을 센 값이다. 오더 수와 방문 수를 서로 비교한 표가 아니다.
7,500·15,000건은 기존 자료의 관측 범위를 넘어선 혼잡 시험이다.
3,500건의 최대 시간당 방문 수가 범위 안이라는 사실만으로 모든 시각·블록·운반 조건이 현실적이라고 결론내릴 수 없다.
**245번은 이 자료의 최대 관측값이며 터미널 처리 한계가 아니다.** 자료의 터미널 전체 포함률도 아직 확인되지 않았다.

### 공식 자료로 확인할 수 있는 범위

- ChainPortal 앱 설명은 트럭 시간을 **게이트 진입부터 상·하차까지**로 정의한다. 현재 연구의 게이트 진입→작업 완료 지표와 방향이 맞는다.
  다만 이름이 같은 지표라도 실제 사건 시각의 정확성과 집계 단위는 별도로 검증해야 한다.
  [공식 앱 매뉴얼, PDF 23쪽](https://www.chainportal.co.kr/manual/download?filename=ChainPortal_APP_Manual.pdf).
- 같은 매뉴얼은 블록 대기 차량 수를 표시하고 게이트 진입·블록 진입·작업 완료·출차를 구분한다.
  확인한 본문에는 대기 수의 포함 대상과 작업 시작 경계에 관한 상세 정의가 없다.
  [공식 앱 매뉴얼, PDF 12·19~22쪽](https://www.chainportal.co.kr/manual/download?filename=ChainPortal_APP_Manual.pdf).
- DGT는 안벽크레인 1기당 운반차 5대와 블록 양측 크레인 분리를 설명한다.
  이것은 현재 합성 모형의 블록당 3대와 배정 단위가 달라 그대로 교체할 근거가 아니다.
  [공식 장비 소개](https://www.dgtbusan.com/DGT/terminal/equipment).
- ChainPortal 정보서비스 매뉴얼에는 OpenAPI 사용 가이드와 이용 신청·승인 절차가 있다.
  현재 확보한 공개 매뉴얼 자체는 위 필드의 상세 사전을 제공하지 않는다. 기존 사용자 측 API 명세나 제공처 정의가 우선 확인 대상이다.
  [공식 정보서비스 매뉴얼, PDF 34~35쪽](https://www.chainportal.co.kr/manual/download?filename=Chainportal-TIS-Manual.pdf).

양하 시각 간격 중앙 13분·적하 24분은 이번에도 재현됐다. 하지만 대기·주행·작업을 분리한 값이 아니므로
현재 470초 운반 주기를 대체하지 않는다. 외부 트럭 ID는 자료에 있으나, 내부 운반차의 이동·가용량 기록과는 다르다.

현재 분별 도착 생성은 **상관된 분별 변동 수식(`correlated_minutes`)**이다. 과거 ak의 날짜 겹치기 방식과 구분한다.
생성 수식을 바꿨다는 사실이 고물량 실측 근거를 새로 만들지는 않는다.
과거 감사에 나오는 미확인 게이트 시각 601건은 보존된 원본의 문제이며, ba·bb에서 현재 보정 대상과 이미 분리했다.

### 판정의 의미

- 기록이 서로 맞는가: 이번 원본 재대조와 기존 입력 재생성 검사는 통과했다.
- 실제 항만처럼 움직이는가: 운반·대기 정의·고물량 포함 범위가 남아 여전히 미통과다.
- 정책이 좋아졌는가: 이번에는 새로 측정하지 않았다. bc의 성능 판정과 기본 정책을 유지한다.

따라서 i/f/ap 작업 전체를 완료 처리하지 않고 외부 근거 대기로 남긴다. 확인 작업 완료와 현실성 보정 완료는 다르다.

## ③ 예정사항

1. **f — 대기 수 정의 확인:** 기존 API 필드 사전과 작업 시작 기록을 확인한다. 모형의 작업 대기 오더 수와 같은 대상을 세는지 판단하기 위해서다.
2. **i — 내부 운반 연결 확인:** 익명 차량의 배정·운반·인계·복귀와 실제 투입 대수를 확보한다. 현재 3대·470초를 실측으로 보정할 수 있는지 판단하기 위해서다.
3. **ap — 고물량 근거 확인:** 전체 기록 포함률과 더 바쁜 날짜의 분별 방문 자료를 확인한다. 고물량 합성 시험의 주장 범위를 정하기 위해서다.

세 작업 모두 기존 Dashboard 등록 과제다. 상세한 최소 항목은 [자료 정의 확인표](../../../../docs/research/v7-discharge/transport-queue-data-contract.md)에 있다.
외부 기관에 메시지를 보내거나 API 이용 신청을 하지는 않았다.

## 재현

저장소 루트에서 기존 연구 환경의 Python과 `PYTHONPATH=src;scripts/v7`을 사용한다.

```text
python scripts/v7/recheck_transport_queue.py --out outputs/reports/yr332_realism_readiness/2026-11-20/raw-replay
python scripts/v7/check_realism_readiness.py --out outputs/reports/yr332_realism_readiness/2026-11-20
```

원본 감사의 `base_commit`은 실행 시점 기록이므로 과거 감사와 달라질 수 있다. 비교한 5개 집계 파일은 그 메타데이터를 포함하지 않는다.
현재 보정·평가 묶음·기존 게이트 파일 6개의 해시는 검사 전후 같았다. 원본 식별자와 개별 사건 원문은 새 보고서에 공개하지 않는다.
