# YR-331-c — 보정 시드 9921000 의 공급 부족 복구

## 한 줄 결론

배(본선)에 **실을 상자를 정할 때 블록에 실제로 상자가 몇 개 있는지 안 봤다.** 그래서
Y08 블록이 첫날 큰 적하(배에 싣기) 537개를 받았고, 사흘 뒤 장부가 5개 모자랐다.
이제 월말에 상자가 모자라는 블록이 생기면, 그 블록의 **가장 늦은 적하 한 줄을 양하(배에서
내리기)로 돌려** 다시 계획한다. 원래 문제가 없던 계획은 한 줄도 바뀌지 않는다.

## 무엇이 문제였나

생성기는 블록마다 "들어오는 상자 ≥ 나가는 상자" 를 요구한다 (`fixed_seed.py` 의 공급 검사).

| Y08 (시드 9921000, 부하 3,500/5,000/7,500) | 상자 수 |
|---|---|
| 처음부터 있던 상자 | 648 |
| 트럭이 가져온 상자 (반입) | 323 |
| **원천 합계** | **971** |
| 트럭이 가져갈 상자 (반출) | 439 |
| 배에 실을 상자 (첫날 적하 1줄, `D00-M1-s2`) | 537 |
| **반출 합계** | **976** → 5개 부족, 생성 거부 |

왜 적하가 됐나 — `month.py` 의 `plan_month_vessels` 는 블록마다 **흐름 수지**만 센다.
"배로 들어온 양 − 배로 나간 양" 이 "트럭이 빼 간 양" 에 못 미치면 내리고, 아니면 싣는다.
Y08 은 시작값이 +1(블록 순번으로 정한 임의값), 첫날 트럭 순반출도 +1 이라 "못 미침" 이
아니어서 537개 적하가 정해졌다. 이 규칙에는 **블록에 지금 상자가 몇 개 있는지(초기 648)**와
**적하 한 줄의 크기(537)**가 들어가지 않는다. 648 − 537 − (사흘 트럭 순반출 1+44+71=116) = −5.

보존식이 깨진 곳은 생성 3단계 중 **둘째 단계(`plan_month_vessels`)** 다. 첫 단계
(`build_month`, 트럭 명단·초기 적재)와 셋째 단계(`build_fixed_seed`, 상자 짝짓기)는
수량을 바꾸지 않았고, 셋째 단계는 모자람을 정확히 잡아 거부했다.

## 어떻게 고쳤나

- 바꾼 입력 계약: **본선 흐름 방향(적하/양하)** 한 가지. 트럭 주문 수·시각, 초기 적재,
  배 물량·시각은 그대로다.
- `plan_month_vessels(..., initial_stock=...)` 를 주면, 계획을 다 세운 뒤 블록별 월말 장부
  (초기 + 반입 + 양하 − 반출 − 적하)를 계산한다. 음수인 블록은 그 블록의 가장 늦은 적하
  한 줄을 양하로 고정하고 처음부터 다시 계획한다. 모자람이 없어질 때까지 반복한다.
- 적하가 하나도 없는데 트럭만으로 모자라면 고치지 않고 그대로 넘긴다 → 생성기가 거부한다.
  (상자를 새로 만들지 않는다.)
- 쓰는 정보는 **계획 명단뿐**이다. 실제 작업 완료 시각·정책·보상은 보지 않는다.
- 이 인자를 넘기는 곳: `ppo/workload_experiment.py`, `scripts/v6/probe_reward_scale.py`.
  인자를 안 넘기는 호출(30일 legacy `month_run`, GPU 학습)은 예전과 똑같이 동작한다.

## 무엇을 시험했나

1. **원 시드 9921000**: 고치기 전 경로는 지금 코드에서도 Y08 원천 971 · 반출 976 · 부족 5
   로 똑같이 거부된다(재현). 고친 뒤에는 바뀐 줄이 Y08 첫날 537개 **한 줄**뿐이고,
   생성·독립 감사를 통과한다(Y08 원천 1,508, 계획상 기다리는 반출 0).
2. **이미 통과하던 시드 7개**(9911000·9931000·9941000·9951000·9961000·9971000·9981000):
   계획이 **완전히 같다**. 생성된 자료의 해시도 인자 유무와 상관없이 같다.
3. **경계 사례**(단위 시험): 월말 재고가 −5·−1 이면 양하로 바뀌고, 정확히 0 이면 적하를
   그대로 둔다. 마지막 적하를 돌려도 모자라면 그다음 늦은 적하까지 돌린다. 적하가 없으면
   무한 반복 없이 그대로 돌려준다.
4. **넓은 표본**(시드 30개 × 3가지 기간, `supply-sweep.json`): 예전 규칙으로 모자라는 시드가
   3일 1/30 · 5일 3/30 · 9일 8/30 개였다. 고친 뒤 모두 0. 문제없던 시드가 바뀐 경우는 0.

## 선택 편향에 대해

- 9921000 은 운이 나쁜 예외가 아니었다. 기간이 길수록 부족이 흔해진다(9일이면 4개 중 1개 꼴).
  예전에 통과한 시드만 쓰면 "적하가 커도 재고가 넉넉한 달" 쪽으로 자료가 치우친다.
- 고친 뒤에는 그 시드들도 쓸 수 있지만, 바뀐 시드에서는 해당 블록의 배 한 줄이 내리는 쪽이
  되므로 **그 배의 싣기/내리기 비율이 달라진다.** 이것이 실제 터미널과 맞는지는 대조하지 않았다.

## 확인하지 못한 것

- 블록이 **도중에** 꽉 차는지(용량 1,440칸): 월말 재고 최대는 1,271 로 용량 안이지만,
  달 중간의 최고치는 재지 않았다.
- 시점 문제: 생성기 계약은 월 전체 수량만 본다. 반출이 상자 도착보다 먼저 계획된 경우는
  지금처럼 "기다림" 으로 남는다(원 시드 고친 뒤 0건).
- 30일 legacy 경로·GPU 경로는 그대로 두었다. 같은 문제가 거기서 생기면 따로 연결해야 한다.
