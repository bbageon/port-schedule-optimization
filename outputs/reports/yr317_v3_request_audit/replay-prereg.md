# YR-317-g — 실패 시점 재관측 사전 고정

2026-09-15. 사용자 지시: 리뷰 대응 다음 단계 실행. 최대 14코어 사용 범위에서 이번 세 정책에 3코어를 배정한다.
이 문서는 이미 끝난 최초 진단의 계약을 대체하지 않는다. 새 관측 기능을 켠 후속 재생의 조건을 실행 전에 고정한다.

## 질문과 범위

- 반출 대상이 없었던 순간 실제 재고가 없었는가, 재고는 있지만 모두 기존 작업에 지정돼 있었는가?
- 용량 거절 당시 실제 빈 공간이 부족했는가, 미도착 작업·예약을 빼면서 투입 여유가 부족해졌는가?
- 원래 본선 요청이 투입·완료·잔여·미투입으로 빠짐없이 보존되는가?
- 새 기록을 켠 결과의 비용·행동·처리 수가 기존 10일 진단과 일치하는가? 차이가 있으면 그대로 보고한다.

## 고정 조건

- 동결 가중치: `outputs/v3/month-02/ckpt_029.pt`. 학습·새 정책 선택·탐색은 없다.
- 관측 기능 `capture_requests=True`, `diagnose_admissions=True`. 정책·환경 투입 규칙·비용식은 기존 그대로다.
- 세 정책: NO_REALLOC(변경 없음), RL(전체), RL_NOVETO(수락 거절 기능만 제거).
- 연결 검사: 각 정책이 같은 시드 9,900,700의 하루 300대 요청을 1회 처리한다. 세 실행은 별도 프로세스로 동시에 진행한다.
- 연결 검사에서 요청·본선 전건 완료, 기록 대조, 학습용 분기 호출 0, 정책 예외 0을 요구한다. 실패하면 10일 진단을 시작하지 않는다.
- 본 진단: 시드 9,500,000의 원래 `plan_month` 앞 10일을 각 정책 1회 재생한다. 트럭 요청 69,000건, 기존 종료 뒤 2시간 추적을 유지한다.
- 정책끼리 병렬 실행하되 한 정책 내부 날짜는 연속한다. 요청 난수·초기 재고·비용·날짜를 재선정하지 않는다.
- CPU 번호 0·1·2를 정책별로 고정하고, 각 프로세스의 계산 스레드는 1개로 제한한다. 기존 v5의 CPU 23은 사용하지 않는다.
- 낮은 실행 우선순위, 최대 동시 실행 3개. 실패 시 이 실행기가 만든 자식 프로세스만 정지한다.
- 연결 검사 3회 + 본 진단 3회가 전체 예산이다. 이득을 보고 기간·시드·횟수를 늘리지 않는다.

## 산출물과 판정

- 정책별 폴더의 진행 상태, 비용·일별 행동, 압축 요청 장부, 실패 시점 재고, 본선 투입·완료·잔여를 저장한다.
- 세 정책의 최초 요청 지문을 대조하고, 요청별 사건·기존 비용식을 별도 분석 코드로 검산한다.
- 기존 10일 결과와 날짜별 비용·거래·처리 수를 비교한다. 오차를 숨기거나 반복 실행해 좋은 재현만 고르지 않는다.
- 원자료가 모이면 `full/summary.json`, 비용·실패 원인 표 `full/results.md`를 자동 생성한다.
- 미지정 재고가 있는데 대상이 없거나 여유 계산이 맞지 않는 경우는 추가 확인 대상으로 남긴다.
- 미투입·누락·불리한 결과를 삭제하지 않는다. 검사 실패와 실행 실패도 별도 파일로 남긴다.
- 성능 확증·현실 제약 검증·수평/수직 평가가 아니다. 새 기록이 정상이어도 현실성과 성능을 자동 통과 처리하지 않는다.

실행기: `scripts/v3/run_admission_replay.py`. 코드·본 계약을 commit·push한 뒤 깨끗한 별도 체크아웃에서 시작한다.
후속 판단은 YR-317-g 안에서 실패 경로·재현 차이를 검토하고 필요한 단일축 보정 범위를 정하는 작업이다.
