# 명단 보조 시각 필드 정리 (YR-332-an)

## 결론

하루 명단의 보조 필드 `gate_in_s`(실제 게이트 진입 시각을 BNCT 규격 이름으로 복사해 둔 값)가
보정 전 시각으로 남던 문제를 고쳤다. **시뮬레이션 결과는 한 비트도 바뀌지 않았다.**
바뀌는 것은 보정 입력(aj·ak)의 입력 지문뿐이다.

## 진행사항

- **원인**: 명단을 만들 때 `order_schema.attach`가 그 순간의 도착 시각을 `gate_in_s`에 복사한다.
  그 뒤 aj(시간대 비중)·ak(시간대 안 간격) 보정은 `arrival_s`만 바꿨다.
- **수정**: `build_stage`가 모든 도착 보정을 마친 뒤 `gate_in_s`를 `arrival_s`에 다시 맞춘다(기본값).
  예약 시각 `reserved_s`는 예약 계약이 이미 다시 쓰므로 건드리지 않는다.
- **저장 입력 재현 방법**: `build_stage(..., bnct_time_sync=False)`로 만들면 aj·ak의 저장 입력 지문 9개가 그대로 나온다.
- **읽는 경로 확인**: v7 코드와 스크립트에서 `gate_in_s`를 읽는 곳 92곳을 나열했다.
  모두 실행 기록(실제로 들어온 시각을 적는 장부), GPU 배열, 실자료 행이다.
  명단의 보조 필드를 읽는 엔진·평가 경로는 없었다.

## 검증

| 검사 | 결과 |
|---|---|
| 저장된 ak 실행 4건 재실행(3,500·7,500건, 규칙·학습 모델) | 결과·트럭 행·후보·선택·사건·작업·기록 해시 모두 동일 |
| 보조 필드를 엉뚱한 값(-12345초)으로 바꾼 실행 1건 | 위와 모두 동일 → 아무도 이 필드를 읽지 않는다 |
| 보정 없는 ag 평가 입력 9개 | 수정 전후 명단이 바이트 단위로 같음 |
| 보정 입력 9개(aj=ak 조건 ①, ak 조건 ②·③ × 3물량) | 옛 방식으로 저장 지문 재현, 새 방식은 `gate_in_s`만 바뀜(78,000건) |
| 회귀 시험 | 92건 통과(새 시험 8건 + 입력 생성·정보·예약·작업 완료 계약 시험) |

**해석**: 엔진은 처음부터 `arrival_s`만 읽었다. 그래서 aj·ak의 정책 비교 결과는 그대로 유효하다.
명단 지문과 입력 지문은 보정 입력에서만 달라진다. 앞으로 이 필드를 읽는 도구도 실제 진입 시각을 받는다.

## 한계

- 정적 검색은 문자열 `gate_in_s` 기준이다. 동적 검사(엉뚱한 값 주입)는 CPU 하루 평가 경로 한 가지로 했다.
- 월 단위·GPU 경로는 명단의 `arrival_s`를 직접 읽는다. 보정 옵션 자체의 월/배열 연결은 YR-332-ai 범위다.
