# 6단계 실험 1 — 같은 작업 결과로 존재 확인 계산 단축

2026-11-05. 실행 코드 `dac998c1`, 원자료와 설정은 [campaign](stage1-existence/campaign.json),
원자료 해시·반복 동일성 재검사는 [summary](stage1-existence/summary.json).

## 진행사항

21블록·42크레인, 하루 관측 24시간과 추가 처리 2시간, CPU 한 스레드로 순차 실행했다.
물량별 고정 입력 하나를 두 번 반복하여 변경 전후 총 6쌍·12회를 비교했다.
후보·계획·선택·사건·완료·비용이 모두 같았고, 반복 실행의 결과도 같았다.

| 하루 예약 트럭 | 기존 전체 계산 | 변경 전체 계산 | 첫 비교 단축 | 반복 비교 단축 |
|---|---:|---:|---:|---:|
| 3,500건 | 51.12초 | 38.88초 | 23.94% | 24.32% |
| 7,500건 | 78.47초 | 62.41초 | 20.47% | 21.92% |
| 15,000건 | 289.41초 | 211.47초 | 26.93% | 27.90% |

실행 가능한 작업이 있는지만 확인하는 곳에서는 첫 안전한 작업을 찾으면 탐색을 마친다.
정책이 선택할 때는 기존과 같은 전체 후보를 만든다. 후보를 줄여 얻은 속도가 아니다.

## 해석

세 물량 모두 두 번씩 결과 보존과 시간 감소를 확인하여 후속 진단에 이 계산 경로를 사용한다.
`decision_probe_shortcircuit=True`로 명시하며, 외부 자리 선택 함수가 있으면 전체 확인을 유지한다.
앞선 [자리 계산 재사용](stage1-slots.md)은 이득을 확인하지 못해 함께 켜지 않는다.

전체 계산시간의 감소가 모든 개별 결정 지연의 감소를 뜻하지는 않는다.
첫 비교의 느린 5% 경계는 8.83→8.60 / 11.84→12.01 / 27.07→28.11밀리초였다.
최대 결정 지연은 107.13→37.70 / 126.66→137.86 / 251.20→254.91밀리초였다.
즉 높은 물량에서 개별 결정 시간까지 개선됐다고 주장할 수 없다.
첫 비교 최대 사용 메모리는 양쪽 모두 약 267~353MiB로 뚜렷한 감소가 없다.
세 입력의 계산 진단이며 실제 항만의 응답시간이나 학습 성능을 보증하지 않는다.
전체 시간에는 환경 준비와 결과 기록이 포함되며 프로세스 기동과 모델 준비는 제외한다.

정확성: 관측한 후보·작업 결과 보존 통과. 계산 효과: 이 세 입력의 반복에서 확인.
현실 타당성: 예약 오차·본선 용량 보정이 남아 있어 현장 성능 확증은 미통과다.
관련 구현의 160개 고유 검증 항목은 [검증 기록](prepared-verification.json)에 보존했다.
