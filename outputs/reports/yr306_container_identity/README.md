# YR-306 — 오더 번호 연결 수정과 재학습 보류

v3의 오더 양식은 그대로였다. 문제는 `con_no`(컨테이너 번호)의 값과 실제 작업 대상이
연결되지 않았다는 것이다. 번호 연결을 수정했지만 **기존 30일 입력으로 재학습할 수는 없다**.
학습 전에 입력을 검사하는 장치를 추가했고, 운영 실행 경로에서도 갱신 0회로 거부됨을 확인했다.

## 진행사항

### 같은 명단으로 수정 전후 비교

- 사전등록: `83d7670`, [작업 명세](../../../.claude/docs/dashboard-task-specs/YR-306-container-identity-audit.md).
- 수정 전 코드 `8ab7d9d`, 수정 코드 `412a324`. 둘 다 변경 없는 별도 코드 폴더에서 점검했다.
- 시드(같은 입력을 다시 만드는 난수 번호) `9900306`, 30일, 트럭 177,500건.
- 두 점검은 같은 감사 스크립트·날짜별 부하를 사용했다. 시뮬레이션·학습은 실행하지 않았다.
- [수정 전 원자료](baseline-frozen.json), [수정 후 원자료](after-frozen.json).

| 검사 | 수정 전 | 수정 후 |
|---|---:|---:|
| 오더의 필드 수 | 6 | 6 |
| 오더 번호와 실제 컨테이너 번호 불일치 | 177,500건 | 0건 |
| 초기 컨테이너 13,608개의 서로 다른 번호 수 | 648개 | 13,608개 |
| 같은 대상의 반복 출고 배정 | 88,679건 | 88,679건 |
| 선적 목록 없는 본선 작업 묶음 | 108개 | 108개 |

즉 양식은 유지하면서 번호 연결은 바로잡았다. 하지만 이미 출고한 상자를 다시 출고하는
날짜별 명단과 대상 없이 물량만 정한 선적 계획까지 고친 것은 아니다.

### 구현한 변경

1. 반출 오더의 번호를 실제 반출 대상에, 반입 오더의 번호를 엔진이 생성하는 번호에 연결했다.
2. 초기 컨테이너의 블록별 중복 번호를 구분했다. 블록을 옮겨도 번호는 바뀌지 않는다.
3. 원래 대상이 없다고 다른 상자를 고르던 대체 동작을 금지했다.
4. 초기 재고·반입·출고·본선 사이의 번호, 중복 출고, 선적 목록을 학습 전에 검사한다.
5. 본선 선적 목록이 있으면 그 대상만 투입한다. 대상 부재·중복은 작업 등록 전에 거부한다.
6. 운영 실행기는 검사 결과와 실패 상태를 저장한다. 실패 후 정책을 계속 학습하지 않는다.

v3·v4 코드와 v5의 고정 물리 엔진 사본, 정책망·비용식·학습 설정은 바꾸지 않았다.
본선 전체 계획을 트럭용 `Order` 하나로 표현하지도 않았다. 본선은 기존 별도 명세를 검사한다.

### 검증 범위

- 직접 관련 검사 84건 통과. 번호 연결·학습 갱신·보상·실패 저장·실제 짧은 연속 실행을 포함한다.
- 연결 검사와 물리 사본 비교 96건 통과. 앞의 84건과 일부 겹치므로 합산하지 않는다.
- 전체 v5 249건과 별도 추가 실패 검사 9건, 서로 다른 검사 **258건 모두 통과**했다.
  실패·건너뛰기 0건. 전체 검사는 31분 44초였으며 옛 하루 단위 반복 실행도 포함한다.
  [검증 원자료](verification.json), [전체 검사](full-tests.xml), [추가 검사](fixed-admission-tests.xml).
- 작은 연속 실행 시험은 **별도 고정 명단**을 공급한다. 첫날 본선 작업을 유지하고 이후 날에는
  새 본선을 넣지 않는다. 기본 명단의 검사를 우회하지 않으며, 원래 30일 입력의 수정 증거가 아니다.
- 작은 3일 시험은 학습 갱신 `[0, 24, 0]`을 확인한다. 준비일·마지막날은 학습하지 않는다는 뜻이다.
- CPU 1개에 제한했다. 다른 v4 학습이 있어 실행 시간을 속도 개선 근거로 쓰지 않는다.
- JSON·XML의 줄바꿈 변환을 이 폴더에서 막아 파일 검증값을 Windows·WSL 사이에서도 보존한다.

### 실제 30일 학습 진입점 확인

수정 코드에 고정한 새 폴더 `outputs/v5/yr306-identity-preflight-30d`에서 운영 명령을 실행했다.
사전 검사에서 다음 결함을 저장하고 **세계를 만들기 전** 거부했다.

- 반복 출고 88,679건, 초기 재고·반입에 출처가 없는 반출 8건.
- 선적 대상 없는 본선 작업 묶음 108개, 그 묶음에 속한 작업 44,670건.
- 학습 갱신 0회, 완료일 0일, 투입 트럭 0건. 최종 학습 모델은 없다.

이는 10일째 오류가 다시 발생한 것이 아니다. 부적절한 입력으로 학습을 시작하지 못하게 한
검사가 의도대로 작동한 결과다. 실패 상태만 보고 새 실행 버그로 해석하지 않는다.

## 해석과 한계

원래 재실행은 10일째 10:37에 Y16 블록의 반출 대상 부족으로 중단됐다. 관찰 장치를 붙인
재현에서도 학습 갱신 202회와 일별 모델 9개가 같았다. 당시 상자 29개는 모두 미완료 반출에
배정돼 있었고, 완료된 작업이 예약을 놓지 않는 문제는 관찰되지 않았다.
[보존한 직접 원인 진단](original-failure-diagnosis.json).

새 감사는 **고정된 화물을 처리한다는 전제와 원래 입력이 맞지 않음**을 확인했다.
이 사실만으로 특정 정책 선택이 실패의 유일한 원인이라고 단정하거나,
PPO의 성능이 나쁘다고 결론 내릴 수는 없다.

번호 검사는 물리 실행 가능성의 필요조건일 뿐이다. 아직 도착·적치되지 않은 고정 화물의
대기 처리, 반입 블록을 바꾼 뒤 그 화물의 후속 출고·선적이 실제 위치를 따라가는 연결은
30일 규모에서 구현·검증되지 않았다. 비용·현실성·규칙 대비 우위는 통과로 바꾸지 않는다.

## 예정사항 — 같은 YR-306 작업 안에서

입고→보관→출고·선적이 같은 컨테이너로 이어지는 30일 입력을 구성하는 것이 남았다.
기존 연결 자료가 있으면 이를 검증하고, 없으면 합성 생성기의 운송 연결 규칙을 먼저 정해야 한다.
이 작업은 상자 수만 맞추는 것이 아니라 **어떤 상자가 언제 들어와 어떤 오더로 나가는지**를
고정하기 위한 것이다. 실제 준비 상태·재배치 후 위치까지 짧은 실행에서 확인한 뒤 재학습한다.

현재 YR-306은 미완료로 유지한다. [최종 검증 원자료](verification.json)와
[진행 판정](gate-after-identity.json)에 완료 범위와 남은 조건을 분리해 기록한다.
