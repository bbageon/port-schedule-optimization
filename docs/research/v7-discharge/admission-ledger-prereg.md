2026-11-08. 사용자는 t·m·w 세 감사를 모두 진행하고 개별 보고하라고 지시했고 재개를 요청했다.

## 실행 범위

- 기존 평가 3일: 3,500/7,500/15,000건, 시드 9913900/9913910/9913920.
- 고전 규칙 7개×3일 = 21회, 최신 flow 모델 3개×3일 = 9회.
- 입력 상한 제거 linear 모델 3개×3일 = 9회. 합계 39회.
- 최초 누락 발견 입력 3,500건·9913320의 reference/optimized 2회를 별도로 재생한다.
  이 2회는 옛 후보 상한 12와 당시 설정을 그대로 유지한다.
- flow 초기값 9913501·15,000건을 1회 반복한다. 총 42회, 추가 성능 표본으로 세지 않는다.
- 모델 초기값 9913501/2/3, 마지막 저장 모델만 사용한다. 모든 후보를 쓰는 기존 평가 조건 유지.
- 각 실행은 기존 결과·후보·선택·사건·작업·기록·결과 해시 6종과 정확 대조한다.
- 본 실행 전 별도 시드 9914409·80건으로 계측만 점검한다. 최대 6프로세스, 각 CPU 1스레드.

## 기록과 불변식

1. 원본 안내자의 skips, 실제 admit 호출 성공/실패, 통지·실제 투입 예정 시각을 기록한다.
2. 투입 실패 순간 물리 빈 칸, 미도착 반입 예약, 양하 예정 예약, 다른 예약, 안전 여유를 분리한다.
3. 전체 입력 = 투입 + 사유별 미투입 + 검토시각 미도달을 맞춘다. 각 오더의 검토 횟수를 센다.
4. 공식 24시간 장부를 변경하지 않는다. 동일 장부의 사본에 실제 bridge 동기화 코드를 적용해
   26시간 기록을 만들고 엔진의 실제 사건 시각과 전건 대조한다. 엔진도 진행시키지 않는다.
5. 24/26시간에 미진입·블록 이동·줄서기·작업 중·출차 이동·출차 완료를 반입/반출별 구분한다.
   실제 완료 뒤 예정된 출차라도 관측창 밖이면 미출차다.
6. 양하·적하의 최종 상태와 남은 작업을 별도로 보존한다. 본선 완료를 관측하지 못한 한계를 유지한다.
7. 동일 입력에서도 정책별 투입 집합이 같은지 ID로 대조한다. 공통 투입 집합의 체류도 계산하되,
   정책이 만든 사후 집합이므로 이를 공정한 인과 성능 비교로 부르지 않는다.
