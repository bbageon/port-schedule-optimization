# 가변 오더 수에 공유 신경망을 적용하는 방법

2026-11-05 · YR-332-h 진단. 실제 수치는 `outputs/reports/yr332_discharge_latency/latency.json`.

## 오더별 적용과 개별 호출의 차이

오더마다 점수를 낸다는 것은 오더마다 신경망 객체를 만들거나 별도 요청을 보내야 한다는
뜻이 아니다. 같은 가중치의 신경망에 N개 행을 한 번에 넣으면 N개 점수를 얻는다.
결정 시점에 이미 알려진 목록을 바로 묶는다. 추가 오더가 모일 때까지 기다리지 않는다.

현재 정책은 각 후보에서 Python→tensor→신경망 호출을 반복한다. 후보의 공통 정보인
대기열 수도 매번 전체 job 목록을 훑어 센다. N개 후보·M개 기록이면 이 부분은 N×M 탐색이다.
전체 오더를 보기로 할 때 신경망 연산만 빨라져서는 충분하지 않다.

## 적용 제안

1. 결정 시점의 현재 상태를 한 번 읽고 일관된 스냅샷을 만든다.
2. 예정/확정 목록의 공통 요약과 대기 수를 한 번 계산한다. 원시 오더는 제거하지 않는다.
3. 실행 가능한 후보의 입력 행을 만들고 같은 망으로 일괄 평가한다.
4. 메모리가 부족하면 후보를 작은 묶음으로 나눠 **전부** 평가한다. top-12 잘라내기가 아니다.
5. 점수 순서에 따라 기존 물리적 실행 가능성과 중복 배정을 검사한다.
6. 상태가 바뀌면 해당 결정의 계산을 갱신한다. 오래된 캐시로 행동을 실행하지 않는다.

예정/확정 집합을 읽는 새 인코더를 구현할 때는 목록의 길이와 총 작업량을 보존하고,
후보마다 전체 목록을 다시 읽지 않도록 목록 요약과 후보 점수 계산을 분리한다.
이는 공유 정책의 계산 재사용이며 별도의 작업 우선순위 정책을 추가하는 설계가 아니다.

## 이번 시제품이 측정한 것

- 현재 9→64→64→1 신경망, CPU 1스레드, 고정 난수 seed.
- 미리 만든 입력의 개별 호출·전체 일괄·1,024행씩 분할 일괄.
- 실제 엔진 스냅샷의 후보 생성→특징→점수→실행 가능성 검사까지의 선택 경로.
- 일괄 시제품은 공통 대기 수를 한 번 세고 기존 특징 함수를 그대로 호출한다.
- 후보 누락 없이 특징 동일성·점수 수치 오차·선택 일치를 검사한다.

일괄 시제품은 연구용 스크립트 안에만 있다. 운영 정책은 아직 교체하지 않았다.
현재 특징이 같아도 모든 향후 학습 모델에서 순위가 같다는 보장은 없으므로 실제 적용 전
다양한 모델·거의 동점인 후보·강제 선택·안전 우선규칙을 포함해 정합성을 검사해야 한다.

## 해석 경계

실시간 적합성은 하루 오더 총량보다 **한 결정에서 처리하는 후보 수, 결정 빈도, 허용 응답시간**에
달려 있다. 원자료 중앙값뿐 아니라 느린 쪽 꼬리도 함께 확인한다.
10회 측정의 95백분위는 사실상 표본 최댓값에 가까우며 현장 지연의 통계적 보증이 아니다.

새 집합 인코더, 42크레인 동시 판단, TOS 통신, 데이터베이스, 실제 운영 부하는 측정하지 않았다.
신경망만의 짧은 시간으로 전체 현장 배포 가능성을 판정하지 않는다. GPU 필수 여부도 미단정.

계측 방법 참고: [PyTorch Benchmark 공식 문서](https://docs.pytorch.org/tutorials/recipes/recipes/benchmark).
준비 실행, 명시적 스레드 수, 반복 측정을 적용했다. 최초 값은 각 측정 구간 첫 호출이며
새 프로세스 시작부터 모델 로딩까지의 전체 시작 지연은 아니다.
