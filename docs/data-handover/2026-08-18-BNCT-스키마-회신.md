# BNCT 트럭 이벤트 인계 — 스키마 대조 회신

- **작성** 2026-08-18 / **대상** BNCT 인터페이스 명세(BCITT `com.bnctkorea.bcitt.api`)
- **작성 범위**: 우리 시뮬레이터 코드와 대조 가능한 부분만 검증했다.
  **BNCT 레포는 열람하지 않았으므로 그쪽 필드 존재·의미는 확인하지 않았다.**

## 0. 결론 먼저

명세는 대체로 정확하고, **1단계(실측 보정)는 확정, 2단계(실운영 대비 비교)도
가능**하다는 판단에 동의한다. 다만 세 가지를 정정·추가한다.

1. **매핑 오류 2건** — 우리 코드에서 확인했다(§1).
2. **결손이 "하나"가 아니라 셋** — 본선 스케줄을 협의 대상으로 승격 권고(§2).
3. **추가 요청 5건 + 확인 2건** (§3·§4).

## 1. 매핑 정정 2건

### ① `travel_base_s` ≠ `blockAvgTT`

우리 코드다.

```python
"travel_base_s": layout.gate_to_block_s(bid)      # = 거리 ÷ 속도
"travel_s":      _clamp_travel(그 값, 오차)        # 오차 붙은 실현
```

`travel_base_s` 는 **게이트→블록 주행의 기준시간**이다. 블록 체류가 아니다.
체류는 블록에 **도착한 뒤**의 이야기라 물리적으로 다른 구간이다.

| | |
|---|---|
| 명세의 매핑 | `travel_base_s → blockAvgTT` |
| **정정** | `travel_base_s` = `gateInTime→blockInTime` 의 **블록별 집계값** |

즉 `travel_s`(개별 실현)와 같은 소스에서 나오며, 그 통계가 기준값이 된다.

**그러면 `blockAvgTT` 는 무엇인가.** 이름상 "블록 평균 체류"라면 오히려
`blockInTime→jobDoneTime`(= 재배치가 줄이려는 값)일 가능성이 크다.
**정확한 정의 확인을 요청한다** — 어느 쪽이냐에 따라 쓰임이 완전히 달라진다.

### ② `fallback_reason` ≠ `conSwapReason`

우리 코드다.

```python
"fallback_reason": "no_free_target" if (want_out and not out) else None
```

이것은 재배정 사유가 **아니다**. **합성 생성기가 "반출 오더를 만들려는데 그
블록에 꺼낼 컨테이너가 없어서 반입으로 바꾼" 흔적**이다. 순수한 시나리오
생성 인공물이며, `requested_flow` 와 짝을 이룬다.

**정정**: `fallback_reason` 과 `requested_flow` 는 실데이터로 가면 **둘 다
사라진다** — 실제 반입/반출은 오더가 정하지 생성기가 정하지 않는다.
`conSwapReason`(컨테이너 위치 변경 사유)은 **대응이 아니라 새 필드**로
따로 받아야 한다. 명세의 "0%는 합성 산물"이라는 진단 자체는 맞다.

## 2. 결손 재평가 — 셋이다

명세는 "남는 한계는 작업 시작 시각 하나"라 했으나, 우리 비용 구조에서 보면
셋이다.

| 결손 | 영향 | 근거 |
|---|---|---|
| 작업 시작 시각 | **낮음** | 대기·작업 분리만 불가. 우리 비용은 `블록도착→완료` 로 계산하므로 **주지표에는 불필요** |
| **크레인 개별 배정** | 없음 (단 영구) | 재배치는 블록 단위 결정이라 현 연구엔 무영향. 다만 **크레인 배차 층을 실측으로 검증할 방법이 영원히 없다** |
| **본선 접안·하역 스케줄** | **중간 — 승격 권고** | 아래 |

### 본선 스케줄이 왜 중요한가

우리 총비용 분해다(기준선 실측).

```
트럭 선형 대기   1,869.0   81.8%
트럭 벌금          245.4   10.7%
본선 지연          171.7    7.5%   ← 비용 항목
```

**7.5%만이 문제가 아니다.** 본선 작업은 **같은 야드크레인을 쓴다.** 즉 본선
스케줄은 비용 항목이자 **크레인 경쟁의 원천**이다.

없으면 2단계에서 과거 하루를 재구성할 때 **크레인이 놀고 있는 것처럼 보인다.**
트럭만으로 재구성하면 "재배치 이득"이 실제보다 크게 나올 수 있다.

명세는 이를 "범위 밖"으로 두었으나, TOS 안에 존재하는 것은 확실하므로
**협의 대상으로 올려주기를 요청한다.**

## 3. 추가 요청 (우선순위)

| # | 요청 | 왜 |
|---|---|---|
| **1** | **본선 접안·하역 스케줄** (ETB/ETD, 본선별 작업량·마감) | §2 — 크레인 경쟁 재구성 |
| **2** | **`VBS_RES_AVL` 실제 값** (`RES_TIME`·`YARD_CAPA`·`RES_AVL_CNT`) | 우리가 크레인 처리량으로 **유도하려던 시간대 용량의 정본**. 실제 제도값이 있으면 유도를 버린다 |
| **3** | **`blockAvgTT` 정확한 정의** | §1-① — 게이트→블록인지 블록→완료인지 |
| **4** | **`REMAIN_TIME` 이력 보존 여부** | 스냅샷만 남고 시계열이 없으면 "도착 전 정보" 재구성 불가 |
| **5** | **`expWaitingMin` 산출식** | 우리 견적식과 대조하려면 계산 방법이 필요 |

### 2번과 5번의 값어치를 특히 강조한다

- **`VBS_RES_AVL`** — 우리는 시간대별 슬롯 용량을 크레인 처리량으로 **유도**하는
  작업을 준비 중이었다. 실제 제도적 상한이 있다면 그 작업을 **취소하고 정본을
  쓴다.** 현재 그 작업은 이 값 확인 전까지 **보류**로 돌렸다.
- **`expWaitingMin`·`blcWaitingCarCount`** — 우리 견적식(대기열 길이 기반 근사)의
  **정답지**가 된다. 현재 우리 견적 모델에 결함 2건이 남아 있는데, 터미널이
  이미 계산한 값을 쓰면 그 경로를 **통째로 우회**할 수 있다.

## 4. 확인만 하면 되는 것

| | 왜 |
|---|---|
| **`conLocFilter` 정규화 후 블록 목록** | 개수 **21** 은 확인됐다(2026-08-18). 남은 것은 **목록과 대응 관계**다 — 실제 블록 식별자가 무엇이고, 게이트로부터의 상대 거리·배치가 어떻게 되는지. 개수가 같아도 **거리 배치가 다르면 주행시간 모형이 어긋난다** |
| **`inOutReserveTime` 이 구간인가 한 점인가** | 우리는 예약을 **구간**(창 시작·끝)으로 모델링해 뒀다. 실제가 한 점이면 그 구조가 남는다 |

## 5. 인계 경로에 대한 의견

명세의 A·B·C 구분에 동의한다. 우선순위는 이렇게 본다.

| 경로 | 의견 |
|---|---|
| **A · 인터페이스 규격** | **이미 받았다.** 이 회신으로 스키마 수정에 착수 가능 |
| **B · 운영 로그 (60일)** | 유용하나 **예약 시각이 없다.** 준수 오차가 이 연구의 핵심 변수라 B 만으로는 1단계가 절반만 된다 |
| **C · TOS 직접 추출** | **가장 필요하다.** `IF_TMNL_EVENT_INFO`(4시각) + `VBS_RES_MST`(예약) 조합이 최소 요건이다. 여기에 위 §3 의 1·2번을 더하면 2단계까지 간다 |

### 익명화

차량번호·기사 연락처·화주명은 **필요 없다.** 다만 차량은 **솔트 해시로
동일성만** 유지해 주기를 요청한다 — 같은 트럭의 반복 방문 패턴이 재배치 효과
분석에 쓰인다. 컨테이너 번호도 동일하다(동일성만 필요, 실번호 불필요).
