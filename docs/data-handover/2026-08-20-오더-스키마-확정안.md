# 오더 데이터 스키마 확정안 v2 (2026-08-20 · 사용자 결정 반영)

> **왜 지금**: 강화학습 학습 단계인데 오더 데이터가 두 벌 이름으로 어중간하다.
> [[YR-187]] A단계가 새 필드를 **더했지만 아무도 쓰지 않는다** — 구 키가 106곳에서
> 실제 동작을 굴린다.

## 0. 사용자 결정 (2026-08-20)

1. `flow` → **`inOut`** — BNCT 이름으로
2. **`inOutReserveTime` 추가** — 최초 코피노 수신 시 기사가 "언제 게이트 진입
   하겠다"고 신고한 **반출입 예정 시각**
3. `gateInTime` 은 **입력**, `blockInTime`·`jobDoneTime`·`gateOutTime` 은
   **출력** — 그대로 두되 **작업이 완료될 때마다 갱신**
4. **`prevConLoc` 추가** — 블록이 바뀌면 기존 `conLoc` 을 여기 보관

## 1. ★시각이 셋이다 — 지금은 하나로 뭉쳐 있다

이것이 이번 확정의 핵심이다.

| # | 시각 | 뜻 | 정책 |
|---|---|---|---|
| ① | **`copinoNoticeTime`** | 코피노가 접수된 시각 — **터미널이 알게 된 순간** | ✅ 가시 |
| ② | **`inOutReserveTime`** | 기사가 **"이때 들어가겠다"고 신고한** 예정 시각 | ✅ 가시 |
| ③ | **`gateInTime`** | 실제로 게이트에 들어온 시각 | ❌ 그 전엔 비가시 |

**지금 우리 무대는 셋이 전부 같은 값**(`arrival_s`)이다. 그래서 두 개념이 사라진다.

```
리드타임   = ③ − ①    "얼마나 미리 알았나"        DGT 실측 중앙 1.27h
예약 준수  = ③ − ②    "약속 시각을 지켰나"        ★우리에게 없음
```

**★앞선 분석 정정**: 2026-08-19 DGT 대조에서 `copino_notice_s → gate_in_s` 를
"예약 준수 오차"라고 불렀는데 **틀렸다.** 그건 **리드타임**이고, 예약 준수는
②와 ③의 차이다. DGT 표본에 `inOutReserveTime` 이 99% 비어 있어 **예약 준수는
아직 실측되지 않았다.**

## 2. 오더 — 생성 시 확정되는 것 (12개)

| 필드 | 타입 | 뜻 | 정책 |
|---|---|---|---|
| `docKey` | str | 방문 고유키 (블록명 접두 제거) | ✅ |
| `inOut` | `GATE_IN`/`GATE_OUT` | 반입·반출 | ✅ |
| `copinoNoticeTime` | float | ① 통지 시각 | ✅ |
| `inOutReserveTime` | float | ② **예정 시각** | ✅ |
| `gateInTime` | float | ③ 실현 진입 | ❌ 미래 |
| `conLoc` | str | 최초 배정 블록 | ✅ |
| `conNo` | str\|None | 대상 컨테이너 (반출) | ✅ |
| `sizeClass` | (str,str,str\|None) | 규격 | ✅ |
| `travelBaseSec` | float | 게이트→블록 **기준** 주행 (거리÷속도) | ✅ 지도 |
| `travelSec` | float | 그 트럭의 **실현** 진입 주행 | ❌ 미래 |
| `exitTravelSec` | float | 블록→게이트 출문 주행 | ❌ 미래 |
| `schema` | str | `"bnct-a2"` | — |

**왜 주행은 소요시간이고 시각이 아닌가**: 재배치하면 목적지가 바뀌어
`blockInTime` 이 달라진다. **소요시간은 트럭 고유값**이라 블록이 바뀌어도 유지된다.
그래서 오더에는 소요를 넣고 시각은 시뮬레이터가 계산한다.

## 3. 진행하며 갱신되는 것 (초기 `None`)

| 필드 | 언제 채워지나 | 장부 대응 |
|---|---|---|
| `prevConLoc` | **판매 확정 시** — 기존 `conLoc` 을 보관 | — |
| `moveLoc` | 〃 — 실제 작업 블록 | — |
| `conSwapReason` | 〃 — 왜 바꿨나 | — |
| `blockInTime` | 블록 도착 | `TimeLedger.block_arrival()` |
| `serviceStartTime` | 크레인이 잡음 (DGT 엔 없음) | `.service_start()` |
| `jobDoneTime` | 작업 완료 | `.job_done()` |
| `gateOutTime` | 출문 (= jobDone + 출문주행) | `.job_done()` 이 함께 확정 |

**장부는 이미 단계마다 갱신하고 있다** — `TimeLedger` 에 `block_arrival()` ·
`service_start()` · `job_done()` 호출이 있다. **오더 레코드에 그것을 이어주면
DGT 로그 한 줄과 필드 대 필드로 맞는다.**

## 5. 이름 표기 — BNCT camelCase 그대로

변환 계층을 없앤다. 실데이터가 오면 **한 글자도 안 바꾸고** 꽂힌다.
(코드 스타일 일관성보다 **데이터 계약 일치**를 택한다.)

## 6. ★두 갈래 결정 — 값까지 벌릴 것인가

지금 ①②③이 전부 같은 값이다.

| | 무엇 | 대가 |
|---|---|---|
| **확정 A — 구조만** | 필드를 셋으로 나누되 **값은 같게** | [[YR-170]] 이후 판정과 **비교 유지** |
| **확정 B — 값까지** | ①②③을 실제 분포로 벌림 | **비교 끊김** — 규칙 기준선부터 재측정 |

**B 가 연구적으로 맞다.** 지금은 트럭이 정보 측면에서 전부 같아 **"어느 트럭을
언제 다룰까"라는 결정이 성립하지 않는다** — RL 이 규칙을 이길 여지를 무대가
안 준다. 다만 [[YR-179]]·[[YR-180]]·[[YR-189]]·[[YR-195]]·[[YR-199]]·[[YR-200]]
수치를 더는 인용할 수 없다.

**권고: A 를 먼저 커밋하고 B 를 별도로.** 한 커밋에 섞으면 회귀가 났을 때
개명 버그인지 값 변화인지 안 갈린다.

## 8. 하지 않는 것

  `exitTravelSec` 은 오더에 있지만 **정책 특징에 넣지 않는다**.
