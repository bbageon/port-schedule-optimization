## 2. 반입 배정 변경 뒤 특정 블록의 공급이 부족해짐

컨테이너 개수 장부는 다음 식을 사용한다.

`모든 요청을 끝냈을 때 남을 개수 = 초기 재고 + 반입 트럭 + 본선 양하 − 반출 트럭 − 본선 적하`

값이 음수이면 해당 배정과 공급 명단 안에서는 모든 반출·적하를 완료할 수 없다.
이 계산은 처리 속도와 무관한 수량의 하한이다. 값이 양수여도 필요한 시각에 재고가 있는지, 장비가 제때 처리하는지는 별도 문제다.

| 블록 | 원래 배정의 종료 수지 | 반입 물량 순유출 | 최종 배정의 종료 수지 | 실제 관련 잔여 |
|---|---:|---:|---:|---|
| Y05 | +229개 | 410개 | −181개 | 반출 트럭 181대 |
| Y08 | +112개 | 137개 | −25개 | 본선 적하 25건 |

Y05의 최종 배정은 `648 + 1,022 + 1,474 − 1,857 − 1,468 = −181`이다.
실제 완료 흐름을 합산한 이 블록의 기말 재고는 0개다. Y08도 기말 재고가 0개이며 적하 25건이 남았다.
두 블록의 부족분 206개는 실행 종료 시 대상 컨테이너를 지정하지 못한 작업 206건과 맞는다.
전체 터미널 기말 재고 9,826개도 완료 작업의 유입·유출 합계와 엔진 기록이 일치했다.

원래 배정의 수지는 실행한 정책의 성능 결과가 아니다. 원래 요청 명단에 대한 수량 계산이다.
본선 잔여 1,817건 전부를 재고 부족으로 설명하지 않는다. 위 계산이 직접 설명하는 것은 해당 두 블록의 206건이다.

거절 기능 제거에서도 최종 배정의 수지가 Y05 −238개·Y07 −19개로 나타났고 대상 미지정 257건과 맞았다.
기준 정책은 원래 배정과 최종 배정 모두 블록별 종료 수지 부족이 없으며 대상 미지정도 0건이다.
세 정책의 완료 흐름으로 계산한 전체 기말 재고 9,471/9,826/9,606개는 각각 엔진 기록과 일치했다.
이 수량 검산만으로 본선의 나머지 잔여가 생긴 서비스·시각별 원인까지 확정하지 않는다.

## 3. 독립 20개월의 원래 입력도 같은 기준으로 확인

이미 고정한 20개월·4,038,000건을 전부 읽었다. 기존 압축 파일 지문을 확인했고 시드·요청·합성곡선을 변경하지 않았다.
정책을 실행하거나 성능을 보고 입력을 골라내는 작업은 하지 않았다.

- 20개월 중 **9개월**은 원래 블록 배정에서도 월말 공급보다 반출·적하 요청이 많은 블록이 있었다.
- 이 부족분은 전체 20개월에서 **1,362개**, 한 달 최대 **552개**였다.
- 날짜별 계획을 누적하면 19개월에서 적어도 한 번 음수 수지가 나타났다. 다음 날 공급으로 회복될 수 있으므로 이것을 월말 부족과 같은 실패로 세지 않는다.
- 이는 원래 입력의 블록별 수급 문제와 정책의 반입 배정 변경 효과를 구분해야 함을 뜻한다. 합성곡선 보존만으로 운영 가능성을 입증하지 못한다.

시드를 제외하거나 물량을 줄여 통과시키지 않는다. 이미 고정한 입력은 원본으로 보존한다.

## 4. 학습·평가 실행 경로 보완

기존 학습·평가 명령은 보정 환경을 선택할 인자가 없어 `run_month`의 기존 모드를 그대로 사용했다.
`--admission-mode PRESERVE`를 학습·평가 양쪽에 연결하고 초기/최종 가중치 메타데이터·실행 결과·평가 재사용 계약에 기록하도록 수정했다.
모드를 바꾸면 기존 평가 결과를 자동 재사용하지 않는다. 기본값은 원래 실행의 재현을 위한 `LEGACY`다.

관련 검사 29개와 재고 계산 사례 3개가 통과했다. 최초 검사는 실행 환경의 `PYTHONPATH` 누락으로 수집에 실패했고 경로를 설정한 재실행에서 통과했다.
이 검사는 연결과 기록 확인이며 실제 추가 학습을 수행했다는 뜻이 아니다.
