# 수직형 환경 구현과 검증

작성: 2026-09-19. 작업: [YR-317-h — 기본 배치 검증](../../../../.claude/docs/dashboard-task-specs/YR-317-h-v3-review-basic-layouts.md).

## 1. 구현 범위

**수직형을 명시적으로 선택하여 연속 시뮬레이션을 실행할 수 있게 했다.**
블록의 긴 방향을 안벽과 직각으로 놓고, 외부 트럭은 육측 끝에서, 본선 연계 차량은 해측 끝에서 컨테이너를 인계한다.
선박 양하는 `안벽 크레인 → 야드 트랙터 → 해측 인계점 → 야드크레인 → 적재 위치`의 흐름이다.
해측 야드크레인이 선박에서 직접 컨테이너를 내리는 구조가 아니다.

기존 원본 환경 `v3/world`와 진행 중인 독립 평가의 고정 소스·입력·모델은 변경하지 않았다.
새 구현은 [layouts](../../../../src/yard_rl/v3/layouts/)에 두고 [월 실행기](../../../../src/yard_rl/v3/stage/month_run.py)의 `environment_spec`으로 선택한다.
현재 연결 범위는 재배정 없는 기준정책과 **Time-only(도착시간만 조정하는 정책)**의 고정 모델 평가다. 새 학습이나 공간 정책 평가는 지원 범위에 넣지 않았다.

## 2. 실제로 달라지는 동작

| 항목 | 이번 수직형 구현 | 의미 |
|---|---|---|
| 블록·저장량 | 21블록, 각 24구간×10열×6단 = 1,440칸 | 기존 입력과 저장 용량 유지 |
| 크레인 | 블록당 2대, 같은 레일에서 서로 통과 불가 | 안전 간격과 이동시간을 계산 |
| 역할 | 첫 크레인은 외부 트럭, 둘째는 본선 연계 작업 | 후보 생성과 실제 배정 모두 역할 검사 |
| 재고 접근 | 두 크레인 모두 전체 적재 위치에 접근 | 재고를 반으로 나눠 반출 불가능한 상자를 만들지 않음 |
| 인계 위치 | 길이 방향 구간 0과 25, 폭 방향 가운데 5.5열 | 크레인이 끝단과 적재 위치 사이를 실제 이동 |
| 주행 여유 | 양끝 인계점 바깥으로 안전 간격만큼 레일 연장 | 방해하는 크레인이 시간을 들여 물러남; 추가 저장 공간은 아님 |
| 차량 도로 | 육측·해측의 별도 직각 도로망 | 실제 연결 경로 거리÷속도로 시간 계산 |
| 양하 중간 작업 | 블록 전체에 진행 중 양하 최대 3건 | 안벽에서 출발해 야드 적재를 마칠 때까지 정원을 차지 |

마지막 행은 **예약 슬롯 정원이나 운송사 변경 제약이 아니다**. 내부 양하 흐름의 합성 정원이다.
여러 선박이 같은 블록을 사용할 때 이 정원을 공유하며, 작업이 끝나면 기다리던 다른 선박도 다시 진행한다.

## 3. 숫자의 근거와 한계

수평/수직과 측면/끝단 인계의 구분은 [Budiyanto 등, 2021](https://www.nature.com/articles/s41598-021-84958-4)을 참고한다.
육측·해측 크레인 역할의 대표 운영 형태는 [Kalmar의 ASC 설명](https://www.kalmarglobal.com/news--insights/articles/2021/kalmar-one-asc-application/)을 참고한다.
내부 운반차량을 거치는 흐름은 [DP World Brisbane 사례](https://www.kalmarglobal.co.uk/news--insights/articles/2014/dp-world-brisbane/)와 같은 구조다.
이는 구조 정의의 근거이며, 아래 숫자의 실측 근거가 아니다. 모든 수직 터미널이 같은 운영 방식을 쓴다는 주장도 아니다.

- 기존 블록 구간 길이·열 폭과 장비 성능은 유지한다.
- 구현용 합성 기본값: 블록 간격 13m, 끝단에서 주도로까지 26m, 게이트·안벽 접근 구간 각각 1,000m, 차량 속도 5m/s.
- 기본 프로파일의 크레인 안전 간격은 2구간이므로 주행 범위는 −2~27이다. 적재는 여전히 1~24구간이다.
- 인계점 간 거리는 162.5m다. 각 끝의 여유 구간과 도로를 명시했지만 크레인 몸체 크기·교차로 교통은 모형화하지 않았다.
- 이 값의 게이트→블록 경로시간은 205.2~381.2초다. 기존 시간 범위에 다시 잘라 맞추지 않는다.
- 내부 운반차량은 기존의 왕복 주기 근사를 사용한다. 경로 왕복시간 410.4~762.4초를 반영하지만, 도착과 빈 차량 복귀를 별도 사건으로 나누지는 않는다.

이 값들은 **구현 검사 사례의 설정**이다. 성능 비교용 두 구조의 최종 수치나 현장 보정 완료값이 아니다.
새 환경에서는 인계 위치·크레인 역할·도로·양하 정원이 함께 달라진다. 결과를 방향 하나의 인과효과로 해석할 수 없다.

## 4. 같은 합성 입력을 유지하는 방법

1. 기존 생성기로 요청 목록, 합성 도착곡선, 초기 재고, 본선 계획을 먼저 만든다.
2. 요청·공급 보정을 기존 방식으로 적용하고 원본 파일 지문을 확인한다.
3. 새 도로에 따라 게이트→블록 기준시간, 실제 주행시간, 출구 주행시간만 바꾼다.
4. 원래 추출한 주행시간의 편차는 유지한다. 출구시간의 원래 기준은 블록별 진입 경로가 아닌 고정 평균 300초이므로 이를 따로 처리한다.
5. 선박 예정 완료시간과 출항시간은 원래 프로파일 기준으로 고정한다. 새 구조에서 계산한 물리 하한과 마감 초과 여부를 별도로 저장한다.
6. 원본 입력과 파생된 실행 입력의 지문, 환경 좌표·경로·정원을 모두 결과에 기록한다.

따라서 원래 도착곡선과 하루 요청 수를 바꾸지 않으면서 구조에 따른 이동·서비스 차이를 확인할 수 있다.
물리 하한이 약속된 마감을 넘는 설정은 숨기지 않는다. 본 비교 전에 이런 불가능한 조건이 없는지 확인해야 한다.

## 5. 검증 기록

마지막 코드에서 새 구조·입력 연결·선박 마감 **55검사 통과**. 기존 환경 관련 **38검사 통과**(학습 분기 검사 1개 제외)로 총 93검사를 통과했다.
검사 파일은 [경로](../../../../tests/v3/test_layout_geometry.py), [크레인·인계](../../../../tests/v3/test_vertical_runtime.py), [입력·월 연결](../../../../tests/v3/test_vertical_environment.py), [본선 마감](../../../../tests/v3/test_vertical_deadlines.py)이다.
초기 연결 검사에서 발견한 설정 객체 생성 오류와 그 수정 전 실패 기록도 보존한다.
세부 실행 기록: [수직형 검증 폴더](../../../../outputs/reports/yr317_v3_vertical/).

같은 1일·21대에서 수정 전후의 전체 결과와 관측 289행이 정확히 일치했다. 새 빈 환경 명세 필드만 제외했다. [기존 경로 동일성 기록](../../../../outputs/reports/yr317_v3_vertical/legacy-equivalence.json).
추가 확인 예정: 고정 모델을 사용한 21블록·2일의 작은 연속 실행.
[실행기](../../../../scripts/v3/qualify_vertical_environment.py)는 같은 진단 입력으로 기준/시간 정책을 순차 실행하고, 학습 여부·요청·재고·본선 장부·일별 관측을 저장한다.
이 짧은 진단의 비용은 구현 점검 자료이며 논문 성능 결과나 독립 반복 표본으로 사용하지 않는다.

## 6. 리뷰 대응과 남은 비교

사용자의 시간 제약에 따라 이전 문서의 `2구조×20시드×4정책` 제안은 이번 실행 범위에서 제외한다.
후속 범위는 **같은 외생 시나리오 1개 × 두 구조 × 기준/시간 정책 = 4실행**이다. 기존 모델을 고정하면 새 구조로 옮겼을 때의 단일 사례 확인이다.

현재 기존 환경은 한 축의 공유형 합성 환경이다. 이것을 새 수직형과 바로 비교해 실제 수평·수직 검증이라고 부르지는 않는다.
같은 h 작업에서 수평 측면 인계·실제 경로를 맞추고, 특히 양하 정원 적용 단위와 이송시간 계산 방식을 맞춘 뒤 비교 계약을 고정해야 한다.
시드 하나의 날짜들을 독립 표본으로 세거나, 두 구조의 비용을 합쳐 한쪽 손해를 가리지 않는다.
수직형 구현 완료만으로 리뷰어 2의 일반화 우려가 해소되지는 않는다. 이후 비교도 합성 환경의 제한적인 구조 민감도 근거로 보고한다.
