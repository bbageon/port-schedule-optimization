# YR-133 판매·수용 실환경 설계와 YR-143 위치조정 제거 계약

> **후속 범위 정정(2026-08-05)**: 본 문서의 실제 TOS/ECS ACK 설계는 이력으로만 보존한다.
> 사용자가 실제 연동을 연구 범위에서 제외했으며, 현재 계약은 [후속 결정](2026-08-05-YR-133-TOS-연동-범위-제외-사용자결정.md)이 우선한다.

> 결정일: 2026-08-02
> 범위: 단일 블록 실행정책 뒤의 다중 블록 작업 재배정, PREPOSITION 존재가치 판정
> 현재 지위: 설계·판정계약 동결, 구현·성능 미확정

## 1. 결론

연구 순서는 다음으로 고정한다.

1. 한 블록 안에서 두 YC(야드크레인)의 실행순서 정책을 먼저 확정한다.
2. 자유 REPOSITION이 없는 편이 좋은지 YR-143으로 직접 비교한다.
3. 그 뒤에만 블록 간 작업 재배정을 붙인다.

재배정에서 `판매`는 원블록의 **이전 제안**, `구매`는 수신 블록의 **추가부담 견적**이다.
어느 블록도 혼자 작업 소유권을 바꾸지 않는다. TransferResolver만 KEEP/TRANSFER를 정하고,
실제 환경에서는 TOS/ECS 승인 뒤 원자적으로 확정한다.

## 2. 왜 내부 실행정책이 먼저인가

source의 `OutRelief`와 receiver의 `InBurden`은 각 블록이 작업을 얼마나 잘 처리하는지에
의존한다. 내부 정책을 바꾸는 중에 재배정까지 학습하면 비용 변화가 실행순서 때문인지
블록 이전 때문인지 분리할 수 없다. 따라서 YR-142·143으로 행동공간을 닫은 뒤 YR-133을 연다.

## 3. 실제 운영 권한 구조

```text
외부 TOS
  └─ job 생성·최초 block·allowed blocks 결정
       └─ 원소유 Block Policy
            ├─ 내부 PPO: 두 YC 공동 실행순서
            └─ TransferHead: 이전 제안·OutRelief
                  └─ TransferResolver
                       ├─ 수신 Block Policy에 InBurden 조회
                       ├─ KEEP 또는 A→B 선택
                       └─ TOS/ECS ACK 뒤 atomic commit/rollback
```

TOS는 연구가 대체하지 않는다. 다만 실제 TOS가 제공하는 후단 재배정 API를 연결하는 것은
가능하다. API가 없으면 정책은 shadow 추천까지만 하고 자동 이전은 주장하지 않는다.

`tos_assigned_block_id`는 감사 이력으로 남고 `execution_block_id`만 변경된다.

## 4. SELL/BUY 계약

### 원소유 블록

```text
NO_OFFER
OFFER_TRANSFER(job_id, OutRelief, uncertainty, state_version, expires_at)
```

발의는 실행도 소유권 변경도 아니다. commit 전까지 작업은 source queue에 남는다.

### 수신 블록

```text
NO_BID(reason)
QUOTE_IN_BURDEN(feasible, InBurden, uncertainty, state_version, expires_at)
```

수신 블록에는 독립 BUY action이 없다. 가상으로 작업을 더했을 때의 부담만 응답한다.

### 중앙 Resolver

```text
KEEP(source, job)
SELECT_TRANSFER(job, source → receiver)
```

Resolver는 PPO·QMIX가 아니다. 견적 비교, 물리 자격, 중복·소유권, 예약, rollback을 담당하는
결정론적 transaction 계층이다.

## 5. 어떤 작업을 언제 옮기는가

| flow | 결정 | 판매 창 |
|---|---|---|
| 반입 STORE | 1차 포함 | 실제 gate-in 뒤, route/block instruction lock 전 |
| 본선 양하 STORE | 2차 분리 | STS handover-ready 뒤, YT 목적지·배차 lock 전 |
| 지정 트럭 반출 | 제외 | 컨테이너가 이미 특정 블록에 존재 |
| 본선 적하 | 제외 | 적하 대상 위치가 이미 고정 |
| 재조작·기적재 컨테이너 | 제외 | 재배정이 아니라 실제 블록 간 운송 문제 |
| 미지정 공컨 반출 | 제외 | TOS 재고·선사 조건의 상위 문제 |

반입은 현재 계약의 gate→block 3~7분을 이용한다. gate-in 전 ETA는 견적 cache에 쓸 수
있지만 실제 소유권 확정은 도착이 확인된 뒤로 제한한다. 양하는 반입과 사건·YT 장부가
다르므로 첫 실험에 섞지 않는다.

## 6. 재배정 mask

다음이 모두 참일 때만 receiver를 조회한다.

- 작업이 아직 unplaced이고 block/slot/YC/YT hard lock 전이다.
- current owner와 assignment version이 일치하고 열린 transaction이 없다.
- 첫 PoC는 transfer count 1회 이하, epoch당 최대 한 작업이다.
- receiver가 TOS의 allowed block set 안에 있다.
- receiver에 최소 물리규격·높이·용량상 호환 slot과 YC 작업 가능성이 있다.
- ETA·owner·allowed block 등 필수정보가 결측이면 KEEP한다.

냉동·위험물·중량·선사·세관 규칙은 실제 자료가 있는 YR-095 단계에서 넣는다. 그전에는
규칙이 없는 실제 터미널 전체가 아니라 최소 물리 제약 PoC라는 범위만 주장한다.

## 7. 견적 계산

```text
OutRelief(A,j) = J_A(KEEP j) - J_A(REMOVE j)
InBurden(B,j)  = J_B(ADD j) - J_B(NO ADD)
TransferCost   = route(origin→B) - route(origin→A) + 모델링된 변경비용
NetGain        = OutRelief - InBurden - TransferCost
```

`J`는 YR-136 v2 비용계약을 쓴다. 트럭·본선 지연, 이동·재조작 같은 실제 계약 항목은 한 번만
계상하고 혼잡도 점수를 다시 보상에 더하지 않는다. 반입 origin은 gate, 양하 origin은 quay다.

초기에는 학습망이 아니라 같은 snapshot의 KEEP/TRANSFER 짝지은 계산으로 부호·순위를
검증한다. 계산 quote의 상금이 확인된 뒤에만 공유 QuoteNet을 별도 축으로 검토한다.

## 8. Block Policy가 보는 정보

- 블록: queue, 평균·최장 대기, YC 잔여부하·고장, 장치율, 호환 slot 여유,
  본선 flow/slack, 앞으로 들어올 공개 예약량.
- 작업: flow, 규격, 공개 ETA와 불확실성, deadline, lock까지 남은 시간,
  owner/version/transfer count.
- receiver 가상상태: 작업을 더했을 때 예상 block arrival, route cost, 예상 queue·YC burden.

미래 실제 도착과 미통지 고장·계획변경은 금지한다.

## 9. 갱신 시점

1차는 event-only로 고정한다.

- actual gate-in, handover-ready, 유의한 ETA·계획 갱신, equipment down/up,
  owner·capacity 변화 때 검토한다.
- 같은 시각에는 정상 물리 사건과 YC 결정을 먼저 처리한다. review가 크레인을 놀리지 않는다.
- timer는 견적기가 통과한 뒤 별도 단일축으로만 추가한다.

## 10. 원자 소유권 변경

```text
OFFERED → QUOTED → PREPARED → VALIDATED → ACK → COMMITTED
                         └─ stale/NACK/timeout/error → KEEP
```

1. source owner를 유지한 채 receiver slot·route/YT를 임시예약한다.
2. 모든 version과 quote TTL을 재검사한다.
3. TOS/ECS에 변경을 요청하고 ACK를 확인한다.
4. owner, 양쪽 queue, arrival event, route, 전역 A→O ledger를 한 transaction으로 바꾼다.
5. 실패하면 snapshot을 복원한다. orphan 또는 duplicate job은 허용하지 않는다.

## 11. 현재 코드와 차이

`MultiBlockTerminal`에는 shared clock, owner/version, capacity reservation,
prepare/validate/commit/rollback 기반이 있다. 그러나 현재 PPO는 단일 블록 실행만 하며
판매·수신 견적을 내지 않는다. 중앙 `review_fn`이 혼잡도 규칙으로 직접 옮길 뿐,
독립 TransferResolver·quote head·TOS ACK·allowed-block mask·양하 trigger는 미구현이다.

## 12. YR-143: REPOSITION이 없을 때 더 좋은가

C0는 `SERVE+PRE_REHANDLE+SAFETY_ESCAPE`, C1은 C0에 검증된 결속 PREPOSITION만 더한다.
자유 REPOSITION은 양쪽 모두 없다. 교착 escape는 정책 최적화가 아니라 공통 안전기능이다.

비용차는 `Δ=C0−C1`로 둔다. 단순히 유의하지 않다는 이유로 PREPOSITION을 제거하지 않는다.

- C0 우월: v2 단측 95% 상한 `<0`, 보호지표도 통과 → 제거.
- C0 비열등: 모든 공동지표 상한이 사전 허용손실 `δ` 미만이고 이동·계산도 감소 → 제거.
- C1 실질 우월: 필수지표 하한이 `δ` 초과 → 유지.
- 나머지 또는 검정력 부족 → 미확정.

완주 100%, backlog 0, 안전위반 0, 미해결 교착 0은 hard guard다. 파일럿으로 분산과
최소검출효과를 먼저 계산하고, 학습초기화와 평가시나리오를 독립표본처럼 과대계상하지 않는다.

## 13. 연구 근거

- [Dynamic Space and Time Partitioning](https://pubsonline.informs.org/doi/10.1287/trsc.1110.0383)은
  변화하는 블록 작업량과 차량 대기시간을 함께 보고 YC 작업영역·시점을 조정한다. 블록 부하를
  고정으로 보지 않는 근거다.
- [Integrated storage allocation and multiple YC scheduling](https://xuebao.sjtu.edu.cn/EN/10.16183/j.cnki.jsjtu.2017.11.013)은
  적재공간 배정과 YC 스케줄을 함께 보며 안전거리·부하균형·이동·유휴비용을 고려한다.
- [Integrated YT·YC scheduling and storage allocation](https://www.scientific.net/AMM.587-589.1797)은
  양하에서 블록 배정, YT, YC 일정이 서로 결합됨을 모델링한다. 양하 재배정을 YT lock 전에
  결정해야 한다는 근거다.
- [Predicted-arrival YC dispatching study](https://informs-sim.org/wsc09papers/224.pdf)는 gate 등에서
  얻은 도착예측으로 실제 차량 도착 전 YC 이동을 검토한다. PREPOSITION은 현실적 가능성이
  있지만 반드시 별도 존재가치 검증이 필요하다는 근거다.

## 14. 적용 범위와 되돌림

- YR-143에서 C0 우월·비열등이 확인되면 전략적 PREPOSITION을 제거하고 안전 escape만 남긴다.
- quote가 직접 반사실의 부호·순위를 못 맞히면 학습 quote로 넘어가지 않는다.
- TOS/ECS ACK가 없으면 자동 재배정은 중단하고 shadow 추천으로 되돌린다.
- 반입이 성공한 뒤에만 양하, timer, 다건 matching을 각각 한 축씩 추가한다.
