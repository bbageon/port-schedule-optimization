# v3 리뷰 대응 — 사용자 맥락과 재현성

> 후속 범위 수정: [현행 전략 §6](2026-09-14-v3-review-refined-strategy.md)을 우선한다.
> 새 예약 제약층·사람 승인 기능은 이번 구현 범위 밖이며 사용자 과업 평가도 필수 실험으로 고정하지 않는다.

2026-09-14 · [전략 본문](2026-09-14-v3-review-response-strategy.md) 상세.
연결: YR-317-e(처리시간·재현성), YR-317-f(사용자 맥락).
이 문서는 **제안**이다. 현재 v3에 사용자 승인 화면이나 운영 연동이 구현됐다고 서술하지 않는다.

## 1. 심사위원 3에게 답할 핵심

대상 사용자를 “항만 관계자”로 뭉뚱그리지 않는다. 우선 사용자는 **터미널 야드·게이트 운영 계획 담당자**,
시간 변경 협의의 상대는 **운송사 배차 담당자**, 변경 결과를 받는 사람은 **트럭 운전자**로 설정한다.
이 역할 구분은 현장 인터뷰 전의 설계 가정이다. 한 명이 모두를 승인한다고 단정하지 않는다.

| 사람 | 실제로 해야 할 결정 | 필요한 정보 |
|---|---|---|
| 터미널 담당자 | 블록 변경 승인·수정·거절, 예약 정원과 정책 사용 범위 설정 | 기존/제안 블록·시각, 용량, 혼잡과 제약, 변경 이유 |
| 운송사 배차 담당자 | 차량·화주 일정에 맞는 시간 변경 수락 또는 불가 응답 | 통지 여유, 가능 시간대, 추가 부담, 기존 예약 유지 선택 |
| 운전자 | 확정 안내에 따라 목적 블록·도착시각 확인 | 최종 확정 여부, 장소·시각, 변경 통지 |

v3의 Seller/Buyer는 소프트웨어 정책이다. **Buyer의 BUY를 사람·운송사의 동의로 해석하지 않는다.**
학습된 거절권 실험도 인간의 감독·수용성에 대한 실험이 아니다.
서로 다른 실제 이해관계자의 사적 비용을 학습했다는 주장도 현 공통 터미널 목적함수와 맞지 않는다.

## 2. 원고에 넣을 상호작용 흐름

1. 담당자가 허용 블록·예약 정원·변경 가능 시간대를 설정한다.
2. 시스템은 확정 전 검토할 변경안을 기존 배정과 함께 제시한다.
3. 담당자는 변경 이유와 제약을 확인하고 승인·수정·거절한다.
4. 시간 변경은 운송사 배차 담당자의 일정 가능 여부를 확인한다.
5. 실행 전 자원 상태와 예약 정원을 다시 검사하고 최종 안내를 보낸다.
6. 응답 지연·거절·제약 위반이면 기존의 유효한 예약을 유지하고 사유를 기록한다.

위는 사용 시나리오다. 외부 운영 시스템의 API·동기화는 현재 연구 제외 범위이므로
실제 연동을 만들지 않고 기록 재생 또는 모형 화면에서 검토한다.
모든 차량을 사람이 매분 승인해야 한다는 운영 가정은 하지 않는다. 검토 가능한 업무량을 먼저 확인하고,
일괄 검토·예외 검토 중 무엇이 필요한지를 평가에서 묻는다. 자동 실행 범위는 검증 전 기정사실로 두지 않는다.

화면에 제시할 것은 기존/제안 배정, 알려진 혼잡·잔여 정원·통지 시간과 가능한 조작이다.
검증되지 않은 신경망 출력을 “정확한 원화 절감액”이나 신뢰확률로 보여 주지 않는다.
효과의 불확실성은 전체 실험의 범위로 설명하고, 개별 제안의 확률 표시는 별도 보정이 있어야 가능하다.
실행 전에 수정·거절할 수 있게 하고 실행 이후 되돌릴 수 있는 범위도 명시한다.

## 3. 필요한 HCI 증거의 두 수준

**기본 개정:** 서론의 사용자·업무 문제, 방법의 시스템 경계·권한, 논의의 사용 시나리오를 추가한다.
정책끼리의 합의와 사람의 통제를 분리한 그림, 정상·불가·응답 지연 사례를 포함한다.
이는 맥락 설명을 보완하지만 사용자 편익을 실증하지 않는다.

**HCI 기여가 제출처의 핵심이면:** 실제 대상 역할의 참가자를 모집해 과업 평가를 설계한다.
제안 규모는 역할별 2~3명, 총 6~9명의 형성적 평가이며 채용 가능성과 역할 중복에 따라 사전 확정한다.
이 숫자로 인구 전체에 대한 유의한 효과를 주장하지 않는다. 정량적인 효과 검정은 별도 표본 설계가 필요하다.
실제 운영자 확보가 안 되면 대리 참가자 평가의 한계를 명시한다.

과업은 정상 혼잡 완화, 다른 일정 때문에 불가능한 변경, 수신 측 용량 부족, 판단 근거가 부족한 변경이다.
동일한 추천 집합에서 “추천만 표시”와 “운영 근거·제약과 수정 기능 표시”를 비교하는 것을 제안한다.
표시 순서를 교차 배정하고 난이도가 비슷한 서로 다른 사례를 써 반복 노출 학습효과를 줄인다.
추천 품질을 조건마다 바꾸지 않아 화면 효과와 정책 효과가 섞이지 않게 한다.

기록할 것은 판단 시간, 잘못된 승인·거절, 이해한 이유, 수정 성공, 업무 부담과 적절한 의존이다.
승인율이 높다는 것만으로 좋은 시스템이라 판단하지 않는다. 나쁜 제안을 거절할 수 있는지도 본다.
인터뷰 원문에서 어떤 정보가 부족했고 권한이 모호했는지 보존한다.

연구 설계 참고로 [Amershi 외, CHI 2019](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)는
사람과 AI 상호작용의 일반 설계 지침을 평가해 제시했다. 이 자료는 설계 틀이며 항만 현장 사용성을 보증하지 않는다.
실험 참여 요청·연락·모집은 이번 작업에 포함하지 않는다.

## 4. 온라인 처리시간 — 망 한 번 호출과 전체 업무를 구분

v3 운영은 반사실 분기 없이 실행되도록 설계됐다. 호출 0회 확인은 속도 측정을 대신하지 않는다.
측정 범위는 **상태·후보 구성 → 제안망 → 수락망 → 충돌·정원 확인 → 확정** 전체다.
시뮬레이터가 다음 상태까지 시간을 진행하는 비용과 실제 시스템에서 정책이 결정하는 비용은 구분한다.
기능별 시간과 전체 결정 묶음 시간을 둘 다 재고, CPU·메모리·스레드 수·라이브러리 버전을 기록한다.

대표·혼잡·최대 후보 수의 실제 저장 상태를 사용한다. 초기 구동과 예열 후 실행도 구분한다.
제안 예산은 조건별 서로 다른 상태 1,000묶음이며 예비 계측 후 측정 계약을 고정한다.
중앙값, P95(100번 중 느린 5번이 시작되는 처리시간), P99, 최댓값,
60초 결정주기 초과 횟수와 그때 후보 수를 보고한다. 현재 결정주기와 비교하되
장비가 다른 현장의 응답시간 보장으로 확대하지 않는다.
외부 통신과 사람의 응답 시간은 별도 미측정 구간이다. 정책 추론시간에 포함한 것처럼 쓰지 않는다.

## 5. 재현 묶음

- 실행 커밋과 변경 여부, 실행 명령, 의존성 버전, 하드웨어와 스레드 수.
- 환경·학습·초기화·탐색·평가 시드의 실제 목록과 체크포인트 해시.
- 특징 이름·단위·정규화·결측 처리, 망 크기·손실식·학습률·배치·라벨 수·탐색 일정.
- 제안 후보 생성·KEEP 처리·Buyer의 입력·동점 해소·정원·충돌 처리 의사코드.
- 반사실 교사의 비교 행동·후속 정책·난수 공유·시간 길이·라벨 기준선.
- 초기화 안정화·측정창·완료 추적·비용 항목·대상 작업 보존 규칙.
- 정책별 월 결과와 날짜별 보조 결과, 실패·미완료·제약 위반도 포함한 원자료.
- 원자료에서 표·그림·통계 결과를 다시 생성하는 명령.

하드웨어와 실행 경로가 확인되기 전에 추론 시간을 추정 숫자로 원고에 넣지 않는다.
사용자 화면·실항만 운영·학습 성공을 미실행 상태에서 완료된 것으로 표현하지 않는다.

## 6. 답변서 문장 구성

각 답변은 “우려를 인정한다 → 무엇을 바꿨는지 → 어떤 결과가 나왔는지 → 어디에 반영했는지”로 쓴다.
현재는 전략 단계이므로 시제는 “검증할 계획”이다. 숫자와 페이지가 생긴 뒤 완료형으로 바꾼다.
심사위원 2에게는 독립 반복과 외부 보정을 별도로 제시하고,
심사위원 3에게는 대상 사용자·권한·사용 시점·검증 수준을 첫 문장에서 답한다.
