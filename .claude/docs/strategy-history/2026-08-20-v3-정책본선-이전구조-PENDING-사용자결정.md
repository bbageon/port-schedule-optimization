# v3 정책 본선 확정·이전 구조 PENDING — 사용자 결정

- **결정일**: 2026-08-20
- **범위**: Dashboard의 정책 아키텍처 분류와 선행관계
- **상태**: 사용자 결정 반영

## 1. 결정 경위

새로 세팅할 v3는 기존 판매정책을 한 단계씩 보정하는 연장이 아니라, 독립 Seller·Buyer와
학습 전용 장기 반사실 교사를 중심으로 다시 세우는 정책 구조다. 그런데 Dashboard에는
이전 v1/v2 보정 작업과 새 v3 정책 작업이 한 순서로 이어져 있어, 무엇을 먼저 구현할지와
어떤 비용·보상 계약이 정본인지 혼동될 수 있었다.

사용자는 이전 아키텍처 관련 작업을 `PENDING`으로 넘기고, `YR-203·207·204·205`가
v3 정책과 직접 관련된 사항이라고 명시하도록 결정했다.

## 2. v3 정책 본선

| 순서 | Row | v3에서 맡는 일 |
|---:|---|---|
| 1 | [[YR-203]] | 오더당 최초 1회 판단, 독립 SELL/BUY 요청, 동시오더 배치 Resolver |
| 2 | [[YR-207]] | gate-in→gate-out 턴타임을 포함한 하나의 원화 환산 terminal cost |
| 3 | [[YR-204]] | SELL↔KEEP, BUY↔REJECT 세계를 학습 때만 굴리는 장기 반사실 교사 |
| 4 | [[YR-205]] | 교사 라벨을 근사하는 독립 Seller·Buyer actor와 운영 추론 |

고정 실행 순서는 다음과 같다.

```text
YR-203 → YR-207 → YR-204 → YR-205
```

네 row는 v3 정책 본선이지만 즉시 착수한다는 뜻은 아니다. 현재 연구 진행 3대 게이트 중
performance(규칙 대비 성능) 게이트가 해소되기 전에는 모두 backlog에 둔다.

## 3. PENDING으로 보존하는 이전 구조

| Row | 보존 이유 | 재검토 시점 |
|---|---|---|
| [[YR-190]] | 이전 v1/v2 정책 무대의 불확실성 스윕 | v3 본선 판정 뒤 |
| [[YR-198]] | 이전 판매층에 크레인 예측정보를 더하는 보정 | v3 본선 판정 뒤 |
| [[YR-201]] | v2 동결 비용표 안의 단기 반사실 보상 보정 | YR-204 판정 뒤 |
| [[YR-202]] | v2 보상에 국소 미래항을 덧붙이는 경로 | YR-204 판정 뒤 |
| [[YR-206]] | 구매 지역분해 아이디어의 동기 기록 | v3 본선 판정 뒤 |

`PENDING`은 기각·삭제·완료가 아니다. 기존 근거를 보존하되 v3 구현의 필수 선행조건으로
실행하지 않는 상태다. 특히 `YR-201→YR-202`는 `YR-203`이나 `YR-204`의 선행에서 뺀다.

완료된 [[YR-187]]과 [[YR-199]]는 과거 결과와 근거이므로 상태를 되돌리지 않는다.
[[YR-208]]은 정책 시각·실제 대기 대수라는 별도 정보축이며, 이번 네 단계 v3 정책
본선에는 넣지 않는다.

## 4. 검토한 대안과 기각 이유

1. **기존 8단계 전체를 v3로 부르기**: 이전 구조 보정과 새 정책 본선이 섞여 구현
   순서와 성공 기준이 흐려지므로 기각했다.
2. **이전 row를 삭제하거나 완료 처리하기**: 아직 판정하지 않은 가설과 결정 경위를
   잃거나 미실행을 완료로 오해하게 하므로 기각했다.
3. **YR-201·202를 YR-204의 필수 선행으로 유지하기**: v3는 YR-207의 같은 terminal
   objective를 H=1시간 동안 직접 비교하므로 v2용 국소 보정을 먼저 거칠 필요가 없다.

## 5. 적용 범위와 되돌릴 조건

- Dashboard index·backlog row·각 task spec의 상태와 선행관계에 이 분류를 적용한다.
- 코드를 구현하거나 실험을 실행하는 결정은 아니다.
- v3 잠금평가 뒤 특정 정보나 국소 비용항의 결손이 원인으로 확인될 때만 해당 PENDING
  row를 별도 단일축 작업으로 다시 검토한다.
- 재개할 때는 먼저 Dashboard 상태와 spec을 함께 바꾼다.
