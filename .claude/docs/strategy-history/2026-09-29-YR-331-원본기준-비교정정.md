# YR-331-f — 원본 배정 유지 기준으로 비교를 정정한 경위

## 사용자 지시와 기존 결과의 경계

2026-09-29 사용자는 학습 결과를 들은 뒤 “기존 작업 규칙이 뭔데?”라고 물었다.
설명은 KEEP+SF-SPT, 즉 거래 없이 실작업 우선·짧은 작업 우선으로 처리하는 코드상의 규칙이었다.
사용자는 이어 “아니 재배정 전 원본기준으로 해야지”라고 비교 기준을 바로잡았다.

기존 e 실험은 새 운영 보상 모델 3개와 같은 횟수로 학습한 이전 원화 보상 모델 3개를 평가했다.
운영 보상 모델의 평균 점수는 7.0645721946886955, 이전 보상은 7.30132313749322였다.
KEEP+SF-SPT의 평균은 6.065577453723356이다. 이전 대비 3.2425758776348235% 개선,
규칙 대비 16.469903295886624% 악화라는 산술 자체는 맞다.
그러나 규칙과의 비교에서는 **거래 허용 여부와 크레인 작업 선택 방법이 동시에 달랐다.**
이 차이를 원본 배정 대비 판매·구매 효과라고 설명하면 사용자가 요청한 연구 질문과 어긋난다.
e의 실행 전 계약·원자료·수치는 덮어쓰지 않고 역사적 비교로 보존한다.

## 원본을 확인한 결과

`src/yard_rl/v6/stage/fixed_seed.py`의 파일 규격은 `yard_rl.v6.fixed_cargo_seed.v2`다.
원입력의 최상위 항목은 days, initial_inventory, lead_mode, month_end_s, orders,
rules, schedule, schema, seed, sources, vessels_by_day다.
오더에는 doc_key, in_out, copino_notice_s, in_out_reserve_s, con_loc, con_no 여섯 필드가 있다.
`orders_from_schedule()`는 실행 기록을 비워서 만든다. 물리 실행 뒤의 작업 순서·완료 시각은 원본에 없다.
일정의 gate_in_s는 합성 입력의 도착 재료이며, 완료 비용이나 실터미널 실행 결과를 뜻하지 않는다.

따라서 원본에서 비용을 바로 읽는 방식은 성립하지 않는다. 예약 시각을 완료 시각으로 대체하면
미처리 작업의 시간을 지워 버리게 된다. 파일을 그대로 복원하고 같은 크레인 정책으로 실행해
원본 배정을 유지했을 때의 결과를 새로 측정해야 한다.
사용자에게 별도의 원본 실행 이력을 뜻하는지 확인 질문을 전달했다. 응답을 기다리는 동안
현재 시드의 최초 위치·예약 시각을 원본으로 보는 비교를 준비했고 그 해석을 설명했다.

## 검토한 대안과 채택 이유

1. 기존 KEEP+SF-SPT 값을 이름만 ‘원본’으로 바꾸는 안: 기각. 작업 선택 정책도 달라 혼동이 남는다.
2. 원본 일정의 시간 필드만으로 비용을 계산하는 안: 기각. 실제 처리·완료 기록이 없고 혼잡 지연이 반영되지 않는다.
3. 기존 모델 평가 결과와 새 KEEP 평가만 이어 붙이는 안: 기각. 기존 난수열은 판매·구매·크레인이 공유하므로
   판매 추첨을 빼는 순간 크레인의 추첨 위치도 바뀐다. 공통 첫날 상태도 보장할 수 없다.
4. 같은 모델의 두 실행을 새로 짝지어 재배정만 허용하거나 차단하는 안: 채택.
   크레인 정책·보상 기준·물리·수요를 같게 두어 이번 재배정 효과라는 질문에 맞춘다.
5. 새로 학습하거나 행동 확률을 최고점 선택으로 바꾸는 안: 기각. 비교 기준 외의 축을 동시에 바꾸기 때문이다.

## 결과 열람 전 고정한 설정

- 모델: e의 train-9931000-operational, train-9941000-operational, train-9951000-operational 최종 가중치.
- 평가 입력: 9961000, 9971000, 9981000. 이전에 보존한 파일 그대로이며 새 잠금평가라고 부르지 않는다.
- 각 입력은 트럭 3,500 / 7,500 / 3,500건, 전체 3일에 끝처리 2시간을 더 실행한다.
- 각 모델의 두 실행은 `original`과 `reallocated`; 총 6회다. 크레인은 양쪽 모두 같은 학습 정책과 추첨 선택이다.
- 첫날 0~86,400초는 두 실행 모두 KEEP. 이 구간의 매분 물리 기록이 정확히 같아야 한다.
- 둘째 날부터 `reallocated`만 판매·구매를 허용한다. `original`은 끝까지 KEEP/REJECT다.
- 주 측정창은 86,400~172,800초. 미처리 트럭과 본선 작업은 259,200초에서 센다.
- 판매·구매·크레인은 역할별 난수 생성기를 사용한다. 시드 규칙은
  `SHA256('v6-original-evaluation-v1:<seed>:<role>')`의 앞 8바이트를 큰자리 우선 정수로 읽고 `2**63`으로 나눈 나머지다.
- 같은 역할의 난수 시드는 두 실행에서 같다. 환경이 달라진 뒤 행동 자체까지 같도록 강제하지 않는다.
- 보상과 평가 눈금은 e의 네 물리 지표·고정 표준편차·각 0.25 비중을 그대로 유지한다.
- 점수 감소율은 `100×(1−재배정 점수/원본 유지 점수)`. 평균은 세 점수의 평균끼리 비교한다.
- 보호 조건: 각 쌍에서 최초 요청~완료 누적시간·트럭 잔여·본선 잔여가 모두 늘지 않아야 한다.
- 가중치 업데이트 0회, 원입력·모델 파일 지문 동일, 물리 제약·전건 투입·원본 6필드 보존을 검사한다.
- CPU 스레드 1개·최대 2개 동시 실행. 기존 합성 환경 현실성 미통과 상태를 승계한다.

## 구현과 실행 전 확인

- 비교 전용 `OriginalComparisonRuntime`만 추가했다. 일반 학습 런타임과 크레인 행동 후보·선택기는 바꾸지 않았다.
- 기준 실행의 KEEP/REJECT 인코딩·마스크를 검사하고, 실제 최종 오더 6필드와 거래 횟수를 대조한다.
- 단위·기존 학습 연결 검사 25개가 통과했다. 역할별 난수 분리 검사에서는 판매·구매 호출 수가 달라도
  같은 입력을 받은 크레인의 30회 선택과 난수 상태가 같았다.
- 첫 짧은 실행 2개는 종료 기록의 `_stamped` 집합이 JSON으로 직렬화되지 않아 저장 단계에서 실패했다.
  물리·정책 실패가 아니라 기록 저장 결함이었다. 발생 단계 이름의 정렬 목록으로 저장하도록 고쳤다.
  실패 로그·부분 기록·당시 체크포인트는 `smoke-a0d4fb94`에 보존한다.
- 수정 뒤 `smoke-a521a101`의 2시간 실행 두 개가 완료됐다. 첫 1시간 물리 기록은 정확히 같았다.
  원본 유지 쪽은 14,500개 오더의 모든 필드가 같고 거래 0건이었다.
  재배정 쪽은 공간 4건·시간 11건이 실제 발생했다. 짧은 실행 성능을 본평가로 보고하지 않는다.
- 본평가 실행 코드는 `a521a101`이며 깨끗한 별도 작업 폴더에서 실행했다.
- 이전 게이트는 과거 비교의 신뢰성을 PASS로 보관하여 reliability 보정 요청을 거부했다.
  사용자 직접 지시의 비교 계약 정정으로 범위를 한정했으며, 성능·현실성 게이트를 통과로 바꾸지 않았다.

## 적용 범위와 재검토 조건

이 비교는 **현재 학습된 크레인을 그대로 둔 상태에서 재배정이 원본 배정보다 나은지**를 답한다.
실제 터미널의 최초 배차 정책·작업 순서 기록을 받으면 그 자료의 재현 가능성과 비교 정의를 먼저 확인해야 한다.
원본 실행 이력이 확인되면 그 기준을 이번 진단과 별도로 명시하며 현재 결과의 이름만 바꾸지 않는다.
학습 정책 전체의 우월성·TOS 대비 성능·최적 혼잡도·정규화만의 효과는 이 비교로 증명하지 않는다.
다음 등록 작업은 c(검증 입력 공급 부족 복구), 이어 a(독립 자료의 안전 수용 상한 확인)다.
