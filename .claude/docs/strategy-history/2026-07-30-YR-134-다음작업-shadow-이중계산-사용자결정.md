# YR-134 다음 작업 shadow 이중계산 — 사용자 결정

> 날짜: 2026-07-30
> 상태: 설계 등록, 구현 전
> 연결: [YR-134 task spec](../dashboard-task-specs/YR-134-next-action-shadow.md)

## 1. 출발한 제안

사용자는 현재 작업을 수행하는 동안 다음 작업을 미리 준비하는 흐름을 제안했다.

```text
[현재 작업 시작]
1. 현재 상태와 ETA 수집
2. 현재 작업 완료 예상상태 생성
3. 다음 작업 후보 채점
4. 다음 작업과 예비 후보 계산

[현재 작업 수행 중]
5. 신규 정보 저장
6. 일반 신규 도착에는 기존 계산 유지
7. 취소·재배정·고장 같은 큰 변화만 반영

[현재 작업 완료]
8. 미리 고른 후보 실행 가능 여부 검사
9. 유효하면 즉시 시작
10. 무효면 예비 후보
11. 둘 다 없을 때 재계산
```

초기안은 다음 작업을 미리 계산한다는 점은 타당하지만, 8~11은 아직 검증되지 않은
예측을 실제 실행에 강제하는 제약이다. 사용자 판단은 **정책 성능을 먼저 검증하고,
그 전에는 제약을 추가하지 않는다**로 확정됐다.

## 2. 확정한 첫 단계

실행을 바꾸지 않는 그림자(shadow) 방식으로 축소한다.

```text
작업 시작
→ 완료 예상상태에서 다음·예비후보 계산
→ 로그에만 저장

작업 완료
→ 동시각 물리사건을 반영
→ 기존 정책이 실제 최신 상태에서 자유롭게 다시 선택
→ 사전 예측과 실제 후보·선택·비용을 비교
```

따라서 계산은 의도적으로 두 번 한다.

- 첫 계산은 “지금 가진 정보로 완료 뒤를 얼마나 맞힐 수 있는가”라는 시험 답안이다.
- 둘째 계산은 실제 완료 상태에서의 현행 의사결정이다.
- 둘째 계산을 생략하면 첫 계산의 정확도와 손실을 알 수 없으므로 연구 단계에서는
  중복이 아니라 검증 비용이다.

## 3. 왜 예약하지 않는가

현재 근거는 hard 예약을 정당화하지 못한다.

- YR-131의 순위학습은 후보 순위 성분을 만들었지만 top-1 일치는 약 0.35~0.40이었다.
- YR-132 종결 잔여 표적은 2/3 초기화에서 좋아졌지만 1/3에서 역효과가 나 기각됐다.
- 작업 중에는 신규 도착, 공개 ETA 갱신, 형제 크레인의 선택, stack 변화가 생길 수 있다.
- 현재 물리 `ReservationTable`은 token·lane·corridor·slot을 실제로 막는다. 예측 로그를
  여기에 넣으면 이미 새로운 제어정책이 된다.

따라서 이 단계의 “예비 후보”는 예약도 보장도 아니다. 단지 top-K 예측 기록이다.

## 4. 두 번째 계산도 정답은 아니다

완료 시점에 현행 정책이 새로 고른 후보는 “그 시점의 정책 선택”이지 최적 행동의
정답이 아니다. 두 계산의 일치율만 보면 같은 정책이 시간에 따라 얼마나 안정적인지는
알 수 있지만, 둘 다 나쁜 후보를 고른 경우를 놓친다.

평가는 두 층으로 나눈다.

1. **시간적 일치**: 사전 top-K가 완료 시점 후보·정책 순위에 얼마나 남았는가.
2. **비용상 품질**: 같은 완료상태의 후보들을 사후 짝비교했을 때, 사전 후보를 썼다면
   최선 참고후보보다 비용이 얼마나 더 들었는가.

사후 반사실은 진단에만 사용하고 실제 실행이나 정책 입력에는 넣지 않는다.
후보별 비용은 같은 완료시점 snapshot·고정 평가창·후속 기준정책·비용계약에서 비교하며,
확률 표본은 공통 무작위수를 쓴다. 여기서 얻는 최선은 검사한 후보·진단 창 안의 참고
최선이지 전 에피소드의 전역 최적은 아니다.

## 5. 정보안전 결정

작업 시작 계산은 그 시점에 알 수 있는 정보만 사용한다.

- 허용: 현재 커밋된 실행계획, 공개 ETA·예약·본선 계획, 형제 크레인의 커밋 의도.
- 금지: 실제 미래 도착, 미통지 고장, 이후 계획변경, 실제 이벤트 큐.

현재 `_rollout_cost`는 엔진 사본의 실제 미래 이벤트를 소비하는 오라클이라 사용할 수
없다. 진행 중 이동은 `observable_stacks()`에 아직 반영되지 않으므로 라이브 stack을
바꾸지 않는 별도 완료 projection이 필요하다.

shadow 계산은 본 정책·시나리오·탐험 난수열을 소비해서도 안 된다. 표본 projection이
필요하면 전용 난수열을 사용하고, 기능 ON/OFF에서 본 실험 난수상태가 동일한지 검사한다.

## 6. 이번 단계에서 하지 않는 것

- 다음 작업 token·slot·lane·corridor 선점
- 새 도착을 무시하도록 정책 강제
- hard invalidation에 따른 자동 후보 교체
- 1순위·예비후보 자동 실행
- replay·보상·Q 입력에 shadow 기록 추가
- “사전계산이 트럭 대기를 줄였다”는 주장

현 시뮬레이터는 추론 벽시계 시간을 물리시간으로 소비하지 않으므로, 미리 계산해도
시뮬레이션 트럭 시간은 줄지 않는다. 이번 단계는 오직 **미래 후보 예측 가능성**을
검증한다.

## 7. 후속 분기

- 예측력·비용상 손실이 사전 문턱을 통과하지 못하면 완료시점 자유 재계산을 유지한다.
- 통과하면 계산 재사용을 soft cache라는 새 단일축 작업으로 등록한다.
- 실제 예약·자동실행·제약은 soft cache 효과까지 독립 검증한 뒤에만 별도 검토한다.

이 결정은 “제약을 먼저 넣어 정책을 좋아 보이게 만들지 않고, 자유 정책의 예측 성능을
먼저 증명한다”는 연구 원칙을 보존한다.

## 8. BlockQ-v2 행동 단위 정정

현재 정책의 후보는 크레인 한 대의 다음 작업이 아니라, 한 decision point에 참여한 모든
`crane_ids`의 공동 배정이다. 따라서 예측 단위도 다음으로 고정한다.

```text
다음 완료사건 뒤 예상 decision point
+ 예상 crane_ids
+ 공동후보 top-K
```

완료 뒤 실제 참여 크레인이 다르거나 decision이 열리지 않으면 비교 가능한 표본만 남기고
버리지 않는다. 전체 예측 기준에서는 실패로 세고, 공동행동 단위가 맞은 표본의 순위
정확도는 조건부 진단으로 따로 낸다.

후보 식별에는 결정 안의 임시 `candidate_id`를 쓰지 않는다. 크레인·행동종류·canonical
`JobRef` 전 필드와 `JobPlan`의 모든 실행결과 필드를 묶은 물리효과 hash로 서로 다른
실행안을 구분한다.

## 9. 사후 비용 자와 무영향 계약

완료시 정책 선택은 최적 정답이 아니므로, 기존 YR-128과 같은 C600 자를 재사용한다.
동시각 사건 처리 뒤 행동 commit 전 동일 snapshot에서 모든 공동후보를 `RC_TRAIN`,
600초 창, SF-SPT 후속정책, 공통 외생난수로 짝평가한다. `shadow 후보 C600 - 완료후보
최소 C600`을 손실로 기록한다. 이는 미래정보를 쓰는 진단용 참고값이며 배포에는 쓰지
않는다. YR-132에서 재현 실패한 개수 잔여 D_H는 이번 표적에서 제외한다.

완료 때 shadow 후보가 사라졌거나 실행 불가능하면 regret을 계산할 수 없다. 그 표본을
조용히 빼지 않고 커버리지 실패로 세며, regret은 생존 후보 조건부 결과라고 명시한다.
후속 soft cache는 전체 커버리지와 조건부 regret을 함께 통과할 때만 검토한다.

shadow 계산은 별도 후보 생성기 clone·전용 난수열·신경망 `eval()`·`no_grad()`를 사용하고,
실제 event log가 아닌 diagnostic sink에만 쓴다. 기능 ON/OFF에서 정책 모드·파라미터,
생성기 cache/counter, Python·Torch·시나리오 RNG 상태가 같아야 “실행 영향 0”으로
인정한다.
