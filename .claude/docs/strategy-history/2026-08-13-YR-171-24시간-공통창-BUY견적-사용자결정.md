# 2026-08-13 — YR-171 **24시간 공통창·정책기반 BUY 견적** 사용자 결정

## 1. 결정 경위

현행 시간 판매는 판매 건마다 `+15분` 한 좌표만 비교한다. YR-170 축 분리 진단에서는
시간 판매만 켠 조건이 KEEP보다 `+438.3` 비용(`+18.68%`, 판매 1건당 `+14.28분`)으로
악화됐다. 고정 15분 뒤가 더 한산하다는 보장이 없고, 기사 외부대기도 비용에 포함되므로
혼잡 첨두를 비껴가지 못하면 구조적으로 손해가 난다.

사용자는 실제 예약정보가 하루 정도 공개될 수 있다는 점을 근거로, 30분을 미래 가시범위가
아니라 예약 슬롯 단위로 쓰고 Resolver와 각 블록이 같은 24시간 계획을 봐야 한다고 정정했다.
또한 수신 블록은 단순히 현재 내부 대수만 답하는 대신, 작업을 받았을 때 자기 ExecutionHead가
어떤 순서로 처리할지를 반영한 추가비용을 반환해야 한다고 확정했다.

## 2. 채택 구조

```text
같은 작업일 24시간 공개 예약·ETA·본선계획(plan_version 고정)
                         ↓
source TransferHead: KEEP 또는 작업 1건 OFFER
                         ↓
각 receiver: 30분 슬롯별 작업 가상 삽입
             동결 ExecutionHead로 수용 전/후 비용 계산
                         ↓
TransferResolver: receiver×slot의 터미널 순비용 비교
                         ↓
KEEP 또는 최저비용 조합 원자 확정
```

수신 응답은 별도 BUY 학습행동이 아니라 **정책기반 BUY 견적 모드**다.

```text
BUY부담(B,t) = J_B(t에 수용) − J_B(수용 안 함)

총 추가비용(B,t)
  = BUY부담(B,t) + 추가주행 + 기사 시간변경 + 불확실성 − source 절감
```

Resolver는 총 추가비용이 `KEEP=0`보다 낮은 조합만 확정한다. 실제 작업순서는 미래에 고정하지
않고, 작업이 도착했을 때 최신 상태의 ExecutionHead가 다시 선택한다.

## 3. 정보·동기화 계약

- 모든 블록과 Resolver는 같은 기준시각·같은 작업일 `00:00~24:00`·같은 version을 쓴다.
- 후보 시간은 같은 날의 30분 슬롯이며 날짜 변경은 금지한다.
- 공개 예약·ETA·본선계획만 사용하고 실제 미래 도착·완료시각은 보지 않는다.
- ETA·본선계획·용량 version이 바뀌면 이전 견적은 만료한다.
- 복수 제안은 작업 1회, receiver와 슬롯 용량, owner 원자성을 함께 지키며 일괄 매칭한다.
- 실제 TOS API·기사 승인 연동은 연구 범위 밖이다. 재예약은 전원 수락 가정의 최대 가능
  효과로만 해석하며 현장 성과로 주장하지 않는다.

## 4. 검토한 대안과 기각·보류 사유

1. **Resolver 수기식만 유지**: 실제 집행 정책이 만드는 트럭·본선·이동 순서를 충분히
   반영하지 못하므로 목표 구조로는 기각한다. 비교 기준선으로는 보존한다.
2. **receiver BUY PPO 별도 학습**: SELL과 BUY를 동시에 학습하면 실패 원인을 나눌 수 없고,
   블록별 비동기 시점 문제도 커진다. 현재는 기각하고 동결 ExecutionHead 견적부터 검증한다.
3. **source PPO가 목적지·시간까지 선택**: 복수 source의 슬롯 중복과 용량 충돌을 해결하기
   어려워 기각한다. source는 작업만 제안하고 목적지·시간은 Resolver에 남긴다.
4. **24시간 실행순서를 즉시 예약**: 미래 오차에 취약하고 정책 성능 검증 전 실행 제약을
   추가하므로 기각한다. 24시간 계산은 견적용이고 실제 실행은 최신 상태에서 재계산한다.

## 5. 구현 지위와 적용 범위

이 문서는 **목표 설계 결정**이며 구현 완료 evidence가 아니다. 현재 코드는 SELL 골격과
고정 `+15분` 시간 좌표, 수기 수신부담 견적 중심이다. 다음은 아직 미구현이다.

- 블록·Resolver 공통 24시간 snapshot/version 계약
- receiver×48슬롯의 ExecutionHead 수용 전/후 가상 실행
- 그 견적을 사용하는 블록×시간 일괄 matching

YR-171에서 `정보계약 재자격 → BUY 견적 shadow → Resolver matching` 순으로 한 축씩 검증한다.
성능이나 계산시간이 미달하면 해당 단계에서 멈추며, 임의 후보축소나 receiver PPO 추가로
우회하지 않는다.
