# YR-331 — 크레인 적정부하·구매 유인·보상 설계 결정

## 1. 결정 경위

사용자는 크레인별 자기 비용을 줄이는 정책이라면 구매가 생기지 않을 수 있다고 보았다.
실제 문헌에서 크레인 적정 작업량을 조사하고, 특정 혼잡도에서 효율·보상이 좋아지도록 설계를
수정하라고 요청했다. 직전의 터미널 간 판매·구매 구상은 추측이므로 보류하라는 지시도 함께 유지한다.

현 v6의 `ppo/runtime.py`를 확인하면 이미 터미널 총비용 증가분의 음수를 모든 블록이 공유한다.
각 크레인의 자기 비용만 별도로 최소화하는 구조가 아니다. 따라서 구매 불가능은 현재 결함으로
입증되지 않았다. 같은 구조의 v5 저장 실행에는 111,714건의 거래 확정(공간 17,023·시간 94,691)이
있다. 구매 호출은 146,032건으로, 호출·수락·거래 확정을 혼동하지 않는다. 이 기록은 구매의 존재만
보여 주며 잘 배웠다는 증거가 아니다. v6 GPU 학습 실적도 아니다.

원기록은 `outputs/v5/yr306-wait-30d-4549ae9/report.json`, 실행 코드 4549ae97db4aad834cad02698fad8c8b8c880f99다.
이번에는 전체 실행을 재현하지 않고 발췌 JSON과 원본 SHA256을 남겼다.

## 2. 문헌의 핵심 사실

- Huynh·Walton(2005) 원보고서 §5: 너무 낮은 예약 상한이 크레인의 추가 이동 때문에 체류를
  늘린 사례가 있다. 특정 두 블록의 45분 평균 체류 제약에서 미방문 5/15/25%별 상한은 7/10/15대/h.
  블록 기준이며 크레인당 공통 권장량으로 바꿔 읽지 않는다. 이동만 센 가동률도 구별한다.
- Ma 외(2022) 표1: 서비스율 0.633컨테이너/2분, 서비스시간 변동계수 0.42687.
  능력은 18.99건/h다. 이는 최적 수용량이 아니다.
- Riaventin 외(2024) 표7·9: 같은 한 크레인·8대/h에서 도착순은 가동률 97%, 체류 1,197초이고
  가까운 트럭 우선은 85%, 307초다. 9대/h에서도 각각 99%/2,380초, 90%/342초다.
  85% 최적을 검증한 연구가 아니며 다른 정책 열에 표 오류가 있어 사용 범위를 제한했다.
- 단일 서버 대기식으로 Ma 입력을 계산하면, 큐 대기 2/5/10분 가정별 상한은
  51.7111/72.8052/84.2627%, 수용률은 9.8199/13.8257/16.0015건/h다.
  5분은 우리 설명 가정이며 부산항 실측 목표가 아니다.
- Ng·Harada·Russell(1999) §3: 할인 잠재함수 차분은 원래 할인 목적의 최적 정책 보존 조건을 제공한다.
  신경망의 유한 학습 성능이나 할인하지 않은 총비용 순위까지 보장하지 않는다.

서지·PDF 위치·조건·파일 식별값은 [문헌 기록](../../../docs/research/v6-workload-reward/literature.md)과
그 폴더 `source_manifest.json`에 보존했다.

## 3. 검토한 대안과 선택

| 대안 | 판정 | 이유 |
|---|---|---|
| 모든 크레인 80% 가동률 목표 | 기각 | 공통 최적이라는 문헌 근거가 없고 이동·재취급을 늘려도 가동률이 높아짐 |
| BUY 한 번마다 고정 상금 | 기각 | 유효 완료 없이 거래·재판매만 늘릴 수 있음 |
| 목표 대기열에 매분 보너스 | 기각 | 일을 끝내지 않고 남겨 두는 별도 목적을 만들 수 있음 |
| 독립 자기 비용에 일괄 구매 가격 추가 | 미채택 | 현재 공유 보상과 불일치하며 가격까지 추가하는 별도 축이 됨 |
| 실제 비용을 부하 점수로 대체 | 기각 | 원화 비용·본선·물량 손실이 좋아졌는지 판정할 수 없음 |
| 처리 능력·수요에 맞는 부하의 잠재함수 차분 | 설계 채택 | 양쪽 부담을 함께 보고 원래 할인 목적을 유지하는 보조 신호로 한 축만 바꿈 |

이는 형식적 학습 목표를 "항상 붐비게 만들기"로 바꾸는 결정이 아니다. 적정 부하 상태를
계산해 그쪽으로 나아가는 변화를 전달하며, 최종 연구 성과는 여전히 실제 비용·서비스로 판정한다.
사용자의 제안을 비용 절감 목적에 맞게 구체화한 설계 판단이며 새로 실증된 가설로 쓰지 않는다.

## 4. 동결 범위·설정 전수

- 이번 산출물: 설계 문서·문헌 기록·수식 계산기·작업 명세. 새 항만 실행·학습은 0건.
- 기준 보상: 공유 터미널 원화 비용, S=1,000,000원, γ=0.999/분, 보상 간격 60초, 수집 60구간.
- 그대로 두는 축: 신경망 37입력·행동·비용 단가·엔진·PPO 갱신 설정.
- 최초 장부 관측 H=15분은 설계 가정이며 5/30분 감도 확인 뒤 실행값을 동결한다.
- 부하 x=f+m, 기준 능력 A>0, 가용 비율 a, 상한 ρ_safe. 고정 업무 f를 삭제하지 않고
  남는 여유에 이동 가능 업무를 능력 비례로 배분한 y를 목표로 한다.
- 점수 P=−Σ A(ρ−ρ*)²/ΣA, 보조 항 η[γ^(Δt/60)P(next)−P(now)]. η=1은 검산에만 썼다.
- 예시 두 대 A=100/100, 고정 업무 0, 상한 0.8/0.8, 부하 120/20→100/40.
  점수 −0.25→−0.09, 무시간 변화 +0.16, 60초 할인 보조 항 +0.16009.
- 원래 요청 시각으로 관측 대상에 포함하므로 이연만으로 부담 장부에서 지워지지 않는다.
- 실제 종료 P=0. 수집 종료·잘린 관측창은 P와 말단 가치를 이어 간다.
- 반사실 세계·새 가치망·COMA·모방 학습·단가 재조정을 함께 추가하지 않는다.
- 적정 상한·허용 대기·η·성능시험 시드/반복은 미동결이다. 그 값을 발명하지 않고
  YR-331-a/b의 착수 전 입력으로 분리했다. 이 문서를 완성된 성능 사전등록으로 부르지 않는다.

## 5. 검산과 게이트

표준 Python 계산기로 23개 검사를 통과했다. 서로 다른 능력·고정 업무 조합 81개에서
목표 배분의 합·상하한을 확인했다. 작업 처리·판매·구매·대기 경로 1,441개를 전부 열거해
할인 누적 보상의 차이가 같은 상수가 되는지 확인했고 최대 오차는 1.74×10^-14였다.
반복 거래·WAIT·변동 시간간격·중간창 말단 가치 처리도 포함한다. 이는 실제 학습 성공의 증거가 아니다.

`authorize-next`는 저장된 scenario PASS 재계산 실패로 `allowed=false`, 종료코드 1이었다.
2026-08-17 게이트·commit 7af37f760ab373eb663a6b7a88320c46698ea3bc를 읽었으며 기준을 완화하지 않았다.
현재 사용자의 직접 설계 요청으로 문헌·수식 작업만 수행했다. GPU 이식 작업을 밀어내거나
새 정책 학습·성능 채택을 허가한 것으로 해석하지 않는다.

## 6. 적용·되돌림

실행 보상은 아직 그대로다. YR-331-a에서 부하를 실제로 측정하고, YR-328의 게이트 전 지연
장부 판정 및 연구 게이트를 충족한 뒤 YR-331-b에서 항 하나만 추가한 비교를 한다.
높은 점수·많은 거래에도 비용·본선·완료가 악화되거나 목표에 접근하려고 작업을 보류하면 기각한다.
공유 보상 공로 희석·가치 추정 문제가 남으면 효과를 주장하지 않고 해당 실패 기제를 분리한다.
원시 주문·작업 보존과 물리·공개시점 검사를 통과하기 전에는 부산항 실제 성능을 주장하지 않는다.
