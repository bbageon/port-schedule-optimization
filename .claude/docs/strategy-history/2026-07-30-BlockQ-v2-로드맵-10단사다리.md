## 6차 피드백 (2026-07-30) — 목표 구조 정정(양방향)·YR-132 승인 조건

**구조 정정 (정본)**: 앞선 "TOS→TransferResolver→BlockQ" 일방향 서술은 부정확 —
①TOS 는 TransferResolver 를 거치지 않고 **각 블록의 Block Q 에 작업을 직접 배정**
②Block Q 는 블록 수만큼 존재(가중치 공유 가능하되 작업목록·스택·혼잡·크레인 상태는
블록별) ③반입·양하 작업도 처음엔 TOS 지정 블록 소속이며, **재배정 가능한 미적재
작업만** 판매 검토 시점에 원소유 Block Q 가 판매 후보(SELL_STORE)를 냄 ④TransferResolver
가 다른 Block Q 들에 수용부담을 조회해 KEEP vs TRANSFER(A→B) 비교·원자 확정. 즉
**Block Q ↔ TransferResolver 는 양방향** — 단 자유 대화가 아니라 정해진 숫자 교환:
판매효과(OutRelief)·수용부담(InBurden)·이전비용 → 절약 > 부담 판정. **SELL_STORE 는
크레인 물리 행동이 아님** — resolver 전 검사 통과 시에만 이동, 실패·무이득 시 원소유
블록이 정상 처리 (YR-099 spec·2026-07-26 결정 기록과 정합).

**구현 갭 (기록)**: 공용 시계·소유권·용량검사·원자 이전·실패 원상복구는 구현됨.
단 현행 실험은 Block Q 가 판매·수용 비용을 계산하는 대신 **중앙 review 함수가 혼잡도
차이(임계 0.10)로 직접 이송을 발동** — TransferQuoteQ 기반 양방향 견적은 미구현.
사다리 10단("검증된 Block Q 를 TransferResolver 와 결합")의 실체가 이 갭 해소다.

**YR-132 승인 + 조건 5**: (가) 종결 잔여 표적이 다음 방향으로 타당 — ①정식 row 등록
후 진행 ②λ 사전 고정(검증자료 보며 조정 금지) ③미완 '개수' 잔여는 **진단용 지위**
(쉬운 작업 다수로 급한 본선 1건을 가리는 편법 가능) ④성공 시 YR-123 비용곡선으로
비용가중 잔여로 승계 ⑤판정은 비용 상관보다 **순위·선택 후 손실(regret)** 중심 +
**완전히 새로운 평가 대역** 사용. 후속 순서: 성공 → 혼합손실(순위+보정) → 실제
에피소드 검증 / 실패 → 상태 별칭·비동기 크레인 정보 검사.
세션 검증치(라벨 재확인): 혼잡 상위 40% 결정 중 후보별 미완 수 차이 존재 57~71%·평균
범위 1.0~1.7건 — 잔여항의 신호 실재 확인.


## 사용자 정정 (2026-07-30) — 판매 발의 주체는 중앙이 아니라 원소유 Block Q

현행 결정층("게이트 진입 순간 **중앙 review 함수가 모든 해당 건을 일괄 검토**, 근거 =
중앙이 관측한 혼잡도 스냅샷 차 ≥ 0.10")은 **잘못된 임시 규칙**임을 사용자가 확정.
정본 설계:

- **발의 주체 = 원소유 단일 블록 큐(Block Q)**: 판매 창(게이트 진입~블록 도착) 안에서
  블록 큐가 스스로 "이 컨테이너를 판매하고 싶다"를 **계산**해 발의한다. 팔 이유가 없는
  건은 검토 대상 자체가 아니다 (중앙 전수 스캔 폐지).
- **동반 정보 = 계산된 판매효과(OutRelief)**: 발의 시 "이 작업이 빠지면 내 블록 비용이
  얼마나 감소하는가"의 계산값을 함께 넘긴다 — 혼잡 스냅샷 같은 외부 관측치 대체.
- 리조버는 **발의된 건에 한해** 수신 후보 Block Q 들의 수용부담(InBurden)을 조회,
  절약 > 부담 + 이전비용 이면 KEEP 대비 구체적 A→B 를 원자 확정.
- 집행층(2단계 커밋·전역 장부·용량·원자성)은 현행 그대로 재사용.

반영: backlog 에 [YR-133](../dashboard-task-specs/YR-133-blockq-sell-quote.md) 등록 —
사다리 10단("검증된 Block Q 를 리조버와 결합")의 구체 명세이자 TransferQuoteQ 갭의
해소 항목. 선결 = Block Q 의 순위·비용 능력(YR-131/132 사다리)과 공통 비용 계산기
(YR-123 — 판매효과·수용부담이 같은 단위로 계산되어야 비교 가능).


## 사용자 정정 2 (2026-07-30) — 판매는 블록 큐의 행동이며, 결정 단위는 "작업 후보들의 선택"

앞선 기록("판매는 물리 행동이 아니므로 행동 공간이 아니라 별도 검토 궤도")을 정정한다.

1. **유형 무지의 정확한 범위**: 본선/트럭이라는 **유형으로 규칙을 두지 않는다**는 뜻일
   뿐이다. 단일 블록 큐는 **작업 하나하나에 대해** "이 작업을 할지 안 할지"를 **견적
   계산으로 판단해야 한다** — 구분의 근거가 유형 라벨이 아니라 작업별 견적 값.
2. **판매 액션의 지위**: 위 기준에서 판매(SELL)는 물리 행동이 아니어도 **블록 큐의
   행동 공간에 포함되는 것이 타당하다** (사용자 확정). 실행 의미는 "리조버에 견적을
   동반해 발의"이며, 물리 이동은 리조버·집행층 통과 시에만 일어난다.
3. **결정 단위의 재정의**: 현행("유휴 크레인이 지금 실행할 작업 하나를 고름")이 아니라
   **미래정보(공개 ETA)를 고려한 "작업 후보들"을 선택할지/안 할지**의 문제다 — 블록
   큐는 크레인 파견자이기 전에 **자기 작업 목록의 관리자**(보유/판매 선택 포함).
4. 유지: 유형 무지 원칙·물리 안전(mask·블록 내부 resolver)·집행층(2단계 커밋)·판매 창
   잠금(블록 도착·배정 후 판매 불가).

착수 시 동결할 설계 질문(미리 기록): ①SELL 결정의 시점(크레인 결정 epoch 와 별도인
큐-관리 단계 vs 게이트 진입 epoch) ②작업별 견적 산출기(BlockQ-v2 능력·YR-123 계산기와의
연결) ③작업 후보 집합 선택의 표현(작업별 keep/sell 이진 + 실행 우선순위) — YR-133
사전등록에서 확정.
