# 중간점검 2026-08-07 — Dashboard ↔ spec ↔ 코드 정합

> 목적: "대시보드 서술과 실제 구현이 자꾸 어긋난다"는 지적을 받아, **기계적으로 전수 대조**하고
> 고칠 수 있는 것은 이 자리에서 고쳤다. 남긴 것은 왜 남겼는지 적었다.

## 1. board row ↔ spec 파일 (전수)

전체 **175 row**(중복 등록 0). 활성(in-progress·ready·backlog·cancelled) 46 · 완료 129.

| 항목 | 점검 전 | 조치 | 점검 후 |
|---|---|---|---|
| 활성 row 중 **spec 파일 없음** | 15 | board row Note 를 그대로 옮겨 spec 생성 | **0** |
| 활성 row 중 **상태줄 없음/불일치** | 22 | `**상태**: <board 상태>` 삽입·정정 | **0** |
| 완료(done) row 중 spec 없음 | 66 | — (1세대 Archive, YR-126 범위) | 66 |
| 완료 row 중 상태줄 없음 | 60 | — (같음) | 60 |

**왜 중요한가**: 감사 하네스(`audit_dashboard`)는 spec 의 `**상태**` 줄을 읽어 board 와 대조한다.
그 줄이 없으면 **검사 자체가 불가능**하다. 지금까지 활성 row 46건 중 37건이 그 상태였다.

생성한 spec 15건은 **row Note 를 옮긴 것**이며 새 서술을 지어내지 않았다. 각 문서에
"연구 설계가 정제된 상태가 아니며 착수 시 채운다"를 명시했다.

> 완료 row 의 공백은 이번에 손대지 않았다. 이미 [YR-126](dashboard-task-specs/YR-126-1-archive.md)
> 로 등록돼 있고, 과거 판정 문서를 지금 소급 작성하면 **당시 근거가 아닌 지금의 해석이 섞인다.**

## 2. spec 서술 ↔ 실제 코드 (현재 활성 작업 중심)

### 고친 것 — YR-150 명세를 코드에 맞춤

| spec 서술 | 실제 코드 | 조치 |
|---|---|---|
| "5~10분 스냅샷 **훅**" | 라이브 훅이 아니라 **A/O 장부 사후 재구성** (값은 동일·표본오차 0) | 서술 정정 |
| "hotspot 배분을 분리하고 블록 ID 를 seed별 순환" | 파라미터는 있으나 **1단계는 균등만**, **순환 미구현** | 현황 명시 + YR-157 범위로 이관 |
| "warm-up·측정창을 동결한다" | 코드 기본값으로 정해졌으나 **spec 에 값이 없었다** | **3,600 / 14,400 / 300초** 명시 |
| 평가계약 주지표에 비용 5종 | 1단계는 `cost_fn` **미부착 = 비용 미측정** | "2단계부터" 명시 |
| 부하 L 의 뜻 | 코드는 **고정 유입량** | 고정 유입량 vs 고정 WIP 대조표로 못 박음(아래 §3) |

### 남긴 것 — 새 과제로 등록

**[YR-160] 채택 배포 구성이 코드에 존재하지 않는다** (가장 무거운 발견).
Dashboard 는 "C0 + 유한 DEFER + 대기 허가증"을 채택 구성이라 적지만, 코드에는 그 이름의
객체가 없다. 행동 정의는 `candidates.py` **모듈 전역 플래그**이고 **기본값이 기각된 쪽**이다.

| 플래그 | 코드 기본값 | 채택 판정 |
|---|---|---|
| `SAFETY_ONLY` | `False` = 전략적 위치조정 **발행** | 위치조정 **제거**가 우월(YR-143/148) |
| `WAIT_MODE` | `"WAIT"` = 무기한 대기 | 유한 `DEFER_ALL`(YR-147) |
| `BOUND_REPO` / `PREPO_ONE_SHOT` | `False` / `False` | B2 계약에서 `True` / `True` |

실험들은 매번 전역을 갈아끼우고 되돌린다(10여 곳). **플래그를 안 켜면 조용히 기각된 정책이
돈다.** 실제로 YR-150 1단계 자격 파일럿의 규칙 기준선이 기본값으로 돌았다 — 자격 확인이
목적이라 판정에 영향은 없지만, **2단계 정책 비교에서 같은 실수가 나면 비교가 무의미해진다.**

## 3. 부하 L 정의 확정 (사용자 확인 2026-08-07)

| 방식 | 뜻 | 채택 |
|---|---|---|
| **고정 유입량** | 4시간 동안 **총** 50~150대가 도착. 터미널 안 대수는 **결과로 측정** | ✅ 현재 계약 |
| 고정 재공량(WIP) | 터미널 **안에 항상** 50~150대가 있도록 계속 보충 | ❌ 폐기 |

폐기 이유: 빨리 처리하는 정책일수록 트럭을 더 받아 **정책별 입력량이 달라져** 공정 비교가 깨진다.
포화 상태를 보고 싶으면 본 성능시험에 섞지 않고
[YR-159](dashboard-task-specs/YR-159-saturation-stress-separate.md) 로 분리한다.

## 6. 재발 방지

이번 불일치들의 공통 원인은 **"검사할 수 없는 상태"** 였다 — spec 에 상태줄이 없어 감사가
돌지 않았고, 채택 구성이 코드에 이름으로 없어 대조할 대상이 없었다. 따라서 규칙 하나를 추가한다.

> **row 를 등록·갱신할 때 spec 의 `**상태**` 줄과 board 상태를 같은 커밋에서 맞춘다.
> 그리고 "채택된 무엇"을 문서에 쓰면, 코드에서 그것을 가리키는 이름이 있어야 한다.**

절차 원본은 [dashboard-ops](../skills/dashboard-ops.md) 와
[research-gates](../skills/research-gates.md) 에 둔다.
