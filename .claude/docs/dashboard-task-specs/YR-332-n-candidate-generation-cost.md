# YR-332-n — 큰 야드에서 후보 생성 계산이 늘어나는 원인 확인

- **상태**: in-progress
- 착수: 2026-11-05. 사용자 6단계 순차 실험 지시의 1단계.
- 사전등록: `docs/research/v7-discharge/six-step-prereg.md`.
- 상위: [[YR-332]], 파생: [[YR-332-l]], 2026-11-05.
- 정책·보상·후보 범위를 유지하는 계산 경로 보정 한 축이다.

## 무엇과 왜

기본 하루 환경 7,500건·시드 9,913,320에서 전체 시간이 개별 144.53초→개선 148.98초였다.
점수/선택은 9.86초→3.39초로 줄었지만 후보 생성은 58.30초→69.39초로 늘었다.
3,500건 세 입력에서도 느린 결정의 경계가 개선 후 높아졌다. 특정 하위 함수 원인은 미확정이다.
작은 빈 야드의 이득을 큰 적재 상태에 일반화하기 전에 실제 병목을 확인해야 한다.

## 완료 기준

1. 동일 입력·모델에서 상태 목록, 물리 상태 대조, 계획 캐시, 슬롯 탐색의 시간을 구분한다.
2. 프로파일링 비용이 포함된 시간과 최종 순수 실행 시간을 구분해 원인을 재현한다.
3. 확인된 계산 한 축만 보정하고 후보·선택·사건·완료·비용이 동일한지 대조한다.
4. 세 기본 물량의 전체 시간과 느린 결정, 메모리를 함께 보고한다. 평균 이득으로 악화를 숨기지 않는다.
5. 입력·물리 용량·학습·보상은 동결한다. 실현 결과를 보고 편한 입력만 선택하지 않는다.

## 2026-11-05 문헌·구현 검토 — 적용 전 제안

사용자는 재현율을 먼저, 효과를 다음으로 검토하도록 요청했다. 후보 보존과 반복 재현을 분리한다.
현재 `DispatchCache.scope`는 크레인별 생성마다 블록 컨테이너·스택 상태를 순회하고,
변경이 있으면 해당 저장 계획을 모두 비운다. 이것의 시간 기여는 아직 별도 실측하지 않았다.
`CandidateGenerator._generate`는 계획을 포함한 raw 후보 생성 뒤 `_prune`을 부른다.
따라서 후보 12 제한을 후보 생성 계산량 12의 보장으로 해석할 수 없다.

보정 후보는 **변경 사건에 따른 갱신**이다. 우선 기존 후보 범위·비용·물리 조건을 동결한다.

1. 전체 적재 상태를 대조하는 대신 변경 시 세대 번호를 올린다. 직접 속성 수정 경로도 추적한다.
2. 불변 제원·적재 의존 계획과 크레인 위치·시간·예약 의존 계산을 분리한다.
3. 영향 범위를 증명할 수 있는 것만 재사용한다. 반입 자리 선택은 다른 스택의 빈자리에도
   영향을 받으므로, 단순히 대상 스택 하나만 보고 무효화를 생략하면 안 된다.
4. 시간만 흘러 예약 창·마감 조건이 바뀌는 사건도 갱신한다. 취소·완료·블록 이동·복제 시 소유권을 보존한다.
5. 개발용 전체 재계산 경로와 후보·계획·실행 가능성·선택·완료·비용을 대조한다.
   대조용 추가 계산 시간과 실제 실행 시간을 따로 보고한다.

[Timefold 공식 문서](https://docs.timefold.ai/timefold-solver/latest/constraints-and-score/performance)는
상태 차이만 반영하는 계산과 불변 정보 재사용을 설명한다. 우리 캐시에 그대로 적용됐다는 증거는 아니다.
[독립 계산 대조](https://docs.timefold.ai/timefold-solver/1.x/constraints-and-score/overview)처럼
빠른 경로와 단순 기준 경로를 비교해 누락 갱신을 찾는 방법을 채택 후보로 삼는다.
[Kaleris N4 공개 설명](https://kaleris.com/advanced-optimization/)은 실시간 작업 상태와
장비 배정을 연결한다. 내부 캐시·학습 코드가 공개된 근거는 없어 동일 알고리즘이라 주장하지 않는다.

후보 제한의 효과·누락은 [[YR-332-o]], 학습 표적·표본은 [[YR-332-p]]에서 별도로 진단한다.
이번 검토에서는 운영 코드 변경·새 성능 실험·학습을 수행하지 않았다.
