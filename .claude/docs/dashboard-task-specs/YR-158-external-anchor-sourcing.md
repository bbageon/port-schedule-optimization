## 왜 필요한가

현실성 게이트는 시뮬레이션 범위가 **문헌·공개자료 범위 안**에 있는지를 5개 지표로 대조한다.
YR-150 1단계에서 제출한 결과는 **FAIL** 이고 사유가 정확히 다섯이다.

| 지표 | 상태 | 필요한 것 |
|---|---|---|
| `gate_to_block_time` | ❌ **시뮬이 문헌 밖** (문헌 120~300초 vs 시뮬 190~410초) | 정본 결정 (아래) |
| `initial_yard_occupancy` | ❌ 미수집 | 블록 점유율 시계열 또는 공개 장치율 통계 |
| `truck_arrival_rate` | ❌ 미수집 | 게이트 시간대별 반출입 실적(VBS/게이트 로그) |
| `crane_service_time` | ❌ 미수집 | 작업 단위 서비스시간 실측 분포 |
| `vessel_workload` | ❌ 미수집 | 선석별 작업량·STS 생산성 실적 |

**미수집 4종은 값을 지어내지 않았다.** 특히 트럭 도착률은 연간 처리량(TEU/년)에서 환산하는
것이 `configs/terminals/busan/manifest.yaml` 에서 **명시적으로 금지**돼 있고, 장치율은
추적 자료에 ❓(보도 개략치)로만 있으며, 크레인 서비스시간은 시뮬 값이 그 문헌 속도에서
유도된 것이라 앵커로 쓰면 자기참조가 된다.

## 정본 결정이 필요한 충돌 — 게이트→블록 시간

저장소 안에 **두 값이 공존**한다.

- `configs/terminals/dgt_armg.yaml` 📚 문헌: **2~5분**(중앙 3.5분 = 210초).
  엔진의 `gate_travel_estimate_s: 210` 도 이 값이다.
- `scenario_gen` YR-103 사용자 계약: **3~7분**(180~420초, 중심 300초).

YR-150 배치는 후자를 앵커로 삼아 190~410초를 만들었으므로 전자의 범위를 벗어난다.
**어느 쪽이 정본인지는 사용자 결정 사항**이다. 선택지는 셋이다.

1. **문헌(210초 중심)을 정본으로** — 배치 중심을 210초로 옮기고 span 을 120~300초 안에
   맞춘다. 그러면 블록 간 주행 차이가 지금보다 **줄어든다**(이송 이득 축이 약해진다).
2. **사용자 계약(300초 중심)을 정본으로** — 문헌 범위를 넓히는 추가 출처를 확보해
   관측범위를 재정의한다. 출처 없이 범위만 넓히는 것은 금지.
3. **두 값을 다른 지표로 분리** — 문헌값은 "순주행", 계약값은 "게이트 처리 포함 총 소요"로
   정의를 나눈다. 이 경우 앵커 지표명과 시뮬 측정 대상이 같은 뜻인지 다시 맞춰야 한다.

**어느 쪽이든 YR-150 0단계 배치가 바뀌면 그 위에서 나온 결과를 다시 돌려야 한다.**
그래서 결과를 본 뒤 임의로 중심을 옮기지 않고 이 결정을 분리해 둔다.

## 무엇을 하는가

1. 위 충돌의 정본을 **사용자 결정으로** 확정하고 `strategy-history` 에 경위를 남긴다.
2. 결정에 따라 배치 또는 앵커 등록부를 고치고, 영향 받는 판정(0단계·1단계)을 재실행한다.
3. 나머지 4종은 **확보 가능한 것부터** 등록부에 추가한다. 끝내 확보 못 하면 그 사실을
   판정에 남기고 현실성 게이트는 계속 미통과로 둔다 — 통과를 위해 범위를 만들지 않는다.
