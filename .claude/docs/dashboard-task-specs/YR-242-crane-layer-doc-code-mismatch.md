## 1. 무엇이 어긋났나

설계문서 `architecture/README.md:76` 한 장 요약은 크레인 층을 **`BlockQ-v4 · 97,410`
동결 학습망**으로 그려 놨다. **v3 코드는 `BlockQ` 를 한 번도 부르지 않는다.**

```python
DISPATCHERS_READY = ("SF_SPT",)      # 이것뿐
# ROLLOUT_GREEDY · FROZEN_NET 은 부르면 NotImplementedError
```

즉 v3 의 **모든 학습·판정이 학습망이 아니라 규칙 배차 위에서** 돌았다.

**아키텍처 교차검증이 못 잡았다** — 계약 키에 배차 항목이 없다.

## 2. 규칙 배차의 실체 — 실측 (2026-08-28)

문서가 "규칙"이라 부르는 `SF_SPT` 의 정렬키는 다섯 자리다:

```python
(실작업인가, 소요시간, 본선인가, −누적대기, job_id)
```

**어느 자리가 실제로 1등을 정하는가**를 셌다 (부하 5,000 · 하루 · 재배치 없음 ·
시드 9,900,777 · SERVE 후보가 2개 이상이던 크레인-결정 **7,923건**):

| 정렬 자리 | 승부를 가른 횟수 | 비율 |
|---|---:|---:|
| 1 소요시간 | 4,877 | **61.6%** |
| **2 본선인가** | **0** | **0.0%** |
| 3 누적대기 | 384 | 4.8% |
| 4 job_id (이름순) | 2,662 | **33.6%** |

**본선·트럭이 같이 걸린 4,123건만 따로 봐도 본선 자리는 0건이다.**

그리고 이름순으로 갈린 2,662건의 정체는 **100% 본선 ↔ 본선**이었다. 이유는 코드에
있다 — `cum = sim.cum_wait(...) if ref.is_external else 0.0` 이라 **본선 작업은 누적
대기가 항상 0** 이다. 그래서 본선 후보 둘의 소요시간이 같으면 앞 네 자리가 전부
동점이 되고 **job_id 문자열 순서**로 넘어간다. 소요시간 동점은 흔하다 — 후보
47,928건이 서로 다른 값 9,909개를 나눠 쓴다(값 하나당 평균 4.8건).

### 그래서 확정된 사실 셋

1. **"본선 우선"은 명목뿐이다** — 7,923건 중 **0건**. 키에 적혀만 있고 작동하지 않는다.
2. **본선 작업끼리의 순서는 기준이 없다** — 100% 알파벳순. 전체 결정의 **33.6%**.
3. **`SF_SPT` 의 실효 거동은 "짧은 것부터, 동점이면 이름순"** 이다 — 사실상 순수 SPT.

> **정정 이력**: 이 실측 전에 두 번 말이 바뀌었다. ①처음 *"크레인은 작업 종류를 안
> 본다"* → ②코드를 보고 *"본선이 3번째 자리에서 우선된다"* 로 정정 → ③실측 결과
> **그 자리가 0% 작동**. 최종은 ③이다. 키에 있는 것과 걸리는 것은 다르다.

## 3. 영향

**① 재배치 효과를 설계가 말한 것과 다른 바닥 위에서 재고 있다.**
[[YR-185]] 실측에 *"얼린 크레인 정책이 규칙보다 비쌌다(A−R +59.97)"* 가 있어 바닥이
바뀌면 재배치 값어치도 달라질 수 있다. **단 이 수치는 v2 다** — v3 에서 미측정.

**② `06b-대조군` 의 일반성 축(배차 무관)이 아예 없다** — 판정 셀 880 중 일반성 몫
**320개를 못 돌린다**.

**③ 본선 비용 가중치가 어느 층에서도 실현되지 않는다.**
판매 층은 `vessel_slack` 이 97.5% 천장이라 본선을 못 보고([[YR-240]]), 크레인 층은
**비용을 안 읽을 뿐 아니라 본선 표시조차 0% 작동**한다. 본선이 먼저 처리되는 경우가
있다면 우선해서가 아니라 **우연히 작업이 짧아서**다.

**④ 현재 판정의 짝비교 자체는 유효하다.** 모든 팔이 같은 바닥·같은 시드를 쓰므로
이름순 33.6% 는 공통 잡음이고 부호검정을 편향시키지 않는다. **깨지는 것은 일반성
주장**이지 판정이 아니다.

## 4. 할 일

1. **계약 키 `dispatchers_ready_target` 추가** — 문서↔코드를 기계로 묶어 재발을 막는다.
2. **설계문서를 코드에 맞추거나, 코드를 설계에 맞춘다** — **어느 쪽인지 사용자 판단 필요**.
   - A. 문서 정정: 크레인 층은 규칙 배차임을 명시하고 [[YR-213]] 미구현을 적는다
   - B. 코드 보강: `JointRolloutGreedy`(계획법)를 `DISPATCHERS_READY` 에 넣는다 —
     **새로 구현할 것이 없다**. 증류 계보(규칙 → 계획법 → PPO → 채택)라 원본이 남아 있다
3. **현재 판정 결과에 한계 문장을 붙인다** — *"v3 판정은 규칙 배차 하나 위에서만
   이뤄졌다 — 배차 무관성 주장을 v3 에서는 못 세운다."*
4. **논문 비교분석 항목** (사용자 지적 2026-08-28): *"크레인 휴리스틱이 바뀔 때마다
   판매 비용이 달라진다."* 옛 3,600대 무대는 **규칙·학습망 두 바닥 위에서** 각각 재서
   2.64분/2.78분을 얻었고 그게 논문의 **배차 무관성 부 주장**이다(`01-초록` 인용).
   **v3 는 바닥이 하나뿐이라 그 주장을 못 세운다.**
