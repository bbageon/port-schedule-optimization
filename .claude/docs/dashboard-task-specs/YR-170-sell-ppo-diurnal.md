- **Epic**: Exp / **Priority**: 🔴 / **등록일**: 2026-08-11 / **상태**: in-progress
- **3대 게이트 보정 대상**: `performance` 하나 — 인가 `allowed=true`(게이트 c113f12)
- **1줄**: 견적을 더 고치지 말고 **판매 정책을 학습시켜 보고**, 안 되면 그때 디버깅한다.

## 왜 이 작업인가 (사용자 결정 2026-08-11)

> *"학습부터 해서 학습이 안 됐다가 나와야 디버깅을 하는 거 아냐?"*

그동안 0B 의 논리를 따라왔다 — **"손으로 만든 견적이 좋은 판매를 못 고르면
학습해도 안 될 테니 학습하지 말자."** 그런데 코드를 확인하니 그 전제가 틀렸다:

```
보상 = −(Φ_final − Φ(결정 시점)) + V(s_end)      # yr151_transfer_ppo.build_batch
Φ    = Σ블록 실현 v2 비용 + 주행/3600 + 기사 외부대기/3600
```

**학습기는 견적(`delta_j`)을 보상으로 쓰지 않는다** — 실현 터미널 총비용에서 배운다.
`delta_j` 는 복기용으로 전이에 join 될 뿐이다. 따라서 견적의 부정확은 학습을 막을
이유가 아니라 **학습이 할 일이 남았다는 뜻**이다.

게다가 현재 게이트가 허가한 축이 정확히 `performance` 하나이고, "판매 정책이
기준선보다 비용을 줄이는가"가 바로 그 축이다 — 학습이 인가된 다음 단계였다.

## 구현 (2026-08-11)

**무대만 바꾸고 학습 루프는 공유한다.** `train_one(episode_fn=...)` 주입 배선을
추가했다(기본값 유지 — 4차 호출부 바이트 불변).

| | 4차(고정 WIP) | **5차(24h 이중 피크)** |
|---|---|---|
| 환경 | `build_fixed_wip` + hotspot | `build_diurnal`(명단 사전 확정) |
| 투입 | `WipAdmissionController`(피드백) | `ScheduledAnnouncer`(개방 루프) |
| 관측창 | 5h | `OBS_24H` 워밍업 2h + 측정 22h + 배수 2h |
| 프로파일 | AGV 보정본(39차 감사 결함) | H-21 YT 주입 |
| 장부 가드 | 등록 = 채움 + 투입 | 등록 = 투입 = 계획 3,600 · 누락 0 |

- 집행 정책 = **채택 PPO 헤드**(C0 + 대기 허가증, 동결). 연구 질문이 "채택 실행
  위에 판매를 얹으면 비용이 더 주는가"이므로 SF 로 돌리면 다른 질문이 된다.
- **한계 명시**: YR-167 자격은 SF 집행으로 통과시켰다. 채택 헤드는 같은 환경
  계약(도착·본선·재고)을 쓰지만 실현 비용 곡선은 다르다.
- 학습 시드 8,400,000 / 8,500,000 / 8,600,000 (자격·관찰·파일럿 대역과 교집합 0).

## 지위 — 성능 주장 없음

이 작업은 **"학습이 되는가"를 보는 실행**이다. 판정(기준선 대비 개선)은 별도
사전등록으로 동결한 뒤에만 한다. 학습 곡선·판매 건수·Φ 추이는 **관측**으로 보고한다.

## 실패해도 되는 작업이다

안 되면 그 결과가 디버깅의 출발점이다. 미리 짐작해서 고치지 않는다.
관측할 것: ①구간 보상이 학습 신호가 되는가(critic 손실·advantage 분포)
②판매 건수가 학습에 따라 변하는가(전부 KEEP 로 수렴하는지 포함) ③Φ 추이.

## 하지 않는 것

- 학습 곡선을 보고 보상·환경 상수를 바꾸는 것(무대는 YR-167 동결본).
- 이 결과로 성능 주장을 하는 것 — 판정은 별도 사전등록 뒤.
- 견적(`delta_j`) 정확도를 학습의 전제로 다시 끌어들이는 것.
