# YR-223b · RUDDER 구현과 사전등록

> [[YR-223]] 본문에서 분리 (200줄 규약) · 2026-08-24
> 코드: `src/yard_rl/rudder/` · 시험: `tests/rudder/`

## 1. 구현 (2026-08-24) — `src/yard_rl/rudder/`

### ★v3 를 복제하지 않는다 (사용자 지시 "새 코드로" 에 대한 해석)

| | 왜 |
|---|---|
| v3 가 v1·v2 를 복제한 이유 | **비교 대상**이라 빌려 쓰면 비교가 오염된다 |
| rudder 가 v3 를 복제 **안 하는** 이유 | **측정 대상**이라 복제하면 사본을 재게 된다 — v3 가 바뀌어도 옛 v3 를 계속 재는 셈이라 **측정이 틀린다** |

**꾸러미는 전부 새 코드**(v3 에 한 줄도 안 더했다). v3 는 **읽기 전용 재료**로 쓴다.
계약은 시험이 지킨다 — `tests/rudder/test_no_v3_mutation.py`(정적·실행중·전역상태),
`test_runner_identity.py`(v3 `run_episode` 와 Φ·거래·결정 일치).

### 파일

| | |
|---|---|
| `tape.py` | 1분 epoch 토큰 **13칸** — 시계3·상태2·**행동4**·비용증분4(원화) |
| `runner.py` | 창 짝 굴리기 · 하루 굴리기 · **개입**(관문 F) · 스냅샷 |

| `train.py` | ★**날 단위** held-out 분할 |
| `contrib.py` | `c_t = g_t − g_{t−1}` · 보존 · 순위 상관 |
| `gates.py` · `qualify.py` | 관문 A~F(문턱 동결) · 1~4단계 구동 |

### ★비용 재측정 — 등록 시 견적이 틀렸다

등록 시 *"궤적 200개 ≈ 11분"* 이라고 적었는데 **하루 굴리는 비용을 빼먹었다.**

| 실측 (2026-08-24) | |
|---|---|
| 하루 1회 | **169초** — 순차 (review epoch 1,441회 × 21블록) |
| 창 짝 1개 (H=3시간) | 약 54초 |
| 날 16 × 창 13 = **208 궤적** | 작업자당 871초 · **8코어면 약 29분** |

11분이 아니라 **약 30분**이다. 그래도 싸다.

### 사전등록 (동결)

```
날      비판정 9,900,900~907 (8일) × 부하 3,500·5,000 = 16 작업
창      날마다 13개 · H=3시간 · 시작 시각은 결정론 등간격
정책    YR-220 최종 체크포인트 ckpt_023 (고정)
모델    LSTM 은닉 32 (약 6,000 파라미터) · 단방향 · 400 epoch
검증    ★날 단위 25% (창 단위로 가르면 겹쳐서 held-out 이 무의미)
관문    A0.5 · B+10% · C0.5 · D+10% · E10% · F70%  (필수 A·B·D·F)
```

**정책을 YR-220 체크포인트로 고정한 이유**: [[YR-222]] 가 지금 정책을 바꾸는 중이라
움직이는 과녁을 쏠 수 없다. 자격시험의 물음은 *"RUDDER 가 의미 있는 기여도를 내는가"*
이지 *"어느 정책이 좋은가"* 가 아니므로 고정된 정책이면 충분하다.


## 2. ★결과 (2026-08-25) — **사용 불가**

### 실행

```
궤적 128 (날 16 × 부하 3,500·5,000 × 창 4) · H=3시간 · 토큰 23,168
정책 YR-220 ckpt_023 고정 · 8코어 · 수집 4,214초 (70분) · 학습 10초
```

### 관문

| | 값 | 문턱 | |
|---|---|---|---|
| A 예측 | **+0.985** | 0.5 | ✅ |
| B 행동제거 | **+0.518** | 0.10 | ✅ |
| C 반복성 | +0.395 | 0.5 | ❌ |
| **D 순서섞기** | **+0.033** | 0.10 | ❌ **필수** |
| E 보존 | +0.339 | 0.10 | ❌ |

**필수 D 미달 → 사용 불가.** 규약대로 ★F 는 돌리지 않았다(배운 게 없는 순위로
개입해 봐야 잡음을 잰다).

### ★왜 D 가 미달인가 — 측정으로 확정했다

**순서를 섞어도 손실이 3.3% 밖에 안 나빠진다** = 모델이 시간 구조를 안 쓴다.
모은 궤적을 다시 굴리지 않고 읽기만 해서 원인을 확정했다:

| Y 를 무엇으로 설명하나 (순서 **없이** 총합만) | 상관 |
|---|---|
| 비용증분 4칸의 총합 | **−0.970** |
| 거래 수 | **−0.961** |
| 행동 4칸의 총합 | −0.869 |

**Y 는 "언제" 가 아니라 "얼마나 많이" 로 거의 결정된다.** 더하기만 하면 되는
문제에 시간 신용 배분을 배울 이유가 없다. 관문 D 가 정확히 이걸 잡으라고 있었고,
잡았다.

### ★관문 A 의 0.985 는 눈속임이다 — [[YR-218]] 과 **같은 함정**

| | |
|---|---|
| 검증 평균오차 | 256,406원 |
| \|Y\| 중앙값 | 128,451원 |
| **오차 ÷ 신호** | **2.00배** |
| \|Y\| 상위 10% | 8,372,287원 |

상관 0.985 는 |Y| 가 8백만원대인 한낮 창들이 끌어올린 값이다. **전형적인 창에서는
오차가 신호의 2배**라 못 쓴다. [[YR-218]] 이 "누적값이 커서 지표가 좋아 보였다" 로
실패한 것과 같은 구조다 — **상관 대신 오차÷신호를 먼저 보는 규약**이 필요하다.

### 결론

**이 무대에서 RUDDER 는 풀 문제가 없다.** 창 수준 `Y` 가 거래 총량에 거의 비례하므로
(−0.96) 시간축 재분배가 더할 정보가 없다. epoch 기여도는 그냥 "그 epoch 의 거래 수"
가 되고, 그건 모델 없이도 안다.

→ **[[YR-224]](정책 연결)은 착수하지 않는다.** 전제가 무너졌다.
→ 대신 이 측정이 드러낸 것을 따라간다 → **[[YR-225]]**.
