# YR-176 — TIME 좌표 슬롯 용량 미반영

- **Epic**: Exp / **Priority**: 🟡 / **등록일**: 2026-08-16 / **상태**: backlog
- **3대 게이트 보정 대상**: `scenario_validity` (명세 계약 위반)
- **1줄**: matching 이 `TIME@k` 에 슬롯 용량을 차감하지 않는다 — 같은 칸에 몰릴 수 있다.

## 무엇이 빠졌나

`sell_review` 의 matching 은 좌표를 확정할 때마다 가상 상태를 갱신한다:

```
if coord not in ("TIME", "KEEP") and not coord.startswith("TIME@"):
    q[coord] += 1.0            # 공간: 대기열 +1
    vcap[coord] = ... + 1      # 공간: 가상 배정 수
```

**시간 좌표는 아무것도 갱신하지 않는다.** 같은 epoch 의 여러 제안이 전부 같은 칸 `k` 를
골라도 막는 것이 없고, 두 번째 제안은 첫 번째가 그 칸을 이미 채운 것을 모른 채 값을 매긴다.

## 왜 지금 안 터졌나 (그리고 왜 고쳐야 하나)

YR-171-C 실측: 하루 시간 판매 186건이 18~20칸에 흩어져 **쌓임이 관측되지 않았다**.
그러나 이는 판매량이 적어서이지 구조가 막아서가 아니다. 판매가 늘거나 견적이
특정 칸을 선호하게 되면 그대로 드러난다.

YR-171 명세는 "복수 OFFER 는 작업 1회·**receiver/슬롯 용량**·소유권을 함께 지키며
매칭한다. 한 건 확정 뒤 **사용한 슬롯 용량을 차감**하고 남은 후보 비용을 다시 계산한다"
고 요구한다 — 현 구현은 이 계약을 지키지 않는다.

## 무엇을 하나

1. 슬롯 용량의 정의를 정한다 — 크레인 처리 가능량(`slot_plan` 특징 4) 기준이 자연스럽다.
2. 확정 시 `vcap_time[(block, slot)] += 1` 로 차감하고, 남은 후보의 견적에 반영한다.
3. 용량 초과 칸은 후보에서 제외한다(임의 pruning 이 아니라 계약상 불가능한 칸).
4. 회귀: 용량이 넉넉한 현 판매량에서는 결과가 **바뀌지 않아야** 한다(구현 검증).

## 하지 않는 것

- 결과를 보고 슬롯 용량 상한을 조정하는 것(YR-171 §하지 않는 것).
