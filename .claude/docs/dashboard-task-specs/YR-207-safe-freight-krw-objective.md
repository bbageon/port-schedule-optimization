## 법정 대기료와 연구 비용을 구분한다

고시의 청구시간은 부두운영사의 도착요청부터 상·하차와 송장 발급 완료까지이고,
첫 1시간은 청구하지 않는다. 우리 장부의 `A→O`는 실제 gate-in부터 gate-out까지다.
따라서 아래 식은 **법정 청구서 재현식이 아니라 고시에서 가져온 시간가치로 정책을
비교하는 연속 목적함수**다. 첫 1시간도 비용을 주어 짧은 턴타임 차이를 학습하게 한다.

법정 대기료 재현값은 별도 진단열로만 두고 reward·Resolver 점수에 더하지 않는다.
고시의 30분 단위 반올림 해석까지 확정하기 전에는 법정 청구액이라고 이름 붙이지 않는다.

## 새 트럭 목적함수

트럭 `j`의 진입을 `A_j`, 진출을 `O_j`, 평가 종료를 `T`라 둔다.

```text
TT_j(T) = max(0, min(O_j, T) - A_j)       # 미완료는 T에서 검열
C_truck(T) = 40,000 × Σ_j TT_j(T) / 3,600
```

완료차는 `O−A`, 미완료차는 `T−A`라서 에피소드 끝에 남아 있는 트럭이 비용을 피하지
못한다. 구현 원료는 이미 존재하는 `TimeLedger.terminal_area_s`다. 현 `block_area_s(B→C)`와
`S−B` 순수 대기는 병목 진단으로만 남기고 `C_truck`에 다시 더하지 않는다.

## 원화 환산 terminal objective

새 ID는 `TERMINAL-COST-KRW-EQ-2026-SAFE-FREIGHT-V1`로 잠근다.

```text
J_KRW_EQ = 40,000 × J_numeraire_rebased
J_numeraire_rebased의 truck_wait 원료 = terminal_area_s / 3,600
```

현 활성 상대비율을 유지하면 계수는 다음과 같다.

| 항 | 원화 환산 계수 | 근거 지위 |
|---|---:|---|
| 트럭 A→O 턴타임 | 40,000원/트럭·시간 | 2026 안전운임 대기료에서 도출 |
| 본선 지연 | 1,320,000원/본선·시간 | 현 비율 33 × 40,000, 가정 |
| YC 주행·공차 | 40,000원/장비·시간 | 현 비율 1 × 40,000, 가정 |
| 재취급 | 2,000원/회 | 현 비율 0.05 × 40,000, 가정 |

나머지 현행 0-weight 항은 0을 유지한다. 기존 `long_wait` 가산은 0으로 내려 `A→O`와
이중 부과하지 않고 꼬리 지표로만 보고한다. 즉 **트럭 항만 공식 근거가 있고 나머지는
원화 눈금으로 바꾼 상대비용**이다. 전체를 실제 터미널 회계비용이라고 주장하지 않는다.

## Seller·Buyer와 Resolver 연결

사실 세계의 `J_KRW_EQ`는 거래당 한 번만 정산한다. [[YR-204]]는 같은 목적함수로
Seller `SELL−KEEP`, Buyer `BUY−REJECT` 비용차를 만들고 두 값을 terminal total에
더하지 않는다. [[YR-205]] 운영 시 actor는 이를 예측하고 Resolver는 상호 동의 edge의
batch 조합을 같은 중앙 비용으로 비교한다.

## 구현 범위

1. 기존 numeraire v1을 덮어쓰지 않고 opt-in cost config와 YAML을 추가한다.
2. interval raw의 트럭 원료를 `block_area_s`에서 `terminal_area_s`의 구간 증가량으로 바꾼다.
3. `cost_id`·고시번호·시행일·계수·VAT 지위·source hash를 결과 header에 기록한다.
4. 원비용 13항과 `B→C`, `S→B`, 법정 대기료 참고열은 분석용으로 계속 저장한다.
5. 새 목적함수로 학습·평가한 결과는 구 상대비용 결과와 금액 크기를 직접 비교하지 않는다.

## 완료 기준

1. 단일 완료차의 A→O 0.5/1/1.5시간 비용이 20,000/40,000/60,000원이다.
2. 미완료차는 종료 `T`까지 비용이 쌓이고 `terminal_area_s` 표본합과 일치한다.
3. 같은 트럭의 `B→C`를 바꿔도 A→O가 같으면 트럭 total이 중복 증가하지 않는다.
4. 활성 4항의 손계산과 `CostBreakdown.total`이 원 단위로 일치한다.
5. 같은 factual trajectory의 terminal total은 actor 수와 무관하게 한 번만 기록된다.
6. 기존 cost config·잠금평가 골든은 바이트 불변이고 신규 테스트·설정 hash가 통과한다.
7. 3대 게이트를 다시 계산하며 성능 미통과면 목적함수 외 새 정보를 추가하지 않는다.
