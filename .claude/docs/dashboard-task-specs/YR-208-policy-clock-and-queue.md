## 왜 이게 결함인가

정보 경계는 "결정 시점에 없는 값을 읽지 마라"이다. 이 둘은 **결정 시점에 명백히
관측 가능**하다. 못 주는 게 아니라 **안 주고 있는** 것이다.

### ① 시각 — 정책에 시계가 없다

무대에 아침·저녁 **이중 피크**가 있는데 `block_features` 7개에 시각이 없다.

```
[inside/10, pipeline/10, crane_backlog/3600, occupancy,
 vessel_slack/3600, announced_30/10, n_cands/6]
```

"지금 06시라 곧 붐빈다"를 알 수 없다. 구 critic 입력에 `min(1, t/end)` 로
있었으나 [[YR-189]] Q 전환에서 critic 을 없애며 **완전히 소멸**했다.

### ② 대기 대수 — 채점과 관측의 정의가 다르다

```
정책이 보는 inside      : gate_in ≤ t < gate_out            (블록 안 전부)
보상이 쓰는 _waiting_at : block_arrival ≤ t < service_start (줄 선 것만)
```

**채점은 "줄 선 대수"로 하면서 정책에는 "총 대수"를 준다.** 같은 특징값인데
실제 상황이 다르면 라벨이 갈리고, 그것은 **"못 줄이는 잡음"으로 계측된다** —
[[YR-199]] 잡음 하한(신호의 77.6%)의 일부를 이 정의 불일치가 만들었을 수 있다.

## ★값싼 선확인 (학습 불필요 · 약 20분)

[[YR-198]] 과 같은 방법이다. 특징을 9차원으로 늘린 상태에서 [[YR-199]] 의
1-최근접이웃 잔차 하한을 **다시 재기만** 한다.

| 결과 | 뜻 | 다음 |
|---|---|---|
| 하한 0.01766 보다 내려감 | 그 정보가 **진짜 설명력**을 준다 | 학습·판정 진행 |
| 그대로 | 라벨이 원래 그만큼 무작위 | **넣지 않는다** — 축 종료 |

**학습을 돌리기 전에 기각할 수 있다.** 판정 대역을 소모하지 않는다(비판정 시드).

## 범위

| 넣는다 | 안 넣는다 |
|---|---|
| `t / sim_end` (0~1) | 이 트럭의 예상 서비스 시각 → [[YR-198]] |
| `waiting_at(block, t) / 10` | 목적지 블록 크레인 부하 → [[YR-198]] |

**`inside` 는 지우지 않고 병기**한다 — 둘의 차(총 대수 − 줄 선 대수 = 작업 중·
이동 중)도 정보다. 지우면 무엇이 효과를 냈는지 못 가른다.
