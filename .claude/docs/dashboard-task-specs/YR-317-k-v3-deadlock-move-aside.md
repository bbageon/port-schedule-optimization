# YR-317-k — 교착 수정: 실행 가능 후보 우선 가지치기

- **상태**: done (2026-09-22)
- 등록: 2026-09-21. parent: YR-317. 근거: [[YR-317-j]] 진단.
- **3대 게이트 보정 대상: `scenario_validity`**.

## ⚠️ 등록 당시 진단이 틀렸고, 9/22 에 정정했다

등록문은 *"비켜서기 행동이 없어 영구 정지한다"* 고 적었다. **틀렸다.**
9/22 고정 소스 스냅샷 재생으로 확인한 실제 원인:

- `_escape_bays`(YR-112)가 비켜설 목표 베이 {4, 5, 6}을 **실제로 계산하고**, 그 세 목표의
  예약은 **전부 승인된다**. 행동은 있다.
- 그런데 후보 가지치기(`_prune`)가 그것을 버린다. 후보 예산은 12칸이고 점수 순으로 채우는데,
  **실행 불가능한** SERVE 174건이 탈출 후보보다 점수가 높아 11칸을 먼저 가져간다.
- 예산을 200으로 늘린 기본 생성기에서는 탈출 후보 3건이 **그대로 나타난다** — 생성은 되고
  있었다. 증거: `outputs/reports/yr317_v3_stall_diagnosis/legacy-probe-21000000-Y17-b/`.
- 즉 수직형 배치(Y05/Y14)에서 이미 고쳤던 것과 **같은 결함**이다. 그때 만든 "실행 가능 후보
  우선" 가지치기를 기본 야드에 적용하지 않았을 뿐이다.

## 무엇을 했나

- 수직형 배치에만 쓰던 `FeasibleCandidateGenerator` 를 **기본 야드도 쓰는 공용 구현**으로
  올리고 이름을 `FeasibleFirstCandidateGenerator` 로 바꿨다. 옛 이름은 별칭으로 남겨
  수직형 실행기·시험이 import 를 바꾸지 않는다.
- ⚠️ **위치는 `v3/layouts/candidates.py` 다** — 처음에 `v3/world/integrated/candidates.py`
  로 옮겼다가 되돌렸다. `v3/world/` 는 v1 엔진의 **사본**이고 확장 3파일을 뺀 전부가
  바이트 동일해야 하는데(`tests/v3/test_world_clone.py`), 거기에 클래스를 덧붙이면 그
  규약이 깨진다. **전체 시험이 이것을 잡았다**(398 통과·1 실패). 파생 생성기는 사본
  바깥에 있어야 한다.
- 정렬 기준: **실행 가능 여부 → 점수 → 기존 순서키**. 예산 크기(12)는 바꾸지 않았고,
  후보를 새로 만들지도 고쳐 쓰지도 않는다 — 있는 후보 중 무엇을 남길지만 바뀐다.
- 남은 후보에 실행 가능한 것이 하나도 없으면 실행 가능한 최상위 하나를 강제로 넣는다.
- `run_month(candidate_pruning=...)` 로 **옵트인**. 기본값 `legacy` 라 기존 80건은 글자 하나
  안 바뀐 채 재현된다. 선택값은 `MonthResult.candidate_pruning` 에 기록된다.
- 학습·평가 실행기에도 같은 선택지를 배선했다: `python -m yard_rl.v3.train
  --candidate-pruning feasible_first`, 평가는 설정의 `candidate_pruning` 항목.

## ⚠️ 이 수정은 교착 전용이 아니다

시험 `test_default_reproduces_itself_and_the_fix_is_a_declared_engine_change` 가 못박는다:
같은 시드·같은 하루에서 두 모드의 비용이 **다르다**(2,819,950 vs 2,894,949원).
예산이 꽉 찬 **모든 순간**에 후보 집합이 바뀌기 때문이다.

→ 수정 엔진의 결과는 기존 80건과 **직접 비교할 수 없다**. 새 사전등록이 필요하다([[YR-318]]).
