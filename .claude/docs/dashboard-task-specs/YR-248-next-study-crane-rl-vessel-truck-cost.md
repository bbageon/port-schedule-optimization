- **선행**: YR-239 현행 연구 판정 완료

## 범위 결정

현행 연구에서 본선은 터미널 부하를 만드는 작업으로만 사용하고, 재배치 정책과 크레인
작업순서가 본선·트럭 비용을 구분해 최적화하는 문제는 다음 연구로 이관한다.

## 관측된 출발점

- 현행 크레인 작업순서는 비용을 읽는 학습 정책이 아니라 최단 처리시간 규칙이다.
- 본선 일정 여유 입력은 15,000대에서도 97.5%가 상한에 붙어 대부분 같은 값이다.
- 본선 유휴는 관측되지만 정책은 직접 원인을 구분하지 못하고 혼잡도만 간접적으로 본다.

## 후보 연구축

1. 본선 계획 완료시각과 일정 여유 범위를 실제 기항시간 범위로 다시 보정한다.
2. 막힌 본선 작업, 버퍼 수준, 대기 작업 중 본선 비율 같은 즉시 신호를 비교한다.
3. 본선과 트럭 비용 가중치를 구분해 비용을 인식하는 크레인 정책을 학습한다.

각 정보와 비용축은 한 번에 하나씩 추가하고, 수요수준별 개선과 긴 대기 악화를 따로
검증한다.

## 0단계 결과 (2026-09-06) — **실험이 필요 없었다. 대수로 증명된다.**

`slack_s` 가 왜 97.5% 상한 포화인지, 무대를 굴리지 않고 정의 셋만으로 답이 나왔다.

```
pc    = start + M·c·d        계획완료      scenario_gen.py:396
rem   = (M − done)·c         남은작업      vessel.py:57
slack = pc − t − rem                       vessel.py:64

계획대로면 t = start + f·M·c, done = f·M 이므로
    slack = M·c·(d − f − 1 + f) = M·c·(d − 1)      ← f 가 소거된다
```

**진척·시각과 무관한 상수다.** `d = 2.0` 이므로 `slack = M·c` — **그 배의 총 작업시간
전체**가 그대로 여유로 깔린다. 선급 3종의 총 작업시간이 4.4~26.2시간이라
`features/block.py:152` 의 `±2h` 클램프에 **전부 붙는다.**

| 규모(moves) | 총 작업 | slack | ±2h 클램프 후 | 정보 |
|---|---|---|---|---|
| 120 | 4.4h | 4.4h | 2.0h | 없음 |
| 360 | 13.1h | 13.1h | 2.0h | 없음 |
| 720 | 26.2h | 26.2h | 2.0h | 없음 |

### 이 칸이 실제로 재던 것

위 유도는 **계획대로 진행될 때**다. 배가 밀리면 slack 이 줄어든다 — 즉 이 칸은
*"이 배가 급한가"* 가 아니라 **"계획보다 얼마나 밀렸나"** 를 잰다. 그런데 여유가
총 작업시간만큼(100%) 깔려 있어서 **작업이 두 배로 늘어져야 0 에 닿는다.**
그 전까지는 상한 뒤에 숨는다.

### 처방 — 클램프만 넓히면 안 된다

- **클램프 확대는 오답이다.** 넓히면 그 자리에 *급함* 이 아니라 `M·c` — **배 크기
  상수**가 들어간다. 죽은 칸이 엉뚱한 칸으로 바뀔 뿐이다.
- **`vessel_deadline_mult` 2.0 → 1.15** 가 답이다. 이미 있는 프리셋
  (`scenario_gen.py:194`). `slack = M·c·0.15` 가 되어 계획보다 15%만 밀려도 신호가 산다.
  `dmult ≥ 1.0` 클램프가 있으므로 1.15 는 물리적으로 달성 가능한 범위다
  (`scenario_gen.py:70-78` — `dmult<1` 은 야드가 무한히 빨라도 불가).

⚠️ **무대가 바뀐다** — v3 판정과 비교 불가. v4 전용 변경으로 못 박고, 바꾼 뒤
**본선 유휴·Φ 구성 변화를 함께 보고**한다(지금 본선 유휴 1.96억원 = Φ의 1.21%가
얼마나 달라지는지). 이것이 [[YR-248]] 후보축 1번 *"기항시간 범위 재보정"* 의 실체다.

증명: `scripts/v4/probe_vessel_slack.py`

### 그래서 1단계 순서가 정해졌다

