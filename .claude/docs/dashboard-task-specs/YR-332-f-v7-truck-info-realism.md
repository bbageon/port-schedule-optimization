- 실측 보정 선행: 원자료 경로(사용자 보유 — 저장소에서 아직 못 찾음). [[YR-332-d]] 판정 전에 끝낸다.

## 사용자 확정 — 2026-11-10

24시간 합성곡선과 **모든 트럭 오더에 예약이 있다는 가정**으로 연구를 진행한다.
미예약·예약 누락은 이번 합성 조건에서 제외한다. 예약 존재와 정시 도착은 구분한다.
[[YR-332-ad]]에서 실제 도착곡선·수요를 고정하고 공개 예약을 별도 생성하는 계약을 먼저 구현·검증한다.
기존 σ=600초는 명시적 합성 가정이며 실측값이 아니다. 이 하위 작업은 원자료 없이 진행할 수 있다.
아래 실측 요약은 역사적 근거로 보존하며 합성 예약 채움률을 낮추는 데 사용하지 않는다.

## 실자료가 말하는 것 (사용자 제공 요약, 11/03 하루)

- 트럭 오더에서 미래 시각은 **예약 시각(`inOutReserveTime`) 하나뿐**이다. 기사가 신고한 값이지 예측이 아니다.
- 예약 시각 채움: 코피노 24,655건 중 65.3%, 방문 2,947건 중 87.9%.
- **게이트 진입이 예약보다 중앙값 93분 늦고, ±30분 안에 맞은 비율은 23.5%.**
- 유효기간 필드는 있지만 0건 채움. 블록 대기 차량 수는 실시간 값으로 있다.
- 예상 대기·도착 예정 같은 값은 없다 — 실측에서 직접 만들어야 한다.

⚠️ 위 숫자는 다른 세션의 분석 요약이다. 원자료로 다시 재서 확인한다.

## v7 지금 상태 (2026-11-10 실제 하루 경로 대조로 정정)

- 최근 K 실험은 기존 입력 9개에 STORE 여부를 더한 10개를 쓴다. 현재 후보·대기·본선 여유 중심이다.
  예정 작업 목록을 시간대별로 직접 요약하는 입력은 없다. 본선 후보도 입력 대상이다.
- 아직 안 온 트럭의 공개 예상시각은 미리 파내기·사전 위치 이동 후보와 결정 기회를 여는 데 쓴다.
  `world/integrated/candidates.py`의 `_visible_eta_of` 등에서 결정 지평 30분을 적용한다.
- 그 값의 출처가 비현실적이다.
  - 최근 하루 평가: `build_diurnal_v3`의 `arrival_s`를 공개 예약과 실제 진입에 같이 쓴다.
    `orders_from_schedule`→`V3Announcer.review`→`_job_from_entry` 경로에 예약 준수 오차 주입이 없다.
    기존 장부 9입력·78,000건의 명단 진입과 실제 진입 차이가 모두 0초였다.
    공개 예약 필드는 장부에 따로 없어 매핑은 코드로 대조했다. 주행 오차와 구분한다.
  - 기존 “약 10분·±20분” 설명은 다른 생성기의 설정을 현재 경로로 오인한 것이다.
  - 30일 무대: `net_schedule_orders` 가 **예약 시각 = 실제 도착 시각**으로 채운다.
- 정책은 공개 예상값을 읽지만 환경이 예약을 실제 진입과 같게 만든다. 현실적인 예약 오차 근거가 없다.

## 할 일

1. 예약 시각과 실제 진입 시각을 **따로** 뽑는다. 차이는 실측 분포(늦는 쪽 치우침, 긴 꼬리를 자르지 않음).
   시간대별·반입반출별로 다른지 먼저 잰다.
2. 리드타임(통지 → 진입) 표본을 DGT 1시간 71건에서 실자료로 바꾼다. 예약 오차와는 다른 축이다.
3. 실자료의 **블록 대기 차량 수** 정의가 ⑨(블록 도착 ~ 작업 시작)와 같은지 대조한다. 같으면 ⑨ 를 실측으로 검증한다.
4. 미리 파내기 후보를 여는 예정 시각은 *예약 + 평균 지각 + 주행* 처럼 **실측으로 보정한 추정치**를 쓴다.
   실현값은 여전히 읽지 않는다.
