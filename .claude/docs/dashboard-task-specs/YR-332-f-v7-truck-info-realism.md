# YR-332-f — v7 트럭 정보 현실화: 예약 시각이 너무 정확하다

- **상태**: backlog
- 상위: [[YR-332]]. 파생: v7 설계 검토(2026-11-04)와 사용자가 가져온 실자료 요약.
- 선행: 원자료 경로(사용자 보유 — 저장소에서 아직 못 찾음). [[YR-332-d]] 판정 전에 끝낸다.

## 실자료가 말하는 것 (사용자 제공 요약, 11/03 하루)

- 트럭 오더에서 미래 시각은 **예약 시각(`inOutReserveTime`) 하나뿐**이다. 기사가 신고한 값이지 예측이 아니다.
- 예약 시각 채움: 코피노 24,655건 중 65.3%, 방문 2,947건 중 87.9%.
- **게이트 진입이 예약보다 중앙값 93분 늦고, ±30분 안에 맞은 비율은 23.5%.**
- 유효기간 필드는 있지만 0건 채움. 블록 대기 차량 수는 실시간 값으로 있다.
- 예상 대기·도착 예정 같은 값은 없다 — 실측에서 직접 만들어야 한다.

⚠️ 위 숫자는 다른 세션의 분석 요약이다. 원자료로 다시 재서 확인한다.

## v7 지금 상태 (코드 확인)

- 크레인 입력 9칸은 전부 **이미 블록에 도착한 트럭**만 본다 — 실자료 범위와 맞다.
- 아직 안 온 트럭 정보는 **미리 파내기 후보**를 열 때만 쓴다(`world/integrated/candidates.py` 의
  `_visible_eta_of` — 결정 지평 30분 안).
- 그 값의 출처가 비현실적이다.
  - 하루 무대 생성기: 실제 진입 = 예약 + 준수 오차(σ 약 10분, ±2σ 에서 자름) — 20분 넘게 틀리지 않는다.
  - 30일 무대: `net_schedule_orders` 가 **예약 시각 = 실제 도착 시각**으로 채운다.
- 누출은 아니다(실현값을 정책이 직접 읽지 않음). 다만 정책이 실제보다 훨씬 좋은 정보로 연습한다.

## 할 일

1. 예약 시각과 실제 진입 시각을 **따로** 뽑는다. 차이는 실측 분포(늦는 쪽 치우침, 긴 꼬리를 자르지 않음).
   시간대별·반입반출별로 다른지 먼저 잰다.
2. 리드타임(통지 → 진입) 표본을 DGT 1시간 71건에서 실자료로 바꾼다. 예약 오차와는 다른 축이다.
3. 실자료의 **블록 대기 차량 수** 정의가 ⑨(블록 도착 ~ 작업 시작)와 같은지 대조한다. 같으면 ⑨ 를 실측으로 검증한다.
4. 미리 파내기 후보를 여는 예정 시각은 *예약 + 평균 지각 + 주행* 처럼 **실측으로 보정한 추정치**를 쓴다.
   실현값은 여전히 읽지 않는다.

## 범위 밖

크레인 입력 칸을 늘리지 않는다. 예약 시각은 *언제쯤 오겠다는 신고값* 으로만 쓴다
(연구 원칙: 핵심 정보로 학습이 되는지 먼저 확인).
