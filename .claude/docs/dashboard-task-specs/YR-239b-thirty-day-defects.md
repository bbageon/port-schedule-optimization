# YR-239b · 30일이 잡아낸 결함 여섯

> [[YR-239]] 본문에서 분리 (200줄 규약) · 실측 2026-08-26
> 넷 다 **하루 무대가 구조적으로 못 보던 것**이다 — 매일 아침 리셋되기 때문이다.

## 결함 첫째 — 배가 **내리기만** 했다 (`stage/vessels.py`)

30일 무대를 처음 돌리자 1일차 Φ 가 17.8M → **138.9M원**(7.8배)으로 튀고 트럭
499대 중 **159대(32%)가 자정까지 못 나갔다.** 야드를 재 보니 하루에
**19,656 → 24,828상자 (+26%)** 로 부풀고 있었다.

원인은 `stage/vessels.py::plan_streams` 한 줄이었다:

```python
"work": "DISCHARGE" if (len(rows) + k) % 2 == 0 else "LOAD"   # 옛 코드
```

`len(rows)` 와 `k` 가 **함께 1씩** 늘어 합이 **늘 짝수**다 — 전 스트림이 양하.
상자가 들어오기만 하고 나가지 않는다.

| | |
|---|---|
| **왜 안 드러났나** | 하루 무대는 이 칸을 **안 읽는다** — 같은 행의 `type_offset`(`k % 2`)으로 배를 세운다 |
| **과거 결과 영향** | **없다.** 하루 무대 실측: 하루 끝 미완 job **0/6,008** · 야드 19,656 → 19,558(**−98**) |
| **고침** | `"DISCHARGE" if k % 2 == 0 else "LOAD"` — 실측 순증 **정확히 0** |

### 결함 둘째 — 배를 **너무 일찍** 치웠다 (정리 순서)

첫째를 고쳐도 남은 job 이 131 → 445 → 642 → **1,566** 으로 늘고 Φ 가 1,568만 →
**5,812만원**, 하루 소요가 72초 → **325초** 로 불었다.

원인은 `retire_done_vessels` 의 조건이 `v.done` **하나뿐**이었다는 것이다.
양하 job 은 시각이 아니라 **박스의 물리 도착**이 푼다
(`engine._release_next_discharge` — 이송이 닿을 때마다 한 건씩). STS 는 이송보다
훨씬 빠르므로 `done` 시점에 **안 풀린 job 이 수백 건** 남아 있고, 그때 배를 치우면
`_transfer_arrive` 가 그 배를 못 찾아 **그 job 들이 영원히 PLANNED 로 남는다.**

고침 — 조건 셋을 **모두** 넘어야 치운다:
`① v.done` · `② 그 배 앞으로 남은 job 0` · `③ 끝난 지 1시간 경과`.
그리고 하루를 닫을 때 **`prune_completed` 를 먼저** 부른다(②가 참이 되게).
재발 방지: `test_a_finished_vessel_with_jobs_left_is_not_retired` 외 3건.

### 결함 셋째 — 반출 대상이 **날마다 겹쳤다** (`V3Announcer.retarget`)

컨테이너 이름은 블록마다 `C0001…C0936` 이라 **날마다 같은 이름이 다시 나온다.**
5일차 트럭이 찍은 `C0123` 을 2일차 트럭이 이미 가져갔으면 `admit_external_job` 이
"반출 대상 부재" 로 거절하고 **트럭이 조용히 사라진다**(부하가 저절로 줄어든다 —
실측 300대 중 288대만 투입). 같은 이유로 본선 적하 대상도 트럭에게 빼앗긴다.

고침 — 반출 대상을 **투입 시각에** 다시 고른다(`make_retarget`): ①명단이 찍은 상자가
아직 있고 아무도 안 찍었으면 그대로 · ②아니면 그 블록에서 아무도 안 찍은 상자 ·
③그것도 없으면 `NO_TARGET` 으로 남긴다. 난수는 **오더 이름에서만** 나온다 —
분기 세계가 같은 상자를 골라야 라벨이 안 오염된다. 결과 **300/300 투입**.

### 결함 넷째 — **블록이 차서 양하가 멈췄다** (용량·수지)

앞의 셋을 고쳐도 남은 일감이 93 → 393 → 570 으로 늘었다. 블록별로 재 보니 원인이 바로 나왔다:

```
[1일차 끝] 용량 1,440/블록
  Y19: 상자 1,323 · 빈슬롯 116 · 막힌 양하 39      ← 92% 차 있다
  Y04: 상자 1,331 · 빈슬롯 109 · 막힌 양하 31
  Y01: 상자   528 · 빈슬롯 912 · 막힌 양하  0      ← 빈 블록은 0 건
```

양하 스트림 하나가 그 블록에 **하루 386상자**를 쌓는다. 초기 장치율 0.65 면
936 → 1,322(92%) 가 되고, **그 블록이 이튿날도 양하면 슬롯이 없어 멈춘다.**
`plan_streams` 의 배정(스트림 번호 홀짝)은 **하루 안에서만** 균형이라 30일에는 한 블록이
사흘 내리 양하를 맡을 수 있다.

고침 둘:
- **블록별 수지 배정** — `plan_month_vessels` 가 *"덜 찬 블록은 내리고, 찬 블록은 싣는다"*
  로 다시 정한다. 수지는 **계획에서만** 계산하므로 정책과 무관하고 시드가 같으면 같다.
  실측: 블록 순증이 **스트림 하나 크기(±660)** 안에 묶인다(무작위 걸음이면 √30배로 발산).
- **초기 장치율 0.65 → `MONTH_FILL_RATIO = 0.45`** (648상자) — 양하 하루 뒤가 1,034(72%).

### 결함 다섯째 — **야드가 하루 1,000상자씩 말랐다** (트럭 수지)

넷을 고치고 부하 5,000 으로 4일을 돌리자 야드가 12,366 → **11,019** 로 내려갔다.
명단을 세어 보니 원인이 명확했다:

```
gate_out_share = 0.6      반입 1,982 · 반출 3,018  =  하루 **−1,036상자**
30일이면 −30,000 인데 야드는 12,000상자다  →  12일이면 텅 빈다
```

하루 무대는 아침마다 리셋되므로 −1,000 이 초기 적재의 5% 로 묻혔다.

**현실은 이 구멍을 본선 양하가 메운다** — 수입 화물이 배에서 내려 트럭으로 나간다.
그래서 배의 양하/적하 목표를 **0 이 아니라 트럭 수지**에 맞춘다
(`truck_net_by_block` → `plan_month_vessels(truck_net=...)`).

계획 기준 실측(30일): 야드 총량이 15,244 → 11,662 사이에서 **오르내리고**
(최저 10,122 · 최고 16,104) 블록 최대 점유는 **86%** 로 멈춤 문턱(92%) 아래다.

### ★결함 여섯째 — **분기 세계가 탐색을 안 했다** (ε 불일치 · 가장 심각)

학습 4일치 로그에서 **라벨의 92.7% 가 "정답 0"** 이었다 — 55건 중 51건이
*"반대로 했어도 3시간 뒤 비용이 원 단위까지 같다"*. 파고들어 보니:

```python
# month_run.py open_teacher() — 이미 만들어진 "본 세계" 시장 객체에만 걸었다
for who in (market.seller, market.buyer):
    who.explore = eps                    # 0.50

# episode.py _Ctx.make_market() — 분기 세계는 ctx 에서 **새로** 만든다
seller = Seller(net, layout, explore=self.explore, ...)   # ← ctx.explore = 0.00
```

`ctx.explore` 는 `run_month(explore=0.0)` 로 만들어진 뒤 **한 번도 안 바뀌었다.**

| | 본 세계 | 분기 세계 |
|---|---|---|
| ε | 0.50 | **0.00** |
| 거래 | 하루 487건 | **3시간 1건** (비례 60건) |

**"사실" 가지가 사실을 재현하지 못했다.** 두 갈래가 다 "아무 일 없는 세계" 라
강제한 오더 하나 말고는 똑같아졌다.

⚠️ **탐색을 켜도 분기는 안 늘어난다** — 분기의 다리는 `on_decision=None`(교사 재귀
금지)이라 `pool.submit` 이 한 번도 안 불린다. 그리고 난수가 좌표 해시
(`actors/explore.py`)라 같은 오더·같은 시각이면 본 세계든 분기든 **같은 동전 결과**
가 나온다 — 탐색을 켠 채로 재현하라고 만든 장치다.

**함께 드러난 것**: 동일성 불변식(`identity_checks`)이 **학습 경로 전체에서 꺼져
있었다**(하루 무대 `loop.py:196` 도 0). 켜져 있었으면 첫 회차에 잡혔다.
세계를 더 쓰지 않으므로(이미 굴린 사실 가지를 대조만 한다) 켜는 비용이 없다.

**고침** — `ctx.explore = eps` 한 줄 + `identity_checks=4` 기본값.
실측(부하 3,000 · 라벨 40 · ε0.50):

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 정답이 0인 비율 | **97%** | **62%** |
| 실질 신호 | 34건 중 1건 | 34건 중 **13건** |
| 동일성 검사 | 꺼짐 | **통과 4 · 실패 0** |

**영향**: 30일 학습 4일치는 **무효**. 판정 경로는 분기를 안 쓰므로 무관하고
(`eval/run.py` 가 `budget` 을 안 넘김 + 하드가드 `rollout_calls_during_eval == 0`),
하루 무대 학습은 `run_episode(explore=eps)` 가 ctx 로 넘기므로 이 버그가 없다.

## ★범위 결정 — 본선은 **부하 생성용**이다 (사용자 지시 2026-08-28)

> *"트럭 본선은 지금 이번 연구에서는 구분을 하지않고 부하를 위해 구현만해놓고,
> 다음 연구에서 적용할 예정이야"*

| | 이번 연구 | 다음 연구 |
|---|---|---|
| 본선의 역할 | **부하를 만드는 배경** — 야드 작업의 **38%**(30일 12.8만 상자) | 트럭과 구분해 다룸 |
| `vessel_slack` 죽은 칸 (A11) | **범위 밖 — 안 고친다** | 여기서 살린다 |
| 본선 비용 항4 (2.99원/GT·h) | 부하 모형의 일부 | 재정의 대상 |

**⚠️ 논문 한계**: *"본선은 부하를 만드는 배경이고, 정책이 본선을 구분해 다루는지는
이 연구의 판정 대상이 아니다."* — 없으면 *"왜 배를 안 봤나"* 에 답할 수 없다.

**★비용 가중치가 어디에 작동하나 — 한 층뿐이다**

| 층 | 비용을 읽나 | 본선을 우선하나 |
|---|---|---|
| **크레인 배정** (`SF_SPT` 규칙 · 동결) | ❌ **안 읽는다** — `(SERVE 우선, 최단시간)` 만 본다 | ❌ |
| **재배치** (학습 중) | ✅ Φ 네 항으로 배운다 | ❌ 직접 신호가 죽어 있다 |

비용을 읽는 배차(`ROLLOUT_GREEDY`·`FROZEN_NET`)는 **미구현**이다([[YR-213]]) —
`DISPATCHERS_READY = ("SF_SPT",)`. ⇒ **선급을 3종으로 가른 설계 의도**
(*"어느 배를 먼저 먹일까"* · 04 §1-2)가 **어느 층에서도 실현되지 않는다.**
연구적으로는 오히려 깨끗하다 — 크레인이 동결이라 **재배치 층의 효과만** 잰다.

**관측된 사실 — 다음 연구의 출발점** ([[YR-240]] 에 상세)
본선 유휴는 30일 내내 있었고(최악 53시간/일 · 합계 1.96억원 = Φ의 1.21%), 정책은
본선을 **직접은 못 보지만**(`vessel_slack` 100% 천장) **간접으로는 본다**
(`_crane_backlog_s`·`_occupancy` 가 작업 종류를 안 가린다).
⇒ 정책은 *"이 블록이 바쁘다"* 는 알지만 *"왜 바쁜지"* 는 모른다.
