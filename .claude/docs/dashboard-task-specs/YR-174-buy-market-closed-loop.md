# YR-174 — BUY 견적망 + 폐쇄형 학습 구조 (43차 설계안 이행)

- **Epic**: Exp / **Priority**: 🔴 / **등록일**: 2026-08-14 / **상태**: done
- **3대 게이트 보정 대상**: `performance` 하나 (인가 allowed=true·c113f12).
  단 **정보 계약이 바뀌면**(24시간 공개) `scenario_validity` 재자격이 선행 — YR-171-A.
- **1줄**: BUY 견적망이 수신 부담을 예측하고, Resolver 가 손해 거래를 집행 전에 막고,
  거래 후 **실제 손익을 판매한 블록에만** 돌려주는 폐쇄 고리를 만든다.

## 왜 — 지금까지 확인된 것

| 확인 사항 | 근거 |
|---|---|
| 전역 보상은 **행동 신호가 0.0004%** | YR-170 진단 |
| 블록별 로컬 보상은 **떠넘기기 구조** | 판 블록 +5.8분 / 받은 블록 −7.5분 |
| 정책 선택지 3개 vs resolver 선택지 960개 | 결과를 좌우하는 결정을 **사람 규칙이 함** |
| 시간 판매는 현 계약에서 1건당 **+14.28분 손해** | 축 분리 진단 |

→ 표준 해법은 **차이 보상**(difference reward)이다. "내가 있을 때 − 없을 때"를 빼면
**시각 잡음이 구조적으로 상쇄**된다. QMIX(가치 분해)는 없는 정보를 만들지 못하므로
잡음이 신호의 2,600배인 지금 상황에는 부적합하고, PPO 를 버려야 하는 비용도 크다.

## 구조 (43차 설계안)

```
공통 24시간 계획
  → 각 source 의 판매 가능 작업 목록 (아직 판매 아님)
  → BUY 견적망: 작업별 20블록 × 48슬롯 부담 예측
  → 작업별 시장요약(최대 이득·2위·차이·최적 시각·불확실성·후보 수)
  → Source SELL PPO: KEEP 또는 작업 1건 OFFER
  → 중앙 Resolver: 전체 OFFER 공동 matching, KEEP 보다 이득일 때만 집행
  → 동결 ExecutionHead 로 실제 운영
  → 거래별 실제 손익 → 그 source PPO 에만 보상
```

### 역할 분리 (섞으면 안 됨)

| 구성 | 역할 | 학습 |
|---|---|---|
| **BUY 견적망** | 수신 부담 예측(수신 블록 **내부만**) | 지도학습 → 이후 **동결** |
| **SELL PPO** | 어떤 작업을 OFFER 할지 | **학습 대상** |
| **Resolver** | 어디로·언제 배정할지 | 결정론 |
| **ExecutionHead** | 크레인 실행 | 동결 |

**BUY 예측값을 SELL 보상으로 그대로 쓰면 안 된다** — 견적이 틀리면 정책도 똑같이
잘못 배운다. 보상은 **실제 실현 손익**이어야 한다.

## 보상 (핵심)

```
D_i = C(source i 만 KEEP 한 세계) − C(실제 거래 세계)
```

최소 구현판:
```
D̃_i = R^real_source − B^real_receiver − ΔC^real_route − ΔC^real_driver
```
- 양수 = 터미널 비용을 줄임 → 양의 보상 / 음수 = 떠넘김 → 음의 보상
- 거래 거절 = 실제 상태가 KEEP 과 같으므로 **보상 0**
- **불확실성 여유는 실제 보상에 다시 넣지 않는다**(예측 안전마진이므로)
- 여러 source 가 동시에 팔았으면 **하나를 KEEP 으로 바꾼 반사실에서 matching 을 다시**
  계산한다 — 그 source 가 빠지며 다른 작업이 빈 슬롯을 쓰는 효과까지 반영해야 한다

### PPO 갱신
```
A_i = D_i / 비용스케일 − V_ψ(S, i)
```
- **Actor**: 실행 시 자기 블록 정보 + BUY 시장요약만 봄
- **Critic**: 학습 시 전체 OFFER·BUY 견적·Resolver 결과를 봄(중앙 critic)
- BUY 망까지 PPO 보상으로 함께 바꾸면 정책이 BUY 망 오류를 악용하므로 **금지**

### 판매 문턱은 학습으로
"이득 1.0 이상일 때 판매" 같은 임의 상수를 두지 않는다. KEEP 가치 = 0 이고,
실제 순이득이 음수인 거래가 반복되면 정책이 스스로 "예상 +1.0 로는 부족하다"를 배운다.

## ★ 44차 피드백 반영 (2026-08-14 — 학습 중단하고 보상 정정)

피드백: "본선 LOAD·UNLOAD 작업은 실제 위치가 선박과 야드에 묶여 있으므로 **판매 대상에
넣으면 안 된다**. 다만 **트럭 수용이 본선에 미치는 간접비용은 BUY 견적에 반드시
포함해야 한다**."

확인한 것: 견적식 `cost_given_queue` 는 `j_truck(...)` 만 돌려주고, 내가 쓴
`realized_credit` 도 마찬가지로 본선 항이 없었다. 본선 지연은 비용식에서 **10배 가중**
(`RHO_VESSEL_V2 = 10.0`)이라, 빠지면 **받는 쪽 부담을 크게 과소평가**한다.

정정 2건 (`yr174_txn_reward.py`):

1. **본선 압력 항 추가** — `_vessel_pressure(sim, t, occupy_s)`: 그 시각 그 블록에
   대기 중인 본선 연계 작업이 있고 그 블록 적하 본선이 실제로 마감을 넘겼다면,
   크레인을 트럭에 쓴 시간만큼 본선이 밀린 것으로 본다(10배 가중). 본선은 한 줄기라
   대기 작업 수를 곱하지 않는다. 마감 여유가 남아 끝난 본선은 비용 0 이므로 세지 않는다.
   **판 쪽(`R_src`)·받은 쪽(`B_dst`) 양쪽에 같은 식으로** 넣는다(대칭성 원칙).
2. **시간 이연의 부담 항 추가** — 기존 식은 "원래 시각의 혼잡 완화 − 기사 외부 대기"
   뿐이라, **미룬 시각에 그 트럭이 실제로 와서 만드는 혼잡**이 빠져 있었다. 이연이
   구조적으로 항상 이득으로 보이는 편향이다(혼잡을 옮겼을 뿐인데도). 1번 항을 넣으면
   그 편향이 10배로 커지므로 같이 고쳤다.

한계(명시): `_vessel_pressure` 는 근사다 — 정확히는 그 점유가 없었을 때의 본선 완료
시각을 알아야 하는데 한 번의 실행에서는 미관측이다. 양쪽에 같은 근사를 쓰므로
**차이(D_i)에서는 계통 오차가 상쇄**되는 것을 노린다.
