# YR-171 — **24시간 공통창 BUY 견적 + 블록×시간 최적화** (YR-161 대체)

- **Epic**: Exp / **Priority**: 🔴 / **등록일**: 2026-08-13 / **상태**: done
- **3대 게이트 보정 대상**: 171-A=`scenario_validity`, 171-B/C=`performance` — 정보계약과
  견적 메커니즘을 한 판정에 섞지 않는다.
- **1줄**: source는 작업만 OFFER하고, receiver는 같은 24시간 공개계획에서 수용 전후 비용을
  계산하며, Resolver가 **수신 블록×30분 슬롯** 중 터미널 비용이 가장 낮은 안을 고른다.
- **구현 지위**: **설계 확정·코드 미완**. 현행 고정 `+15분` 좌표와 수기 receiver 견적을
  이 목표가 이미 구현된 것으로 해석하지 않는다.

### 왜 구조적으로 손해인가

비용 계약상 **기사의 터미널 밖 대기가 안 대기와 같은 단가**로 계상된다
(`yr151_transfer_ppo.py:196`). 따라서 +15분 이연의 손익은

```
순이득 = (터미널 안 대기 절약분) − 15분
```

**절약분이 15분을 넘을 때만 이득**이고, 그건 혼잡 첨두를 정확히 비껴갈 때만
생긴다. 그런데 **고정 +15분은 고를 수가 없다** — 15분 뒤가 더 붐비면 그냥 손해다.
실측 +14.28분/건은 이 구조가 그대로 나타난 값이다.

| 구분 | 현재 | 변경 |

### 역할과 계산 순서

1. **공통 동결 스냅샷**: 모든 source·receiver·Resolver가 같은 기준시각, 같은 작업일
   24시간 공개 예약·ETA·본선계획, 같은 `plan_version`을 쓴다. 미래 실현값은 금지한다.
2. **source TransferHead**: `KEEP` 또는 작업 1건 `OFFER`만 고른다. 목적지와 시간은 고르지
   않는다. source 절감은 `J_source(유지) − J_source(제거)`로 계산한다.
3. **receiver BUY 견적 모드**: 별도 BUY 정책을 학습하지 않는다. 각 허용 슬롯에 작업을
   가상 삽입한 계획 복사본에서 **동결 ExecutionHead**를 실행하고 다음을 반환한다.

   ```text
   BUY부담(B,t) = J_B(t에 수용) − J_B(수용 안 함)
   ```

   `J_B`는 트럭 대기·본선 지연·크레인 이동을 같은 v2 비용단위로 합친 예상값이다.
4. **TransferResolver**: 가능한 `(receiver B, slot t)`를 한 저울에 올린다.

   ```text
   총 추가비용(B,t)
     = BUY부담(B,t) + 추가주행 + 기사 시간변경 + 불확실성 − source 절감
   ```

   가장 작은 안이 `KEEP=0`보다 쌀 때만 선택한다. 전부 0 이상이면 거래하지 않는다.
5. **일괄 matching**: 복수 OFFER는 작업 1회·receiver/슬롯 용량·소유권을 함께 지키며
   매칭한다. 한 건 확정 뒤 사용한 슬롯 용량을 차감하고 남은 후보 비용을 다시 계산한다.
6. **실제 집행**: BUY 견적은 미래 순서를 확정하는 예약이 아니다. 실제 도착 때 ExecutionHead가
   최신 상태에서 실행순서를 다시 고른다. ETA·본선계획·용량 version이 바뀌면 견적은 만료된다.

### 정보 입력 범위

- receiver의 가상 계획에는 예약 트럭 수·공개 ETA·크레인 처리 가능량·본선 작업계획·밀린
  작업·이미 옮겨진 수를 넣는다.
- source actor에는 3,600건 원자료를 직접 넣지 않고, 같은 24시간 스냅샷에서 만든 시간대별
  예상 혼잡곡선·본선여유처럼 압축한 공개 정보만 준다.
- Resolver만 24시간을 보고 블록은 30분만 보는 비대칭, 또는 서로 다른 version 견적을 한
  번의 matching에 섞는 것을 하드 실패로 처리한다.
- 20 receiver×48슬롯 가상 실행의 계산시간을 반드시 계측한다. 결과를 보지 않은 결정론적
  후보축소 없이 임의 pruning하여 최적 슬롯을 누락하지 않는다.

근거: 부산항 체인포털 VBS 가 적용시간 00~24시·슬롯 30분/1시간·예약 변경 가능시간과
마감시간 분리 구조를 쓴다. 하루 단위 가시성·슬롯 용량·임박 잠금은 실제 구조와 정합.

## 반드시 붙일 단서

- **예약 최적화 ≠ 재예약**: 최초 예약 전 추천은 최적화, 확정된 시간 변경은 재예약이며
  **기사 동의가 필요**하다. 현 시뮬레이션은 **전원 수락**을 가정하므로 결과는 실제 운영
  성과가 아니라 **"모두 수락할 때의 최대 가능 효과"**로만 읽는다.
- 이 변경은 **정보 계약을 바꾼다**(30분 전 공개 → 하루 명단 공개) → YR-167 자격이
  무효가 되므로 **재자격이 선행**이다. 상수 하나 교체가 아니다.
- 기존 연구의 입찰 구조는 조직적 근거일 뿐, **ExecutionHead 가상 실행 기반 BUY 견적의
  성능은 우리 실험에서 새로 증명해야 한다**. 이를 기존 연구가 검증한 정책으로 쓰지 않는다.

## 단일축 사다리

1. **171-A 정보계약**: 같은 작업일 24시간 공개 스냅샷·48슬롯·version/만료만 구현하고
   미래정보 누출·시나리오 현실성을 재자격한다. 성능 주장은 금지한다.
2. **171-B BUY 견적 shadow**: 소유권을 바꾸지 않고 동결 ExecutionHead의 수용 전/후 비용,
   결정론·가법성·실현 부담과의 방향성을 검증한다. 기존 수기 견적과 섞어 학습하지 않는다.
3. **171-C Resolver matching**: B를 통과한 견적만 블록×시간 공동선택에 연결한다. KEEP,
   현행 수기 견적, 새 정책기반 견적은 같은 미열람 시드에서 분리 비교한다.

각 단계는 앞 단계 evidence 뒤 별도 동결한다. 24시간 창과 BUY 견적과 matching을 한 번에
바꾼 성능 결과로 원인을 주장하지 않는다.
