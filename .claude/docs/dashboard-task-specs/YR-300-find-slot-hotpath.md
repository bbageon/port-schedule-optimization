# YR-300 — 시뮬레이터 핫패스 최적화 (`find_slot`)

- **상태**: 🟢 진행 중 · 2026-09-07 (사용자 지시 *"①+② 이렇게 하는데"* · *"v4 에 적용해야"* · *"가지치기만 일단 하자"*)
- **분류**: Infra
- **세대**: **v4 전용** ([[YR-297]] 경계 — v3 는 논문 코드라 손대지 않는다)

## 왜

30일 학습이 18시간, 판정 한 팔이 4~6시간 걸린다. *"신경망이 CPU 라 느린가"* 를 재 보니
**망은 전체의 0.03%** 였다(결정 20만 회 × 24µs = 5초 / 전체 249분). 병목은 다른 데 있었다.

프로파일(2일치·cProfile 925초):

```
find_slot        2,797,412회 · 자체 215초 · 누적 775초 = 84%
  ├ stack()      1,203,914,783회   ← 12억 회
  ├ top_tier       669,077,624회
  └ stack_size_ok  533,255,693회
gantry_m/trolley_m 각 299,417,796회
```

`find_slot` 이 280만 번 불리는데 **매번 야드 스택 240개를 전부 훑고**, 칸마다
`top_tier()`·`stack_size_ok()` 를 부르면 그 안에서 `stack()` 이 또 불린다 —
호출 1회당 `stack()` 430회.

## 무엇을 했나 — 계산식은 한 글자도 안 바꿨다

| | 무엇 | 효과 |
|---|---|---|
| ① | 칸마다 `_stacks` 를 **한 번만** 꺼내 top·규격 양쪽에 쓴다 | 12억 → 2.8억 |
| ② | `gantry` 는 bay 에만 의존 → **row 루프 밖**으로 (10분의 1) | 3억 → 0.3억 |
| ③ | `geom` 속성·딕셔너리를 지역변수로 (frozen dataclass 라 안전) | 속성 접근 제거 |
| ④ | **가까운 bay 부터 보다가 거리 하한이 최선을 넘으면 중단** | 240칸 → 41.7칸 |

**④ 의 정당성**: 비용 = `g + trolley + top·tier_h` 인데 **뒤 두 항이 항상 0 이상**이라
`g` 가 그 bay 의 비용 하한이다. 하한이 이미 찾은 최선보다 크면 그 bay 도, 더 먼 bay 도
최선을 못 넘는다. 잘리는 후보는 비용이 **엄격히** 크므로 사전식 tie-break 와 무관하다.
⚠️ **비용식에 음수 항이 추가되면 이 논리가 깨진다** — 코드 주석에 계약으로 못 박았다.

**부동소수**: 피연산자·결합순서를 안 바꿨다(`(A+B)+C` 유지). 비트 단위로 같다.

## 검증 — 다섯 겹

1. **워크플로 감사** (분석 3갈래 + 각각 반증 검증 · 에이전트 6): 코드 대조 · 독립 퍼즈
   2만 회 · 실제 패치로 시험 549 passed. *"결과를 바꾸는 경로를 찾지 못했다"*
2. **동등성 시험** `tests/v4/test_find_slot_equiv.py` 9건 — 인라인 사본이
   `stack_size_ok`·`top_tier` 와 같은 판정을 내는지 적재율 5수준에서 전 칸 대조
3. **v3 원본 vs v4 최적화 직접 대조** `scripts/v4/verify_find_slot.py`
   — 적재율 7수준 × 3,000회 = **21,000 호출 · 불일치 0건**
4. **★동률 강제 대조** — ④ 가 순회 순서를 바꾸므로 여기가 유일한 위험 지점이었다.
   크레인을 bay 중간(정수+0.5)에 세워 좌우 bay 를 **정확히 동거리**로 만든 뒤 3,600회
   대조 — **불일치 0건**
5. **엔진 전체 동등성** `tests/v4/test_world_equivalence.py` — 원본 트리와 같은 하루

## 효과

```
find_slot 자체   3.04초 → 0.29초 (2만 호출)   **10.3배**
  적재율 15%     16.2배 · 45% 9.9배 · 75% 7.4배
전체 기대        find_slot 이 84% 이므로 약 4배
```

**연구 속도가 4배**가 된다: 30일 학습 18시간 → 약 4.5시간, 판정 한 팔 4~6시간 → 1~1.5시간.

부수 효과: [[YR-299]] B(반사실 창 3→6시간)를 막던 *"계산이 2배 든다"* 가 사라진다
(6시간 창 학습 36시간 → 9시간).

**운영 속도는 원래부터 충분했다** — `find_slot` 은 운영 경로에 없다. 운영 1회 결정은
**33마이크로초**(제안망 29후보 채점 + argmin + 수락망 + 비교, 단일 코어). 결정 주기
60초 대비 여유 180만 배. 논문의 *"운영 추론 분리"* 주장을 뒷받침하는 수치다.

## ⚠️ 남긴 부채

`stack_size_ok` 의 적재 규칙이 **두 곳**에 있게 됐다(원본 메서드 + `find_slot` 인라인).
나중에 reefer·위험물·중량 규칙이 붙으면 인라인 사본이 조용히 뒤처지고, 신규 적재(STORE)
경로에는 후조건 가드가 없어 **틀린 슬롯이 그대로 나간다**. `test_find_slot_equiv.py` 가
두 구현의 일치를 지킨다 — 규칙이 갈리면 그 시험이 먼저 깨진다.

## 안 한 것 — 결과 캐시 (사용자 결정 *"가지치기만 일단 하자"*)

워크플로가 실측까지 마친 후보가 하나 더 있다: **`find_slot` 결과를 기억해 두고 야드가
바뀔 때만 버리기.** 호출의 **72%가 같은 야드 상태의 중복**이라(야드는 `place`/`remove`
때만 바뀌는데 그 사이 계획·검증 경로가 같은 계산을 6~16회 반복) 3.3배까지 간다.
그림자 대조 84.7만 회 불일치 0 · 캐시 최대 300개.

**보류 사유**: 상태가 하나 늘어난다. 지금은 야드가 유일한 진실인데 캐시가 생기면
*"야드"* 와 *"야드에 대한 기억"* 둘이 되고, 나중에 야드를 바꾸는 세 번째 경로가 생기면서
캐시 비우기를 잊으면 **오류 없이 조용히 옛 답**이 나온다. 넣는다면 *"야드를 바꾸면
반드시 캐시를 비운다"* 를 강제하는 시험을 함께 둘 것.
