# 05 — 정보 경계 (v3 설계 · 축 ④)

> **성격**: to-be 설계. 코드가 여기에 맞춰진다. → [index](README.md)
> **관련 코드**: `integrated/time_sell.py`(`notified_gate_in`) · `v2/features.py`(현행 세대 특징) ·
> `sell_gain.py`(규칙) · `buy_estimator.py`

**v3 에서 경계 자체는 안 바뀐다.** 바뀌는 것은 **경계 안쪽인데 안 주던 것**을
주는 일이다(§5). 경계를 넓히는 게 아니라 **덜 준 것을 채운다.**

```contract
policy_has_clock_target   = 1
policy_waiting_def_target = 1
```

## 0. 원칙

> **결정 시점에 존재하지 않는 값을 읽으면 반칙이다.**

미래 실현값을 보면 정책이 "이 트럭은 유난히 늦게 오겠군"을 알게 되는데, 실제
터미널은 그걸 모른다. 그러면 성능이 좋아 보여도 **실현 불가능한 성능**이다.

## 1. 정책이 볼 수 있는 것

| 종류 | 예 |
|---|---|
| **통지 시각** | `notified_gate_in(job)` — 공개 통지분만 |
| 현재 상태 | 블록 내부 대수 · 대기열 · 크레인 잔여 · 적치율 |
| 공개 ETA | `public_block_eta` — 통지 + 기대 주행 |
| 지도 정보 | `travelBaseSec`(거리÷속도) · 블록 간 거리 |
| 이력 | 이송 횟수 · 이연 횟수 |
| 본선 계획 | `planned_completion_s`(계획값) |

## 2. 정책이 **못 보는** 것

| 종류 | 왜 |
|---|---|
| `gateInTime` (아직 안 온 트럭) | **미래** |
| `travelSec` · `exitTravelSec` | 그 트럭이 실제 얼마 걸릴지는 **미래** |
| `blockInTime` · `jobDoneTime` · `gateOutTime` | 시뮬 **출력** |
| 본선 `actual_completion_s` | **미래** |
| 30분 창 밖의 트럭 | 아직 **통지 전** |
| 다른 블록의 이번 epoch 제안 | **동시 결정** — 구조적으로 불가 |

## 3. 학습 목표에는 실현값을 쓴다 — 이건 반칙이 아니다

```
입력(특징)  → 공개 정보만
목표(라벨)  → 실현값 사용 (D_i 는 실제로 일어난 일에서 계산)
```

**학습은 사후에 한다.** "그때 그렇게 했더니 이렇게 됐다"를 나중에 알려주는 것은
정상이다. 반칙은 **결정 시점에** 미래를 보는 것이다.

### ★v3 반사실도 같은 논리다 — 단, 선이 하나 더 필요하다

교사는 **미래를 1시간 굴려서** 라벨을 만든다([04b](04b-학습-잣대.md) §3). 이건
학습 때만 하므로 반칙이 아니다. 하지만 선을 못박아야 한다.

| | 미래를 봐도 되나 |
|---|---|
| **교사** (반사실 rollout · 라벨 생성) | ✅ 사후 계산이므로 |
| **학생** (Seller·Buyer · 배포) | ❌ **입력은 공개 정보만** |
| 판정 실행 | ❌ 학생만 돈다. 교사는 아예 안 불린다 |

**위험 지점**: 교사가 만든 라벨을 학생 **입력**에 섞으면(예: "예상 반사실 이득"을
특징으로) 그 순간 미래가 새어 들어온다. **라벨은 목표에만, 입력에는 절대 안 넣는다.**

## 4. 감사 이력 — 실제로 새던 곳

| 시점 | 무엇 | 조치 |
|---|---|---|
| 2026-08-09 (감사 치명 6) | `block_features` 가 실현 `a_gate_in` 을 읽음 | `notified_gate_in` 으로 교체 |
| 2026-08-09 (감사 치명 1) | critic 입력을 학습 직전 zeros 로 덮어씀 | 결정 시점 저장으로 정정 |
| YR-173 | BUY 견적망 입력 | 공개 정보만 — 실현 미래값 **한 줄도 안 읽음** 명시 |

**규칙(`sell_gain`)도 같은 경계를 지킨다**: "통지된 gate-in · 공개 ETA · 현재 내부
대수 · 통지된 미래 도착. 미래 대기열 예측은 결정론 배수 + 통지 도착만으로."

→ **규칙과 학습이 같은 정보로 겨룬다.** 규칙은 오라클이 아니다.

## 5. ★v3 변경 ④ — 경계 안쪽인데 **덜 준** 것

경계와 무관하게 **줄 수 있는데 안 주는** 정보가 있다. 이건 결함이다.

| 정보 | 관측 가능? | v2 | v3 | row |
|---|---|---|---|---|
| **지금 몇 시인가** (`t/end`) | ✅ 당연히 | ❌ 없음 | **추가** | [[YR-208]] |
| **실제 대기 대수** (`_waiting_at`) | ✅ 공개 관측 | ❌ `inside` 로 대체 | **병기** | [[YR-208]] |
| 이 트럭의 예상 서비스 시각 | ✅ 크레인이 계산 중 | ❌ | 추가 | [[YR-198]] |
| 목적지 블록의 크레인 부하 | ✅ | ❌ 출발지만 | 추가 | [[YR-198]] |

**두 row 로 갈라 넣는다** — [[YR-208]] 은 블록 요약 **7 → 9차원**(출처가 블록
자신), [[YR-198]] 은 **크레인 층에서 넘어오는 통신선**이라 성격이 다르다.
**한 번에 한 축**(설계 원칙 2).

`inside` 는 지우지 않고 **병기**한다 — 총 대수 − 줄 선 대수 = 작업 중·이동 중이라
그 차이도 정보다. 지우면 무엇이 효과를 냈는지 못 가른다.

### 왜 이 둘인가

**시각** — 구 critic 입력에 `min(1, t/end)` 로 있었으나 [[YR-189]] Q 전환에서
critic 을 없애며 **완전히 소멸**했다. 무대에 아침·저녁 **이중 피크**가 있는데
정책에 시계가 없다. "지금 06시라 곧 붐빈다"를 알 수 없다.

**대기 대수** — 정의가 어긋난다.

```
정책이 보는 inside      : gate_in ≤ t < gate_out            (블록 안 전부)
보상이 쓰는 _waiting_at : block_arrival ≤ t < service_start (줄 선 것만)
```

**채점은 "줄 선 대수"로 하면서 정책에는 "총 대수"를 준다.** 같은 특징값인데 실제
상황이 다르면 라벨이 갈리고, 그건 **"못 줄이는 잡음"으로 계측**된다 —
[[YR-199]] 잡음 하한(신호의 77.6%)의 일부를 설명할 수 있다.

### 넣기 전에 값어치를 먼저 잰다

[[YR-208]]·[[YR-198]] 둘 다 **학습 없이** 판정할 수 있다. 특징을 늘린 상태로
[[YR-199]] 의 잡음 하한(1-최근접 잔차)을 **다시 재기만** 하면 된다(각 20분).

| 결과 | 뜻 | 다음 |
|---|---|---|
| 하한이 내려감 | 그 정보가 **진짜 설명력**을 준다 | 학습에 투입 |
| 그대로 | 라벨이 원래 그만큼 무작위 | **넣지 않는다** |

**학습을 돌리기 전에 기각할 수 있다** — 이게 이 축을 3단계에 둔 이유다.
**판정 대역도 안 쓴다**(비판정 시드 9,900,0xx).

## 6. 리드타임이 분포가 되면 (축 ①과의 접점)

[02](02-무대.md) §4 에서 통지 리드가 트럭마다 달라지면 정보 경계에 두 가지가 생긴다.

| | 처리 |
|---|---|
| 아직 통지 안 된 트럭 | **후보에 아예 없다** — 경계가 저절로 지켜진다 |
| 통지 전 도착 (14.1%) | 통지 시점에 이미 도착 → 공간 판매 불가, 시간 이연만 |

**리드타임 자체는 정책이 봐도 된다** — "나는 이 트럭을 3시간 전에 알았다"는 결정
시점의 공개 사실이다. 미래가 아니다.
