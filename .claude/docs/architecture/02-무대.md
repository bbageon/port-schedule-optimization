# 02 — 무대 (v3 설계 · 축 ①④)

> **성격**: to-be 설계. 코드가 여기에 맞춰진다. → [index](README.md)
> **관련 코드**: `integrated/profiles.py` · `yard_layout.py` · `terminal_stream.py`

**v3 에서 물리는 안 바뀐다**(21블록·크레인 2대·24시간). 바뀌는 것은 **하루 물량이
축이 된 것**(§2-1)과 **트럭이 언제 통지되는가**(축 ① · §4)다.

## 0. 계약 (기계 검증 대상)

`verify_architecture.py` 가 **이 블록을 읽어** 코드와 대조한다.
값을 바꾸려면 **여기를 고친다** — 스크립트는 안 고쳐도 된다.
`_target` 접미는 **아직 안 한 작업**(⏳)이지 불일치가 아니다.

```contract
blocks              = 21
cranes_per_block    = 2
block_slots         = 1440
observe_s           = 86400.0
day_total           = 7500
truck_sla_s         = 1800.0
rho_vessel          = 10.0
gate_nearest_s      = 190
gate_farthest_s     = 410
lead_time_dist_target = 1
```

## 1. 물리

| | 값 | 근거 |
|---|---|---|
| 블록 | **21개** (`Y01`~`Y21`) | `terminal_layout().ids` |
| 블록당 크레인 | **2대** (`YC-L`, `YC-W`) | `profile.cranes` |
| 블록 규격 | 24 bay × 10 row × 6 tier = **1,440 슬롯** | `profile.block` |
| 배치 | **한 줄(단일 축)** — 게이트에서 거리순 | `layout.position_m()` |
| 게이트→블록 | **190 ~ 410초** | `gate_to_block_s()` = 거리 ÷ 속도 |

```
게이트 ─ Y01(190s) ─ Y02(201s) ─ … ─ Y21(410s)
        가까움 ←──────────────────────→ 멂
```

**⚠️ 실데이터와 다름**: DGT 는 **24종 이상**·**A열·E열 두 줄 + 검사장(`INS`)** 이다.
우리는 단일 축 21개 — 거리표 재작성이 [[YR-196]] 대상.

| | 값 |

| 본선 | **소2 · 중1 · 대 30% 확률** · 기항 물량 = `TEU × U(15%,30%)` → §2-2 |

**고정 재공량(WIP)** 무대다 — 도착 명단이 **사전 확정**되고 개방루프로 투입돼
두 정책이 **같은 트럭·같은 시각**을 받는다(짝비교의 근거).

## 2-1. ★하루 물량은 축이다 — 3,500 · 5,000 · 7,500 (사용자 결정 2026-08-20)

**셋 다 실제 항만에서 일어날 수 있는 오더 건수다**(사용자 제공). 하나를 고르는 게
아니라 **세 물량 전부에서 판정하고 전부 통과해야** 한다 — 구 3,600 단일 무대는
실측 범위의 **아래쪽 끝 하나만** 본 것이다.

```contract
load_levels_target = 3
```
| 물량 | 평균 | **피크** | 피크 가동률 | 성격 |
|---|---|---|---|---|
| 3,500 | 146/h | 475/h | 57% | 한산 — 구 무대와 사실상 같다 |
| 5,000 | 208/h | 679/h | 81% | 빡빡하지만 능력 안 |
| **7,500** | 313/h | **1,018/h** | **121%** | **피크 초과** — 쌓였다 밤에 빠진다 |

크레인 능력 840대/h(21블록×2대×3600÷180초). 7,500 도 하루로는 능력의 37%다.

### ★첫 실측(7,500) — 재배치의 부호가 뒤집혔다

**안 팔기 Φ 25,034.69 · 규칙 25,536.54 → `+501.86` 으로 재배치가 손해**(시드
9,900,501 짝비교·비판정). **3,600 에서는 −158.13 개선**했고 그게 논문 **서사 B 의
본 주장**이다. 원인이 **과포화 자체**인지 **규칙의 오판**인지에 따라 결론이
정반대다 — 후자면 그동안 못 찾던 "학습이 규칙을 이기는 조건"이다 → [[YR-210]]

### ⚠️ 과거 판정 수치와 직접 비교 불가

[[YR-180]] +97.94 · [[YR-195]] +39.92 · [[YR-200]] +61.66 은 전부 **3,600 무대** 값.
단 **앞으로의 판정은 성립한다** — 짝비교라 규칙 팔을 같은 런에서 다시 재기 때문
(비교 대상은 "그 부하에서의 규칙"이지 과거 절대값이 아니다).

## 2-2. 본선도 같은 크레인을 쓴다
소2·중1·**대1 은 30% 확률**, 기항 물량 `TEU × U(15%,30%)`. 선급이 정하는 것은 하루
물량이 아니라 **접안 시간**(13.5/22.5/**31.5h** — 대형은 24h 창을 넘는다)이고 제약은
**동시 접안 처리율**이다 → **[02b 본선](02b-본선.md)**

## 3. 난수는 전부 시드에서 미리 뽑힌다

```python
random.Random(f"h21d:arr:{seed}")   # 도착 시각      f"h21:mix:{seed}"   # 반입출·규격
random.Random(f"h21:resid:{seed}")  # 주행 오차      f"h21:exit:{seed}"  # 출문 주행
```

**정책이 결정할 시점에는 이미 다 확정돼 있다** — 세계는 결정적이고, 정책은
[이벤트가 온 것](00-라이프사이클.md)만 볼 수 있을 뿐이다.

이것이 [[YR-199]] 잡음 하한(신호의 77.6%)의 해석에 중요하다 — 그 잡음은
환경의 무작위성이 아니라 **우리가 준 특징으로 구분 안 되는 것**이다.

## 4. v3 변경 ① — 통지 리드타임을 분포로

### 지금: 30분 고정 (`ANNOUNCE_LEAD_S = 1800.0`)

**★정정 (2026-08-20)**: 여기 "결정 자체가 성립하지 않는다"고 적었으나 **과했다** —
리드가 같아도 도착 시각·반입출·규격·이송 이력은 다르므로 **고를 것은 있다.**
정확히 없는 것은 **정보 격차라는 축 하나**다 — "어느 트럭을 더 일찍 알았나"로
구분할 수가 없다. 그런데 **그 축이 규칙이 못 다루는 유일한 종류의 질문을 만든다**:

> 5시간 전에 아는 트럭을 지금 배정할까, 정보를 더 모으고 나중에 결정할까?

규칙(`sell_gain`)은 창 안의 정보로 순이득을 계산하는 **공식**이라 "기다리면 더
나은 선택지가 올 확률"이라는 개념이 아예 없다. 학습은 경험에서 그걸 배울 수 있다.
지금 무대에는 **그 질문 자체가 없다.**

### v3: 실측 분포에서 뽑는다

DGT 실측(`copino_notice_s` → `gateIn`, 100건): 중앙값 **1.27시간** ·
사분위폭 **2.36시간** · 음수(통지 전 도착) **14.1%**.

**두 팔로 잰다** — 리드 고정(현행) vs 리드 분포. 규칙 대비 격차가 어떻게 달라지는지가
판정 대상이다. 설계·사전등록 → [[YR-190]].

### ⚠️ 리드만 늘리면 아무것도 안 바뀐다

후보 자격이 **창** 기준이기 때문이다.

```python
iter_pre_gate_candidates(mbt, src, horizon_s=WINDOW_S)   # WINDOW_S = 1800
    → 공개 ETA 가 30분 안에 든 트럭만 후보
```

5시간 전에 통지해도 **후보가 되는 건 여전히 도착 30분 전**이라 정책이 할 수 있는
일이 안 늘어난다. **창이 리드를 따라가야** 긴 리드가 실제 기회가 된다(계산량 상한을
위해 창에 뚜껑을 씌운다) → [03](03-결정층.md) §5 · [[YR-190]]

### 음수 리드(14.1%)

통지보다 트럭이 먼저 오는 경우다. [00 라이프사이클](00-라이프사이클.md)이
`copinoNotice ≤ gateIn` 을 요구하므로 **리드 0 으로 눌러 담는다** — 통지 즉시
도착이라 공간 판매는 불가하고 시간 이연만 가능하다. 후보 생성 규칙이지 새 비용항이
아니다.

## 5. v3 변경 ④ — 정책에 덜 주던 것 (→ [05](05-정보경계.md))

### ② 정책이 시각을 모른다

`block_features` 7개에 **시각이 없다**:

```
[inside/10, pipeline/10, crane_backlog/3600, occupancy,
 vessel_slack/3600, announced_30/10, n_cands/6]
```

무대에 이중 피크가 있는데 **"지금 06시라 곧 붐빈다"를 알 수 없다.**
`t/end` 는 구 critic 입력에만 있었고 [[YR-189]] Q 전환에서 critic 을 없애며 소멸.

### ③ 대기 대수를 정책이 다른 값으로 본다

| | 정의 |
|---|---|
| 정책이 보는 `inside` | 게이트인 ≤ t < 게이트아웃 — **블록 안 전부** |
| 보상이 쓰는 `_waiting_at` | 블록도착 ≤ t < 서비스시작 — **줄 선 것만** |

**채점은 "줄 선 대수"로 하는데 정책에는 "총 대수"를 준다.**

**둘 다 [[YR-198]] 이며, 잡음 하한 재측정(20분·학습 불필요)으로 값어치를 먼저
잰다** — 특징을 늘려도 [[YR-199]] 잡음 하한이 안 내려가면 넣을 이유가 없다.

## 6. 안 바꾸는 것과 그 이유

| | 왜 유지 |
|---|---|
| 단일 축 21블록 | DGT 는 A·E 두 줄 + 검사장이지만, **RL 아이디어 검증이 목적**이라 무대 충실도는 후순위 ([[YR-196]] 🟡) |
| 사전 확정 도착 명단 | **짝비교의 근거** — 두 정책이 같은 트럭·같은 시각을 받아야 날 단위 t검정이 성립 |
| 시드 선추출 | 위와 같은 이유. 리드타임이 분포가 돼도 **시드에서 미리 뽑는 방식은 그대로** |
