# 02 — 무대 (v3 설계 · 축 ①④)

> **성격**: to-be 설계. 코드가 여기에 맞춰진다. → [index](README.md)
> **관련 코드**: `integrated/profiles.py` · `yard_layout.py` · `terminal_stream.py`

**v3 에서 물리는 안 바뀐다.** 21블록·크레인 2대·24시간·3,600대는 그대로다.
바뀌는 것은 **트럭이 언제 통지되는가**(축 ①) 하나다.

## 0. 계약 (기계 검증 대상)

`verify_architecture.py` 가 **이 블록을 읽어** 코드와 대조한다.
값을 바꾸려면 **여기를 고친다** — 스크립트는 안 고쳐도 된다.
`_target` 접미는 **아직 안 한 작업**(⏳)이지 불일치가 아니다.

```contract
blocks              = 21
cranes_per_block    = 2
block_slots         = 1440
observe_s           = 86400.0
day_total           = 3600
truck_sla_s         = 1800.0
rho_vessel          = 10.0
gate_nearest_s      = 190
gate_farthest_s     = 410
lead_time_dist_target = 1
```

## 1. 물리

| | 값 | 근거 |
|---|---|---|
| 블록 | **21개** (`Y01`~`Y21`) | `terminal_layout().ids` |
| 블록당 크레인 | **2대** (`YC-L`, `YC-W`) | `profile.cranes` |
| 블록 규격 | 24 bay × 10 row × 6 tier = **1,440 슬롯** | `profile.block` |
| 배치 | **한 줄(단일 축)** — 게이트에서 거리순 | `layout.position_m()` |
| 게이트→블록 | **190 ~ 410초** | `gate_to_block_s()` = 거리 ÷ 속도 |

```
게이트 ─ Y01(190s) ─ Y02(201s) ─ … ─ Y21(410s)
        가까움 ←──────────────────────→ 멂
```

**⚠️ 실데이터와 다름**: DGT 는 **24종 이상**이고 **A열·E열 두 줄 + 검사장(`INS`)**
이다. 우리는 단일 축 21개. 거리표 재작성이 [[YR-196]] 대상.

## 2. 물량과 시간

| | 값 |
|---|---|
| 하루 트럭 | **3,600대** |
| 반출 비율 | **0.6** (실측 61.6%) — DGT 는 49% |
| 40피트 비율 | 0.7 |
| 관측 계약 | warmup **7,200초** + measure **79,200초** = **86,400초(24h)** |
| 도착 패턴 | **아침·저녁 이중 피크** |
| 트럭 SLA | **1,800초**(30분) 초과부터 벌점 |
| 본선 가중 | **ρ = 10** — 본선 지연은 트럭의 10배 |

**고정 재공량(WIP)** 무대다 — 도착 명단이 **사전 확정**되고 개방루프로 투입된다.
그래서 두 정책이 **같은 트럭·같은 시각**을 받는다(짝비교의 근거).

## 3. 난수는 전부 시드에서 미리 뽑힌다

```python
random.Random(f"h21d:arr:{seed}")     # 도착 시각
random.Random(f"h21:resid:{seed}")    # 주행 오차
random.Random(f"h21:mix:{seed}")      # 반입/반출·규격
random.Random(f"h21:exit:{seed}")     # 출문 주행
```

**정책이 결정할 시점에는 이미 다 확정돼 있다.** 즉 진짜 우연이 아니라
**가려놓은 것**이다 — 정책은 통지된 것만 볼 수 있을 뿐, 세계는 결정적이다.

이것이 [[YR-199]] 잡음 하한(신호의 77.6%)의 해석에 중요하다 — 그 잡음은
환경의 무작위성이 아니라 **우리가 준 특징으로 구분 안 되는 것**이다.

## 4. v3 변경 ① — 통지 리드타임을 분포로

### 지금: 30분 고정

```
ANNOUNCE_LEAD_S = 1800.0   # 모든 트럭이 정확히 30분 전 통지
```

**모든 트럭이 정보 측면으로 똑같다.** 그래서 **"어느 트럭을 언제 다룰까"라는
결정 자체가 성립하지 않는다** — 고를 이유가 없으면 규칙과 학습이 다를 이유도 없다.

### v3: 실측 분포에서 뽑는다

DGT 실측 (`copino_notice_s` → `gateIn`, 표본 100건):

| | 값 |
|---|---|
| 중앙값 | **1.27시간** |
| 사분위폭 | **2.36시간** |
| 음수(통지 전 도착) | **14.1%** |

**이게 왜 축을 만드나**: 리드타임이 제각각이면 트럭마다 **"내가 아는 정도"가 다르다.**
5시간 전에 안 트럭은 여유롭게 옮길 수 있고, 이미 문 앞인 트럭은 손댈 수 없다.
**정보 격차가 있어야 정보를 쓰는 정책이 이긴다.**

### ★리드와 검토 창을 분리해야 한다

지금 상수 하나(`ANNOUNCE_LEAD_S = 1800`)가 **두 역할**을 겸한다.

| 역할 | v3 |
|---|---|
| **통지 리드** — 얼마나 미리 아나 | **트럭마다 다름** (위 분포) |
| **검토 창** — 판매를 검토하는 구간 | **상수 유지** (계산량 상한) |

리드가 5시간이어도 5시간 내내 검토하지는 않는다 — 계산량이 그만큼 는다.
분리 지점은 [03 결정층](03-결정층.md) §5 → [[YR-190]] 착수 시 확정.

### 음수 리드(14.1%)를 어떻게 다루나

통지보다 트럭이 먼저 오는 경우다. **재배치 후보에서 빼는 게 아니라, 통지 시점부터
남은 시간이 0 인 것으로 둔다** — 이미 도착했으니 공간 판매는 불가하고 시간 이연만
가능하다. 이건 후보 생성 규칙이지 새 비용항이 아니다.

## 5. v3 변경 ④ — 정책에 덜 주던 것 (→ [05](05-정보경계.md))

### ② 정책이 시각을 모른다

`block_features` 7개에 **시각이 없다**:

```
[inside/10, pipeline/10, crane_backlog/3600, occupancy,
 vessel_slack/3600, announced_30/10, n_cands/6]
```

무대에 이중 피크가 있는데 **"지금 06시라 곧 붐빈다"를 알 수 없다.**
`t/end` 는 구 critic 입력에만 있었고 [[YR-189]] Q 전환에서 critic 을 없애며 소멸.

### ③ 대기 대수를 정책이 다른 값으로 본다

| | 정의 |
|---|---|
| 정책이 보는 `inside` | 게이트인 ≤ t < 게이트아웃 — **블록 안 전부** |
| 보상이 쓰는 `_waiting_at` | 블록도착 ≤ t < 서비스시작 — **줄 선 것만** |

**채점은 "줄 선 대수"로 하는데 정책에는 "총 대수"를 준다.**

**둘 다 [[YR-198]] 이며, 잡음 하한 재측정(20분·학습 불필요)으로 값어치를 먼저
잰다** — 특징을 늘려도 [[YR-199]] 잡음 하한이 안 내려가면 넣을 이유가 없다.

## 6. 안 바꾸는 것과 그 이유

| | 왜 유지 |
|---|---|
| 단일 축 21블록 | DGT 는 A·E 두 줄 + 검사장이지만, **RL 아이디어 검증이 목적**이라 무대 충실도는 후순위 ([[YR-196]] 🟡) |
| 사전 확정 도착 명단 | **짝비교의 근거** — 두 정책이 같은 트럭·같은 시각을 받아야 날 단위 t검정이 성립 |
| 시드 선추출 | 위와 같은 이유. 리드타임이 분포가 돼도 **시드에서 미리 뽑는 방식은 그대로** |
