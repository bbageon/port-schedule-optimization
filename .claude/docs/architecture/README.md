# 아키텍처 v3 — 통합 아키텍처 (index)

> **성격**: 이 문서는 **as-is 기록이 아니라 to-be 설계**다. v3 로 전면 리팩토링하는
> 목표 구조를 정의하고, **코드가 여기에 맞춰진다.**
>
> 코드와 다르면 **코드가 아직 안 따라온 것**이다(설계가 틀린 게 아니다). 다만
> 설계가 틀렸다고 판단되면 **이 문서를 먼저 고치고** 코드를 따라오게 한다.
>
> **이름 주의**: `BlockQ-v1~v4` 는 **크레인 망**의 세대로 이미 쓰인다. 여기서
> 말하는 **v3 는 재배치 축 아키텍처 전체**의 세대다 — 다른 축이다.

## 세대

| | 무엇이 핵심이었나 | 결과 |
|---|---|---|
| **v1** 확률 정책 | PPO — "이 트럭을 내놓을 확률" · critic 기준선 | 규칙 대비 **+97.94**. critic 붕괴·보상 0 이 91% |
| **v2** 비용 채점 | Q 회귀 — "비용이 얼마" · argmin · 문턱 | 규칙 대비 **+39.92**(최선). 구조 결함 3종 소멸, 그래도 못 넘음 |
| **v3** **통합 아키텍처** | 데이터·보상·구조·정보를 **한 설계로 묶는다** | 진행 중 |

## v3 는 왜 "통합"인가

**v1·v2 는 재배치 정책 한 칸만 갈아끼웠다.** 무대도 스키마도 보상식도 그대로 두고
"확률로 고를까, 비용으로 고를까"만 바꿨다. 두 번 다 규칙을 못 넘었다.

**막힌 이유가 정책 한 칸에 없었다.** 네 군데가 동시에 걸린다 —

| # | 무엇 | 지금 무엇이 막나 | 어디서 |
|---|---|---|---|
| **① 데이터** | 오더(통지·예정) 와 이벤트(실현) 를 가른다 · 필드 6개 | 셋이 **한 값**이라 예약 준수·리드타임 축이 **아예 없다** | [01](01-오더-스키마.md) |
| **② 보상** | 추정 → 진짜 반사실 → **장기 반사실**(H=1h) · 단위를 **원화**로 | "밀렸을 것이다"라는 **추측**을 정답으로 쓴다 | [04b](04b-학습-잣대.md) |
| **③ 구조** | Seller·Buyer 두 축 · 교사(rollout)→학생(추론) | 시야(40분)와 신용 배분을 **동시에 못 가진다** | [03](03-결정층.md) |
| **④ 정보** | 시각 · 실제 대기 대수 · 예상 서비스 시각 | 채점에는 쓰면서 정책에는 **안 준다** | [05](05-정보경계.md) |

**그리고 이 넷을 재는 무대 자체가 하나가 아니다** — 하루 물량 **3,500·5,000·7,500**
셋 다 실측이라 **전부에서 판정하고 전부 통과해야** 한다([02](02-무대.md) §2-1).
7,500 첫 실측에서 재배치의 부호가 뒤집혀 [[YR-210]] 이 그 진단을 맡는다.

**하나만 고치면 나머지가 발목을 잡는다.** ②반사실을 넣어도 ①시각이 한 값이면
"미루기"의 차이가 안 잡히고, ③시야를 넓혀도 ④시계가 없으면 피크를 못 읽는다.
그래서 **네 축을 한 설계로 놓고** 순서대로 넣되, 판정은 축마다 따로 한다.

**v3 = 반사실이 아니다.** 반사실은 ② 하나다.

**v2 가 남긴 벽**: 학습 잣대의 시야가 **트럭 한 대의 방문(약 40분)** 이고, 규칙도
근시안이라 **RL 에게 구조적 우위가 없다.** [[YR-199]] 가 예측 정확도의 한계도 쟀다
(오차의 95%가 지금 특징으로는 못 줄이는 잡음).

## 리팩토링 순서

| 단계 | 무엇 | 상태 |
|---|---|---|
**전부 이미 등록된 row 다.** 새 작업을 만들지 않는다 — v3 는 흩어져 있던 row 들을
**네 축으로 묶어 순서를 준 것**이다.

| 단계 | 축 | row | 무엇 | 판정 방법 |
|---|---|---|---|---|
| **0** | 무대 | [[YR-210]] | **부하 3수준에서 재배치가 유효한가** — 부호 전환점 | 비판정 (학습 불필요) |
| **1** | ① | [[YR-187-B]] | 스키마에 실측값 · `record_swap()` 배선 | **회귀만** (동작 불변) |
| 2 | ① | [[YR-190]] | 리드타임을 분포로 (불확실성 σ 스윕) | 규칙 대비 · 새 대역 |
| 3 | ④ | [[YR-208]] · [[YR-198]] | 시각·대기수 / 크레인 예상 서비스 시각 | **잡음 하한** (학습 불필요) |
| 4 | ② | [[YR-201]] → [[YR-202]] | 진짜 반사실 신용 → 미래 비용항 | 잡음 하한 |
| 5 | ③ | [[YR-203]] | 독립 SELL/BUY 요청 · 배치 Resolver 계약 | 구조 계약 |
| 6 | ② | [[YR-207]] | 원화 환산 목적함수 (안전운임 40,000원/h) | 단위 전환 |
| 7 | ② | [[YR-204]] | **장기 반사실 교사** H=1h | 잡음 하한 |
| 8 | ③ | [[YR-205]] | Seller·Buyer 학생 · 운영 추론 | 규칙 대비 · 새 대역 |

### ⚠️ 5~8 은 지금 착수 금지

[[YR-203]]·[[YR-207]]·[[YR-204]]·[[YR-205]] 는 전부 **"현재 performance 게이트
해소 전 착수 금지"** 로 등록돼 있다. 규칙을 못 넘고 있는 상태에서 구조를 더 키우면
무엇이 원인인지 못 가린다.

**지금 할 수 있는 것은 1~4** — 데이터 정비(①) · 정보 보강(④) · 보상 정확도(②)다.
셋 다 **판정 대역을 거의 안 쓴다**(1은 회귀, 3·4는 잡음 하한).

**통합 설계지만 통합 투입은 아니다.** 네 축을 한 설계로 정의하되 **한 번에 하나씩**
넣고 축마다 판정한다(설계 원칙 2).

## 교차검증 — 리팩토링 진행률

```bash
PYTHONPATH=src python .claude/docs/architecture/verify_architecture.py
```

각 문서의 ```contract 블록이 **목표값**이고 스크립트가 코드와 대조한다.
`_target` 접미 키는 **아직 안 한 작업**으로 분류돼 "진행중"으로 표시된다 —
불일치(❌)와 미완(⏳)을 구분하기 위해서다.

**2026-08-20 기준**: 계약 30개 · 일치 23 · **불일치 0** · 미배선 0 · **진행중 10**.
진행중 10개가 곧 **v3 리팩토링 잔여량**이다.

| ⏳ 진행중 | 지금 → 목표 | 단계 |
|---|---|---|
| `lifecycle_stages_target` | 4 → 5 (`copinoNoticeTime` 없음) | 1 |
| `order_fields_target` | 17 → 6 | 1 |
| `record_fields_target` | 5 → 7 (`record_swap()` 미호출) | 1 |
| `load_levels_target` | 1 → 3 (3,500·5,000·7,500) | **0** |
| `lead_time_dist_target` | 0 → 1 | 2 |
| `policy_has_clock_target` · `policy_waiting_def_target` | 0 → 1 | 3 |
| `block_dim_target` | 7 → 9 | 3 |
| `counterfactual_h_s_target` | 0 → 3600 | 7 |
| `seller_buyer_target` | 0 → 1 | 8 |

**값은 문서에 한 벌만 둔다.** 스크립트에 박아두면 복사본이 셋이 되어 문서만
낡아도 아무도 못 잡는다.

| 상황 | 무엇을 고치나 |
|---|---|
| 설계가 바뀜 | **문서 contract 블록** — 스크립트는 안 건드린다 |
| 새 계약값 | 문서 1줄 + `GETTERS` 1줄 |
| 새 종류의 검사 | 스크립트에 로직 |
