**오더 하나가 지나가는 길**이다. 스키마도 보상도 재배치 가능 구간도 전부 여기서
파생되므로 다른 문서보다 앞에 둔다.

**오더 1건은 반드시 이 다섯 단계를 이 순서로 지난다** (사용자 확정 2026-08-20).
시뮬레이션이라도 이 순서를 어기면 안 된다.

```
코피노 수신 ──► 게이트 진입 ──► 블록 진입 ──► 작업 완료 ──► 게이트 아웃
copinoNotice    gateIn         blockIn       jobDone       gateOut
     ①              ②             ③            ④             ⑤
  오더가 생김    ← ─ ─ ─ ─ ─ 터미널이 이벤트를 전송 ─ ─ ─ ─ ─ →
```

```contract
lifecycle_stages_target = 5
```

### 이 순서가 강제하는 것

| 불변식 | 뜻 |
|---|---|
| `copinoNotice ≤ gateIn ≤ blockIn ≤ jobDone ≤ gateOut` | 시각이 **단조 증가** |
| 건너뛰기 없음 | `jobDone` 이 찍혔는데 `blockIn` 이 `None` 일 수 없다 |
| 되돌아가기 없음 | 각 단계는 오더당 **한 번**만 |

**`serviceStart` 는 이 다섯에 없다.** 터미널이 안 보내주는 값이라 라이프사이클의
단계가 아니고, `blockIn ≤ serviceStart ≤ jobDone` 사이에 끼는 **시뮬레이터 내부
관측**이다 (→ §3-1).

### 재배치가 가능한 구간이 여기서 정해진다

| 재배치 | 언제 가능 | 왜 |
|---|---|---|
| **공간 판매** (`conLoc` 변경) | **① 통지 후 ~ ② 게이트 진입 전** | 게이트를 지나면 이미 그 블록을 향해 달리고 있다 (`gate_in_observed` 면 후보 제외) |
| **시간 이연** (+15분) | 〃 | 아직 안 왔으니 늦출 수 있다 |
| 반출(`inOut=0`) 공간 판매 | **불가** | 꺼낼 컨테이너의 위치가 이미 정해져 있다 |

**판단은 그 구간 안에서 딱 한 번** — 공개 ETA 가 재배치 창에 **처음 들어온** 60초
epoch 이다([[YR-203]] · [03](03-결정층.md) §4). 코피노를 받은 순간이 아니다.

### 지금 어디까지 검사하나

| 구간 | 검사 |
|---|---|
| `gateIn ≤ blockIn ≤ serviceStart ≤ jobDone ≤ gateOut` | ✅ `test_yr089_time_contract.py::test_event_order_per_truck` (구 2블록 무대·완료 트럭만) |
| **`copinoNotice ≤ gateIn`** | ❌ **없음** — 지금은 둘이 같은 값이라 자명하고, [[YR-190]] 이 리드타임을 분포로 바꾸면 의미가 생긴다 |
| 건너뛰기·중복 | ❌ 없음 — `TimeLedger` 의 setter 는 순서를 **전혀 검사하지 않는다**(그냥 대입) |

**⚠️ 실측과 충돌한다**: DGT 표본의 **14.1%가 통지보다 먼저 도착**한다
(`gateIn < copinoNotice`). 라이프사이클을 그대로 강제하면 그 14%를 표현할 수 없다.
[[YR-190]] 착수 시 "리드타임 0 으로 눌러 담을지 / 순서 위반을 허용할지"를 정한다.

## 시계 — 이벤트는 무엇으로 시각을 찍나

**시뮬레이션은 시계 `t` 를 하나만 갖는다** (초 단위 · `t=0` 이 하루 시작).
다섯 단계의 시각은 전부 **그 이벤트가 일어난 순간의 `t`** 다.

| | 규칙 |
|---|---|
| 기록 방식 | 이벤트가 끝나는 순간 **그때의 `t` 를 그대로 적는다** |
| 유도 금지 | 나중에 "아마 이때쯤이었을 것"으로 **되계산하지 않는다** |
| 미발생 | 아직 안 온 단계는 **비어 있다**(`None`) — 0 이나 추정값으로 채우지 않는다 |
| 단위 | 초. 시각이지 소요시간이 아니다 |

**"미발생은 비어 있다"가 정보 경계의 실체다.** 정책이 미래를 못 보는 이유는
우리가 가려서가 아니라 **그 칸이 아직 비어 있기 때문**이다.

### 이벤트 시각과 결정 시각은 다르다

```
이벤트   ── 아무 때나 일어난다        t = 43,127.4 초
결정     ── 60초 격자에서만 열린다     t = 43,080 · 43,140 · …
```

트럭은 격자에 맞춰 도착하지 않는다. **이벤트는 연속 시각에 찍고, 결정은 격자에서
한다.** 그래서 "결정 시점에 마지막으로 본 상태"와 "지금 실제 상태"가 최대 60초까지
어긋날 수 있다 — 이건 결함이 아니라 결정 주기의 정의다.

### 정책도 같은 시계를 본다

`t` 는 결정 시점에 당연히 관측 가능한 값이므로 **정책이 봐도 된다.**
지금 설계는 정책 특징에 `t` 를 넣지 않았는데 그건 [05 정보 경계](05-정보경계.md)
§5 가 **결함으로 적어둔 것**이다 → [[YR-208]].

## 기록의 주인은 오더다

시각은 **오더 레코드가 들고 있다** ([01](01-오더-스키마.md) §3). 별도 장부에
두고 오더가 참조하는 구조가 아니다.

| | |
|---|---|
| 원본 | **오더 1건** — 자기 다섯 시각을 자기가 갖는다 |
| 비용·KPI | 그 오더들을 **읽어서** 적분한다 |

실제 터미널과 같은 모양이다 — 이벤트가 오면 그 작업 지시서에 시각이 찍히고,
정산은 그 지시서들을 모아서 한다. **적분이 원본을 갖지 않는다.**
