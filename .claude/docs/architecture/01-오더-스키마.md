## 0. 데이터는 둘이다

한 트럭의 방문에 얽힌 데이터는 **언제 생기느냐가 다르다.**

| | 무엇 | 언제 생기나 | 정책 |
|---|---|---|---|
| **① 오더** | 터미널이 **외부에서 받는** 작업 지시 | 코피노 접수 **1회** | ✅ 전부 |
| **② 실행 기록** | 트럭이 **실제로 움직인 사실** | **이벤트가 끝날 때마다 터미널이 전송** | 지난 것만 |

**둘뿐이다.** 오더에는 미래가 한 조각도 없고, 기록은 **일어난 뒤에야** 생긴다.
그래서 정보 경계가 **구조로** 보장된다 — 정책이 미래를 못 보는 이유는 우리가
가려놨기 때문이 아니라 **아직 이벤트가 안 왔기 때문**이다.

**★정정 (2026-08-20 사용자 지적)**: 이전 판은 네 시각을 "시나리오가 미리 정해둔
숨은 값"으로 적었다. **틀렸다** — 기사가 게이트인·블록인·작업완료·게이트아웃 하면
**터미널이 그 이벤트를 전송해 준다.** 없는 값이 아니다. 시뮬레이터가 그것을
*만들어내야* 하는 건 맞지만 그건 **구현 사항**(§2)이지 데이터 층이 아니다.

DGT 로그는 ①과 ②가 한 줄이다(로그이므로). 대조할 때 감안한다.

**라이프사이클이 전제다** — 오더 1건은 `코피노 수신 → 게이트 진입 → 블록 진입 →
작업 완료 → 게이트 아웃` 다섯 단계를 이 순서로 지난다. 이 문서의 시각 필드·파생값은
전부 거기서 나온다 → **[00 라이프사이클](00-라이프사이클.md)**

## 1. ① 오더 — 코피노 1통으로 확정 (6)

**코피노 1건 = 오더 1건 = 컨테이너 1개.** 20피트 2개를 실었으면 **오더 2건**이다.

| 필드 | 타입 | 뜻 | 정책 |
|---|---|---|---|
| `docKey` | str | 방문 고유키. **블록명 접두 없음** | ✅ |
| `inOut` | int | **반출 0 · 반입 1** | ✅ |
| `copinoNoticeTime` | float | 코피노 접수 — **터미널이 알게 된 순간** | ✅ |
| `inOutReserveTime` | float | 기사가 신고한 **반출입 예정 시각** | ✅ |
| `conLoc` | str | 배정 블록 (**기정**) | ✅ |
| `conNo` | str | 컨테이너 번호 (**기정**) | ✅ |

**`copinoNoticeTime` 과 `inOutReserveTime` 은 함께 들어온다** — 코피노 한 통에
"지금 접수했고, 이때 들어가겠다"가 같이 담긴다.
**규격(`size`)은 넣지 않는다** — 오더 1건 = 컨테이너 1개라 개수 정보가 불필요하다.

## 2. 시뮬레이터는 그 이벤트를 만들어내야 한다 (구현 사항)

실제 터미널에서는 트럭이 움직이면 **이벤트가 온다.** 우리는 시뮬레이터라 그
이벤트를 **직접 만들어야** 하고, 실험을 재현해야 하므로 재료를 시드에서 뽑는다.

| 만들 이벤트 | 무엇으로 만드나 | 코드 |
|---|---|---|
| `gateInTime` | 도착 시각을 시드에서 추출 | `random.Random("h21d:arr:{seed}")` |
| `blockInTime` | `gateIn + 진입 주행 소요` | `arr = realized + travel_s` |
| `gateOutTime` | `jobDone + 출문 주행 소요` | `r.gate_out = t + exit_travel_s` |

**주행을 '소요시간'으로 들고 있는 이유**: 재배치하면 목적지가 바뀌어
`blockInTime` 이 달라진다. **소요는 트럭 고유값**이라 블록이 바뀌어도 유지된다.

**이건 데이터 층이 아니다.** 오더도 기록도 아니고 **시뮬레이터 내부의 생성
재료**다. 레코드에 노출하지 않는다 — 노출하면 정책이 **아직 안 온 이벤트**를
미리 보게 된다.

**DGT 와 방향이 반대다** — 로그에는 `blockInTime` 이 이미 찍혀 있고 소요를
거기서 유도한다. 우리는 결과를 적는 게 아니라 **만들어야** 한다.

## 3. ② 실행 기록 — 이벤트 종료마다 터미널이 전송 (7 · 초기 `None`)

### 터미널이 전송하는 이벤트 — 넷

| 필드 | 언제 | 기록 API |
|---|---|---|
| `gateInTime` | 게이트 진입 | `TimeLedger.register()` |
| `blockInTime` | 블록 도착 | `.block_arrival()` |
| `jobDoneTime` | 작업 완료 | `.job_done()` |
| `gateOutTime` | 출문 | `.job_done()` 이 함께 확정 |

**기사가 그 지점을 통과하면 터미널이 전송한다.** 그 시각이 지나야 레코드에
나타나므로 정책이 오더를 읽어도 미래를 못 본다 — 가려놓은 게 아니라 **아직 안
온 것**이다.

### 전송되지 않는데 우리가 쓰는 것 — 하나

| 필드 | 언제 | 기록 API |
|---|---|---|
| **`serviceStartTime`** | 크레인이 잡음 | `.service_start()` |

**⚠️ 터미널이 이건 안 보내준다** (DGT 실데이터에도 없다). 시뮬레이터라서 알 수
있을 뿐이다. 그런데 **보상 계산의 두 곳**이 이걸 쓴다 → 아래 §3-1.

**실데이터로 가면 이 항이 사라진다.** 그때 무엇으로 대체할지는 그 시점의 결정이다.

### 재배치가 일어나면 갱신되는 것 — 둘

| 필드 | 언제 | 기록 API |
|---|---|---|
| `prevConLoc` | **판매 확정** — 기존 `conLoc` 을 보관하고 `conLoc` 을 새 블록으로 | `record_swap()` |
| `conSwapReason` | 〃 — 사유 | 〃 |

**`moveLoc` 은 두지 않는다** (2026-08-20 결정) — `conLoc` 이 **항상 현재 블록**을
가리키고, 바뀔 때 옛 값이 `prevConLoc` 으로 간다. 필드 둘이 "어느 게 지금인지"를
헷갈리게 만드는 것보다 낫다.

## 3-1. ★`serviceStartTime` 은 왜 못 지우나

보상 계산의 **두 곳**에서 쓰인다.

**① 크레인 점유 시간** — "기다린 시간"과 "작업한 시간"을 가른다.

```python
occupy = job_done − service_start          # ← 이것만이 진짜 점유
b_dst  = own + blocked_dst × occupy/3600 + vessel_pressure(..., occupy)
```

없으면 `blockIn → jobDone` 을 써야 하는데, 그러면 **줄 서서 기다린 20분까지
크레인 점유로 센다**(실제 작업은 3분).

**② 누가 "대기 중"인지 판정** — `_waiting_at()` 이
`block_arrival ≤ t < service_start` 로 큐를 센다. 없으면 **작업 중인 트럭까지
대기로 센다.**

**유도 불가**: 작업시간이 트럭마다 다르다(재취급·규격). 표준 180초(`SVC_REF_S`)는
**예측용**이지 실측이 아니다.

**⚠️ 그래서 실데이터가 아픈 자리다.** 터미널이 안 보내주므로 `occupy` 를 계산할
수 없고 **보상의 큰 항이 사라진다.** (2026-08-18 인계 회신에서 이 결손을 "영향
낮음"이라 적었으나 **정정한다** — 위 두 용도를 보면 영향이 크다.)

지금 연구 목표는 **RL 아이디어의 효과 검증**이지 실환경 적용이 아니므로
시뮬레이터가 아는 값을 그대로 쓴다. 실데이터로 갈 때 다시 본다.

## 4. 파생 (저장하지 않음)

라이프사이클의 이웃한 두 시각을 빼면 나온다.

| 값 | 식 | 값 | 식 |
|---|---|---|---|
| **`turnTime`** | `gateOut − gateIn` | 진입 주행 | `blockIn − gateIn` |
| 리드타임 | `gateIn − copinoNotice` | 대기 | `serviceStart − blockIn` |
| **예약 준수 오차** | `gateIn − inOutReserve` | 작업 | `jobDone − serviceStart` |
| | | 출문 주행 | `gateOut − jobDone` |

**저장하지 않는 이유**: 시각에서 전부 유도된다. 중복 저장은 불일치의 원인.

## 5. v2 에서 버리는 것

| 필드 | 왜 |
|---|---|
| `job_id`·`block`·`arrival_s`·`size_ft40` | 구 이름 |
| `requested_flow` · `fallback_reason` | **합성 인공물** — 생성기가 "반출로 만들고 싶었다" / "꺼낼 컨테이너가 없어 반입으로 바꿈"을 기록한 것. **실데이터에 없는 개념**이다 |
| `size_class` | 오더 1건 = 컨테이너 1개이므로 불필요 |
| `travel_base_s` | **읽는 곳 0** — `layout.gate_to_block_s(conLoc)` 로 계산 가능 |
| `travel_s`·`exit_travel_s` | 오더가 아니라 **시뮬레이터 생성 재료**(§2)로 이동 |
| `schema` | 행마다 반복할 이유 없음 — **파일 머리에 한 번** |

BNCT 명세가 `fallback_reason` 을 `conSwapReason` 에 대응시켰으나 **완전히 다른
것**이라 정정했다(2026-08-18).

| `docKey` | `'Y01:D-00000'` | 블록 접두 없음 |
| 기록 5시각 | 장부에만 · 오더와 **연결 안 됨** | 병합 |
| `prevConLoc` | 필드는 있으나 `record_swap()` **미호출** | 판매 확정 시 갱신 |
